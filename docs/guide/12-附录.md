## 一、术语表

| 术语 | 含义 |
|:--|:--|
| **主 Reactor / 主循环** | 主线程的 `EventLoop`，只负责 `accept` |
| **子 Reactor / 子循环** | 子线程的 `EventLoop`，处理已建立连接的读写 |
| **连接归属** | 一个连接的 fd、协议状态、超时定时器全部只属于一个线程 |
| **事件源** | 任何能让 `epoll_wait` 返回的输入：socket、`timerfd`、`eventfd`、`signalfd` |
| **触发模式** | `-m` 的取值，监听侧与连接侧各自的 LT/ET 组合 |
| **LT / ET** | 水平触发（持续通知）与边沿触发（只在状态变化时通知） |
| **半关闭** | 对端关闭写端（`EPOLLRDHUP`），本端仍可发送 |
| **原项目 / 旧架构** | TinyWebServer 的半同步 / 半反应堆实现 |
| **本项目 / 新架构** | 二次开发后的主从 Reactor 实现 |
| **缓冲块（Batch）** | 日志异步写入的落盘单位，默认 64 KiB |
| **背压** | 写盘速度跟不上写入速度，此时丢弃新行并计数 |
| **软上限** | 允许略微超出、以换取实现简化的上限（如 `split_lines`） |
| **同时段 A/B** | 把旧代码用 `git worktree` 重建，与当前代码在同一时段背靠背测量 |
| **阶段零至四** | 本项目的五个推进阶段（基线 / 工程基础 / 正确性 / 并发 / 性能） |

## 二、参数速查

```bash
./build/server [-p port] [-l LOGWrite] [-m TRIGMode] [-o OPT_LINGER] \
               [-s sql_num] [-t thread_num] [-c close_log] [-f config_file]
```

| 参数 | 含义 | 默认 | 取值 |
|:--|:--|--:|:--|
| `-p` | 监听端口 | 9006 | 1~65535 |
| `-l` | 日志写入方式 | 1 | 0 = 同步（每行落盘），1 = 异步（批量落盘） |
| `-m` | 触发模式组合 | 0 | 0 = LT+LT，1 = LT+ET，2 = ET+LT，3 = ET+ET |
| `-o` | 优雅关闭连接 | 0 | **有意不产生效果**，见下 |
| `-s` | 数据库连接池大小 | 8 | ≥ 1 |
| `-t` | 子 Reactor 线程数 | 8 | ≥ 0（**0 = 不建子线程，全归主循环**，用于对照） |
| `-c` | 关闭日志 | 0 | 0 = 打开，1 = 关闭 |
| `-f` | 配置文件路径 | `./config.ini` | 显式指定却找不到文件时**终止启动** |

**命令行优先于配置文件**，两者可混用。未识别的键会终止启动。

### 配置文件（`config.ini`，模板见 `config.example.ini`）

| 节 | 键 |
|:--|:--|
| `[server]` | `port`、`trig_mode`、`opt_linger`、`thread_num`、`close_log`、`root_dir` |
| `[database]` | `host`、`port`、`user`、`password`、`database`、`pool_size` |
| `[log]` | `write_mode`、`dir`、`file`、`buf_size`、`split_lines`、`batch_buf_size`、`flush_interval` |

日志各项的取值范围见 [README](../README.md) 的「日志配置」一节；越界在启动阶段直接报错，而不是静默夹取。

### `-o` 为什么有意不产生效果

`-o`（`opt_linger`）当前施加在**监听描述符**上，本就无效果。把它挪到连接描述符上会让它生效——而 `SO_LINGER { l_onoff = 1, l_linger = 0 }` 在连接描述符上的语义是「`close` 时发送 **RST** 而非 FIN，并丢弃未发送的数据」，对 Web 服务端是**有害**的：会截断响应、破坏长连接。

因此**有意保持它无效果**，并在配置示例与 README 中写明理由。保留该参数是为**兼容原项目的命令行接口**。

> 这是「**区分『没做』与『决定不做』**」的一个实例：状态被**决定**才算闭环，被**遗忘**则不是。

**「仍开放」不等于「该做」**——其中很多属于明确的功能边界。以下四条是**既真实、又与「已修缺陷可能复发」相关**的。

### 4.2 值得优先处理的四项

| # | 项 | 说明 |
|--:|:--|:--|
| 1 | **`http_conn` 的请求行/头部状态机与表单解析仍无单测** | URL 解码与路径规范化已由 `url_codec` 覆盖（10 个用例）。成本最低的下一步是把 `parse_form_body` 提取为独立单元——它是无状态纯函数，不必拆分连接管理 |
| 2 | **`-Werror` / 格式检查 / Sanitizer 未纳入 CI** | CI 目前只跑单元测试，**无法阻止新告警进入**。格式检查需先固定 `clang-format` 版本；Sanitizer 因耗时适合作为独立 workflow |
| 3 | **`Transfer-Encoding: chunked` 不支持** | 同一个问题在三份记录里各记一次，**从未处理**。「重复记录但无人处理」本身就是清单的盲区 |
| 4 | **`webserver.cpp` 的 `m_root` 仍是手动内存管理** | 即「内存管理 RAII 化」标为「部分完成」的实际缺口，原因见 [05](05-生命周期与资源管理.md) §5（**析构顺序约束**） |

### 4.3 一批结构清理项（不影响正确性）

全项目审核（`033`）列出了一批死代码与结构问题，至今未处理：

- `lock/locker.h` 中未使用的成员（`cond`、`sem` 的隐式拷贝赋值）
- `GetFreeConn()`、`LogConfig::close_log`、`Channel::m_revents`、`TcpConnection::fd()/peer()` 等**未被调用的接口**
- `http_conn.cpp` 职责混杂（解析、路由、上传、数据库访问、HTML 生成同处一文件）

**它们被如实记入清单，而不是存在于「没写就等于没有」的状态。**

### 4.4 「接受的限制」里的典型例子

| 项 | 为什么接受 |
|:--|:--|
| `-o` 不实现 | 让 `l_linger = 0` 的 RST 语义真正生效对 Web 服务端有害 |
| 符号链接未处理 | 站点根目录下无符号链接，上传目录不在根内 |
| 静态资源无扩展名限制 | 对静态站点属预期行为 |
| 上传与列表无鉴权 | 项目无会话机制 |
| 扩展名白名单基于名称而非内容 | 因一律按附件下载，风险边界可接受 |
| 口令强度未校验 / 无失败频次限制 / 无修改重置流程 | 属功能边界 |
| 客户端与服务端同机 | 测量环境固有 |
| 崩溃时最多丢一个 `flush_interval` 的日志 | 批量落盘的固有代价 |
| `split_lines` 由精确上限变为软上限 | 精确上限需按行切块，代价与收益不成比例 |
| TSan 对定时条件变量等待的误报 | 工具限制，无法在项目内消除 |

### 4.5 两条「延后承诺无人回收」的教训

记录里曾有两处写「留待某阶段一并处置」，而**那个阶段收口时无人回收**：

| 出处 | 处置 |
|:--|:--|
| 「`-o` 留待阶段三一并处置」 | 阶段三后**决定不实现**，状态改为「接受的限制」 |
| 「日志目录名超长静默截断留待批次三一并看待」 | 已由阶段三的日志重写顺带消除（`m_dir_name` 改为 `std::string`），**但无任何记录记下这次关闭**，事后补记 |

> **教训**：阶段收口时应把「指向本阶段的延后项」列出来**逐条销账**，否则**延后等于遗忘**。

## 五、可继续演进的方向

按「收益 / 成本」排序，都是从当前状态出发最自然的一步：

| 方向 | 说明 | 成本 |
|:--|:--|:--|
| **补 `parse_form_body` 的单测** | 无状态纯函数，提取即可测 | 低 |
| **CI 加 `-Werror`** | 告警已清零，条件已具备（需先在 CI 上跑通若干次确认无新增告警） | 低 |
| **CI 加格式检查** | 需先固定 `clang-format` 版本，否则跨版本会产生误报 | 低 |
| **CI 加 Sanitizer 独立 workflow** | 耗时较长，适合定期执行而非每次推送 | 低 |
| **支持 `Transfer-Encoding: chunked`** | 需改动请求体的界定方式（目前完全依赖 `Content-Length`） | 中 |
| **大体积上传单独构造用例** | 覆盖接近体积上限的分支 | 低 |
| **静态资源改用 `sendfile`** | 比 `mmap` + `writev` 更少的用户态参与，但会改变已测通的发送路径 | 中 |
| **分离压测客户端与服务端** | 消除「同机竞争」这一最大的方法学缺陷 | 中（需两台机器） |
| **会话机制** | 让上传与列表可加鉴权 | 高 |
