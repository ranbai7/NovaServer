## 一、术语表

### 1.1 服务器与网络基础

| 术语 | 含义 |
|:--|:--|
| **socket** | 网络通信端点；在程序里用文件描述符表示 |
| **文件描述符（fd）** | 进程访问内核对象的整数编号；关闭后会被内核复用 |
| **监听 fd / 连接 fd** | 前者负责 `accept`，后者代表一条已建立的客户端连接 |
| **TCP** | 提供可靠、有序字节流的传输层协议；不提供消息边界 |
| **HTTP** | 跑在 TCP 上的文本协议，规定请求与响应的格式 |
| **请求行 / 状态行** | 请求或响应的第一行：方法、路径、版本，或版本、状态码、原因短语 |
| **请求体** | 空行之后的内容；`POST` 表单、上传文件放在这里 |
| **`Content-Length`** | 请求体/响应体的字节长度 |
| **`Content-Type`** | 正文的媒体类型，如 `text/html`、`image/png` |
| **长连接** | 一个 TCP 连接上依次处理多个 HTTP 请求；HTTP/1.1 默认如此 |
| **管线化** | 客户端在收到前一个响应之前就发送下一个请求 |
| **半关闭** | 对端关闭写端（`EPOLLRDHUP`），本端仍可发送 |
| **multipart/form-data** | 用 boundary 分隔多个 part 的表单编码，用于文件上传 |

### 1.2 并发与事件驱动

| 术语 | 含义 |
|:--|:--|
| **阻塞 / 非阻塞 IO** | 没数据时挂起线程，还是立即返回 `EAGAIN` |
| **epoll** | Linux 的事件通知机制：内核代管一批 fd，只返回已就绪的那些 |
| **LT / ET** | 水平触发（持续通知）与边沿触发（只在状态变化时通知） |
| **事件循环（EventLoop）** | 反复「等事件 → 分发 → 处理」的循环 |
| **Reactor** | 事件分发器 + 事件源绑定 + 处理器的服务器结构 |
| **主 Reactor / 主循环** | 主线程的 `EventLoop`，默认只负责 `accept`；`-t 0` 时也处理全部连接 |
| **子 Reactor / 子循环** | 子线程的 `EventLoop`，处理已建立连接的读写 |
| **连接归属** | 一个连接的 fd、协议状态、超时定时器全部只属于一个线程 |
| **one loop per thread** | 每个线程一个事件循环，连接归属唯一线程 |
| **`EPOLLONESHOT`** | 一次性关注：通知一次后自动失效，需重新注册 |
| **`timerfd`** | 把「定时到点」变成 fd 可读事件 |
| **`eventfd`** | 一个 fd + 8 字节计数器，用于跨线程唤醒 |
| **`signalfd`** | 把进程信号变成 fd 可读事件 |
| **信号掩码** | 线程属性，决定哪些信号被阻塞；子线程继承创建时的掩码 |
| **异步信号安全** | 信号处理函数中允许调用的函数集合，白名单很短 |
| **`mmap` / `munmap`** | 把文件映射进进程地址空间 / 解除映射 |
| **`writev`** | 一次系统调用写出多段不连续的数据（`iovec` 数组） |
| **零拷贝发送** | 静态文件正文不经过应用层用户态缓冲，直接从映射区写入 socket 发送缓冲区 |

## 二、参数速查

```bash
./build/server [-p port] [-l LOGWrite] [-m TRIGMode] [-o OPT_LINGER] \
               [-s sql_num] [-t thread_num] [-c close_log] [-f config_file]
```

| 参数 | 含义 | 默认 | 取值 |
|:--|:--|--:|:--|
| `-p` | 监听端口 | 9006 | 1~65535 |
| `-l` | 日志写入方式 | 1 | 0 = 同步（每行落盘），1 = 异步（批量落盘） |
| `-m` | 触发模式组合 | 0 | 0 = LT+LT，1 = LT+ET，2 = ET+LT，3 = ET+ET |
| `-o` | 优雅关闭连接 | 0 | **有意不产生效果**，见下 |
| `-s` | 数据库连接池大小 | 8 | ≥ 1 |
| `-t` | 子 Reactor 线程数 | 8 | ≥ 0（**0 = 不建子线程，全归主循环**，用于对照） |
| `-c` | 关闭日志 | 0 | 0 = 打开，1 = 关闭 |
| `-f` | 配置文件路径 | `./config.ini` | 显式指定却找不到文件时**终止启动** |

**命令行优先于配置文件**，两者可混用。未识别的键会终止启动。

### 配置文件（`config.ini`，模板见 `config.example.ini`）

| 节 | 键 |
|:--|:--|
| `[server]` | `port`、`trig_mode`、`opt_linger`、`thread_num`、`close_log`、`root_dir` |
| `[database]` | `host`、`port`、`user`、`password`、`database`、`pool_size` |
| `[log]` | `write_mode`、`dir`、`file`、`buf_size`、`split_lines`、`batch_buf_size`、`flush_interval` |

日志各项的取值范围见 [README](../../README.md) 的「日志配置」一节；越界在启动阶段直接报错，而不是静默夹取。

### `-o` 为什么有意不产生效果

`-o`（`opt_linger`）当前施加在**监听描述符**上，本就无效果。把它挪到连接描述符上会让它生效——而 `SO_LINGER { l_onoff = 1, l_linger = 0 }` 在连接描述符上的语义是「`close` 时发送 **RST** 而非 FIN，并丢弃未发送的数据」，对 Web 服务端是**有害**的：会截断响应、破坏长连接。

因此**有意保持它无效果**，并在配置示例与 README 中写明理由。保留该参数是为**兼容既有命令行接口**。

> 这是「**区分『没做』与『决定不做』**」的一个实例：状态被**决定**才算闭环，被**遗忘**则不是。

## 四、改造起点的问题清单

项目启动时整理过 28 项问题，按性质分五类。这里保留完整分类，作为理解后续各项改造的背景；具体如何解决散见于各册。

### 4.1 并发与生命周期（7 项）

| # | 问题 | 后果 |
|--:|:--|:--|
| 1 | **触发模式未按配置生效** | 注册 fd 时读取的成员尚未赋值，实际始终按 LT 注册 |
| 2 | **定时器链表缺少线程约束** | 主线程遍历链表与工作线程修改链表之间没有同步 |
| 3 | **资源释放路径重叠** | 连接关闭与定时器回调均释放同一 fd，且无幂等保护 |
| 4 | **超时回调持有裸指针** | 定时器指向静态数组元素，缺少对象失效后的安全丢弃机制 |
| 5 | **读写路径存在忙等** | 主线程轮询标志位等待工作线程，占 CPU 且无可见性保证 |
| 6 | **描述符耗尽无兜底** | ET 下 `accept` 因 `EMFILE` 失败后不会再触发 |
| 7 | **连接对象预分配** | 按最大连接数静态分配连接数组，每个携带固定缓冲区 |

### 4.2 正确性与健壮性（11 项）

日志缓冲区越界写、`recv` 返回值漏判、成员未初始化、共享用户表读写同步不对称、**静态资源路径未规范化**、**数据库查询字符串拼接**、**口令明文存储**、参数解析依赖固定偏移、错误响应状态码不匹配、**固定读缓冲区**、配置硬编码。

> 加粗的三项属于安全问题，详见 [11](11-安全加固.md)。

### 4.3 协议实现（3 项）

- **URL 未解码**——`%XX` 序列按字面处理，含转义字符或非 ASCII 的路径无法正确匹配
- **未支持 HEAD 方法**——解析阶段直接判定为错误请求
- **头部长度与 `Content-Length` 缺少校验**——未处理超长头部、非数字或异常取值的长度字段

### 4.4 功能完整性（2 项）

- **上传文件不可访问**——文件写入 `./upload/`，而静态根目录为 `./root/`，上传后无法通过 HTTP 查看
- **上传缺少类型与大小约束**——仅做路径分隔符剥离

### 4.5 代码规范（5 项）

大量 `strcpy`/`strcat`/`sprintf`、头文件里的全局 `using namespace std`、`malloc`/`free` 与 `new`/`delete` 混用、用 `assert` 承担运行时校验（Release 下失效）、只读方法普遍缺少 `const`。

### 4.6 清单之外

清单是「按条目」整理的，但**条目之外的代码从未被系统检查过**。四个阶段收口后，对全部源码做了一次独立审核，又查出 8 处缺陷，其中几条很值得记：

| 缺陷 | 性质 |
|:--|:--|
| **绝对形式 URI 且无路径时空指针解引用** | **一条请求即可打挂单进程服务端** |
| 管线化请求被静默丢弃 | 一个 TCP 段内的多个完整请求只处理第一个 |
| 登录与注册从未取过连接池连接 | 直接把空 `MYSQL*` 交给 `mysql_stmt_init`，**直接段错误** |

> **清单能保证列出的都做完，但不能保证该列的都列了。** 阶段收口后补一次不限于清单的全项目审核，价值不在于查出多少，而在于覆盖清单永远覆盖不到的地方。

### 4.7 被保留的设计

改造并非推倒重来。以下设计经过验证后保留下来，并在新的并发结构里继续使用：

| 保留项 | 理由 |
|:--|:--|
| **三状态机解析结构**（请求行 → 头部 → 内容） | 结构正确，与并发模型无关 |
| **`mmap` + `writev` 发送** | 静态资源省去应用层拷贝，是发送路径里最有效的部分 |
| **路由改写**（`/2` `/3` 把 `m_url` 改成跳转页面） | 结构可用，只在参数解析上加固 |
| **连接池的 RAII 借用/归还** | 设计合理，保留接口 |
| **日志单例 + 同步/异步两种模式** | 语义保留，实现重写（见 [06](06-日志系统.md)） |
| **命令行参数接口**（`-p -l -m -o -s -t -c`） | 保持接口兼容，降低使用者的迁移成本 |
| **空闲超时 15 秒** | 沿用取值使超时行为与改造前一致，便于对比 |

### 5.2 值得优先处理的四项

| 1 | **`http_conn` 的请求行/头部状态机与表单解析仍无单测** | URL 解码与路径规范化已由 `url_codec` 覆盖（10 个用例）。成本最低的下一步是把 `parse_form_body` 提取为独立单元——它是无状态纯函数 |

### 5.3 一批结构清理项（不影响正确性）

全项目审核（`033`）列出了一批死代码与结构问题，至今未处理：

- `lock/locker.h` 中未使用的成员（`cond`、`sem` 的隐式拷贝赋值）
- `GetFreeConn()`、`LogConfig::close_log`、`Channel::m_revents`、`TcpConnection::fd()/peer()` 等**未被调用的接口**
- `http_conn.cpp` 职责混杂（解析、路由、上传、数据库访问、HTML 生成同处一文件）

**它们被如实记入清单，而不是存在于「没写就等于没有」的状态。**

### 5.4 「接受的限制」里的典型例子

| 项 | 为什么接受 |
|:--|:--|
| `-o` 不实现 | 让 `l_linger = 0` 的 RST 语义真正生效对 Web 服务端有害 |
| 符号链接未处理 | 站点根目录下无符号链接，上传目录不在根内 |
| 静态资源无扩展名限制 | 对静态站点属预期行为 |
| 上传与列表无鉴权 | 项目无会话机制 |
| 扩展名白名单基于名称而非内容 | 因一律按附件下载，风险边界可接受 |
| 口令强度未校验 / 无失败频次限制 / 无修改重置流程 | 属功能边界 |
| 客户端与服务端同机 | 测量环境固有 |
| 崩溃时最多丢一个 `flush_interval` 的日志 | 批量落盘的固有代价 |
| `split_lines` 由精确上限变为软上限 | 精确上限需按行切块，代价与收益不成比例 |
| TSan 对定时条件变量等待的误报 | 工具限制，无法在项目内消除 |

### 5.5 两条「延后承诺无人回收」的教训

记录里曾有两处写「留待某阶段一并处置」，而**那个阶段收口时无人回收**：

| 出处 | 处置 |
|:--|:--|
| 「`-o` 留待阶段三一并处置」 | 阶段三后**决定不实现**，状态改为「接受的限制」 |
| 「日志目录名超长静默截断留待批次三一并看待」 | 已由阶段三的日志重写顺带消除，**但无任何记录记下这次关闭**，事后补记 |

> **教训**：阶段收口时应把「指向本阶段的延后项」列出来**逐条销账**，否则**延后等于遗忘**。

## 六、可继续演进的方向

按「收益 / 成本」排序，都是从当前状态出发最自然的一步：

| 方向 | 说明 | 成本 |
|:--|:--|:--|
| **补 `parse_form_body` 的单测** | 无状态纯函数，提取即可测 | 低 |
| **CI 加 `-Werror`** | 告警已清零，条件已具备 | 低 |
| **CI 加格式检查** | 需先固定 `clang-format` 版本 | 低 |
| **CI 加 Sanitizer 独立 workflow** | 耗时较长，适合定期执行 | 低 |
| **支持 `Transfer-Encoding: chunked`** | 需改动请求体的界定方式 | 中 |
| **大体积上传单独构造用例** | 覆盖接近体积上限的分支 | 低 |
| **静态资源改用 `sendfile`** | 比 `mmap` + `writev` 更少的用户态参与，但会改变已测通的发送路径 | 中 |
| **分离压测客户端与服务端** | 消除「同机竞争」这一最大的方法学缺陷 | 中（需两台机器） |
| **会话机制** | 让上传与列表可加鉴权 | 高 |
