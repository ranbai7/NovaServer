# 04 · 注册与登录：MySQL 如何在服务器里工作

> **本章讲什么**：用户在注册页填写用户名和口令，按下提交之后，这些字符如何穿过浏览器、HTTP、服务器进程，最终变成 MySQL 里的一行记录；登录时又如何被查出来并校验。顺带讲清两个服务器开发中的基础件：**表单解析**与**数据库连接池**。
>
> **读完能回答**：
>
> - 浏览器提交表单时，实际发给服务器的字节长什么样？
> - 服务器如何从 HTTP 请求体里取出 `user` 和 `password`？
> - 为什么不给每个请求新建一条 MySQL 连接？连接池如何借用与归还？
> - 口令为什么不能明文存？加了盐的哈希如何校验？
> - 为什么 SQL 要用「参数化查询」而不是拼接字符串？
>
> **对应源码**：`http/http_conn.cpp` 的 `parse_form_body`、`register_user`、`lookup_user`、`do_request`；`CGImysql/sql_connection_pool.{h,cpp}`；`auth/password_hash.{h,cpp}`
> **前置知识**：[01](01-看懂一个Web服务器.md) 的 HTTP 报文与 fd；[03](03-静态资源服务.md) 的请求读取与路由。

## 速览

1. 注册页和登录页是普通 HTML 表单，提交后浏览器发 `POST` 请求，请求体是 `user=...&password=...` 这种 `application/x-www-form-urlencoded` 格式。
2. 服务器按 `Content-Length` 读完请求体，用通用键值解析取出字段，不再依赖「用户名在第几个字节」这种固定位置。
3. 处理注册/登录前，从**数据库连接池**借一条已经建立好的 MySQL 连接，离开作用域自动归还。
4. 注册：锁内查重 → 计算加盐哈希 → 用参数化 SQL 写入 → 同步更新进程内用户表。
5. 登录：先查进程内用户表，再用 PBKDF2 校验哈希；成功与失败分别把请求路径改写为欢迎页或错误页。
6. 这条路径上做过三类改造：明文口令改加盐哈希并自动迁移、SQL 拼接改参数化、固定偏移解析改通用键值解析。

## 一、用户看到的注册与登录

### 1.1 页面与表单

访问 `/0` 得到注册页，核心 HTML 是：

```html
<form action="3CGISQL.cgi" method="post">
    <input type="text"     name="user"     placeholder="请输入用户名" required>
    <input type="password" name="password" placeholder="请输入密码" required>
    <button type="submit">注册</button>
</form>
```

登录页 `/1` 结构相同，只是 `action` 是 `2CGISQL.cgi`。

`action` 里的 `3` 和 `2` 是本项目沿用的路由约定：对于 `POST` 请求，服务器只检查路径最后一个 `/` 后面的第一个字符，`3` 表示注册、`2` 表示登录。所以 `POST /3CGISQL.cgi`、`POST /3`、`POST /3anything` 都会进入注册分支。

### 1.2 浏览器实际发送的请求

表单没有指定 `enctype`，浏览器使用默认的 `application/x-www-form-urlencoded`。假设输入用户名 `alice`、口令 `123456`，请求大致是：

```http
POST /3CGISQL.cgi HTTP/1.1
Host: 127.0.0.1:9006
Content-Type: application/x-www-form-urlencoded
Content-Length: 25
Connection: keep-alive

user=alice&password=123456
```

请求体的规则很简单：

- 字段之间用 `&` 分隔；
- 键和值之间用第一个 `=` 分隔；
- 空格常被编码成 `+`，特殊字符编码成 `%XX`。

登录只是把路径换成 `/2CGISQL.cgi`，请求体结构完全一样。

## 二、服务器如何读到表单字段

### 2.1 头部解析：记录请求体长度

`parse_headers()` 逐行读取头部，遇到这些字段会特别处理：

| 头部 | 处理 |
|:--|:--|
| `Host` | 必须存在；HTTP/1.1 的要求，缺失回 `400` |
| `Connection: close` | 关闭长连接 |
| `Content-Length` | 严格解析为十进制数字；重复、非数字、超上限都拒绝 |
| `Content-Type: multipart/form-data` | 标记为文件上传，并提取 `boundary` |
| `Expect: 100-continue` | 在确定要收请求体时回 `100 Continue` |

头部结束（遇到空行）时，如果 `Content-Length != 0`，说明还有请求体：

```cpp
m_body_start = m_checked_idx;       // 记录请求体起点
m_check_state = CHECK_STATE_CONTENT;
return NO_REQUEST;                  // 等请求体到齐
```

### 2.2 内容阶段：等请求体收全

内容阶段不再按行扫描。判断依据是：

```cpp
if (m_read_idx >= m_content_length + m_body_start) {
    m_string = m_read_buf.data() + m_body_start;
    return GET_REQUEST;
}
```

- `m_body_start` 是头部结束时记录的位置；
- `m_content_length` 是头部声明的长度；
- `m_read_idx` 是当前已读到的总长度。

三者满足条件，说明请求体已经完整。这里特意**不用解析游标 `m_checked_idx`** 来推算请求体位置：游标在按行解析头部时会被推到读索引附近，跨多次读取后会漂移，导致「数据早到齐了，却永远判定没收完」。这个缺陷在改成动态缓冲后才暴露，详见 [10](10-协议实现.md)。

### 2.3 通用键值解析

真正取字段的是 `parse_form_body()`：

```cpp
std::map<std::string, std::string> parse_form_body(const char *body, long length)
{
    // 以 & 切字段，以第一个 = 切键值，键和值都做 URL 解码（+ 还原为空格）
}
```

它不假设字段名、顺序、长度，也不依赖固定偏移。拿到的结果放进 `std::map`，调用方按名字取：

```cpp
auto user_it   = params.find("user");
auto passwd_it = params.find("password");
if (user_it == params.end() || passwd_it == params.end() || user_it->second.empty())
    return BAD_REQUEST;
```

**为什么要有这一步改造**：早期实现依赖「用户名从某个固定位置开始、到下一个 `&` 结束」之类的假设。只要表单字段顺序变化、字段名变化，或者用户名里含有编码字符，解析就会错位。改成通用键值解析后，表单结构对服务器透明。

## 三、数据库连接池：为什么不每次新建连接

MySQL 是一个独立运行的数据库服务：服务器程序通过客户端库与它建立 TCP 连接，发送 SQL，取回结果。下面说的「连接」，指的就是这条服务器进程到 MySQL 的会话。

### 3.1 新建一条 MySQL 连接有多贵

一次 `mysql_real_connect` 至少包括：

1. 与 MySQL 服务器建立 TCP 连接；
2. 完成 MySQL 的握手与身份认证；
3. 协商字符集、能力标志等。

如果每次注册/登录都做一遍，请求延迟会明显上升；并发高时，MySQL 还要为大量短连接分配资源。**连接本身是可以复用的**，于是有连接池。

### 3.2 连接池的结构

本项目在启动时一次性建立若干条连接：

```cpp
// connection_pool::init
for (int i = 0; i < MaxConn; i++) {
    MYSQL *con = mysql_init(NULL);
    mysql_real_connect(con, host, user, password, db, port, NULL, 0);
    connList.push_back(con);
    ++m_FreeConn;
}
reserve = sem(m_FreeConn);   // 信号量初值 = 空闲连接数
```

运行期用两个结构管理：

| 结构 | 作用 |
|:--|:--|
| `connList`（`std::list<MYSQL*>`） | 空闲连接队列 |
| `reserve`（信号量） | 计数：还有多少条连接可借 |
| `lock`（互斥量） | 保护队列的并发访问 |

借连接：

```cpp
MYSQL *connection_pool::GetConnection()
{
    reserve.wait();          // 没有空闲连接就阻塞等待
    lock.lock();
    MYSQL *con = connList.front();
    connList.pop_front();
    --m_FreeConn; ++m_CurConn;
    lock.unlock();
    return con;
}
```

归还连接就是把连接放回队尾并 `reserve.post()`。

### 3.3 RAII：借还自动成对

如果每个调用点都手写「借 → 用 → 还」，中间任何一条 `return` 都可能漏掉归还，池里的连接会越来越少，最终所有请求都卡在 `reserve.wait()`。

本项目用 `connectionRAII` 把借还绑定到作用域：

```cpp
class connectionRAII
{
public:
    connectionRAII(MYSQL **con, connection_pool *pool) {
        *con = pool->GetConnection();
        conRAII = *con;
        poolRAII = pool;
    }
    ~connectionRAII() { poolRAII->ReleaseConnection(conRAII); }
};
```

使用方式：

```cpp
MYSQL *mysql = nullptr;
connectionRAII mysqlcon(&mysql, m_connPool);
// 这里使用 mysql；函数返回或提前 return 时，析构函数自动归还
```

这正是 RAII（资源获取即初始化）的典型用法：**把「释放」交给对象的生命周期，而不是交给每一处控制流**。

## 四、注册：从表单到一行记录

注册分支的核心在 `do_request()`：

```cpp
connectionRAII mysqlcon(&mysql, m_connPool);
if (mysql == nullptr) return INTERNAL_ERROR;

const std::map<std::string, std::string> params =
    parse_form_body(m_string, m_content_length);
// 取出 name 与 password

if (*(p + 1) == '3') {
    switch (register_user(name, password, mysql)) {
    case RegisterResult::kInserted:  strcpy(m_url, "/log.html"); break;
    case RegisterResult::kDuplicate: strcpy(m_url, "/registerError.html"); break;
    case RegisterResult::kFailed:    strcpy(m_url, "/registerError.html"); break;
    }
}
```

`register_user()` 做四件事：

```cpp
RegisterResult register_user(name, password, conn)
{
    g_users_lock.lock();                       // ① 整个序列在锁内
    if (g_users.find(name) != g_users.end()) { // ② 查重
        g_users_lock.unlock();
        return kDuplicate;
    }

    const std::string encoded = password_hash::encode(password);  // ③ 加盐哈希
    const bool inserted = execute_two_params(
        conn, "INSERT INTO user(username, passwd) VALUES(?, ?)", name, encoded);

    if (inserted) g_users[name] = encoded;     // ④ 同步进程内用户表
    g_users_lock.unlock();
    return inserted ? kInserted : kFailed;
}
```

### 4.1 为什么「查重 → 写库 → 更新内存」要放在同一把锁里

如果查重和插入之间释放锁，两个线程可能同时查到「不存在」，然后都去插入，产生重复用户；同时进程内用户表也会出现两次更新。

把整段序列放在锁内，判重与插入之间**不存在竞态窗口**。代价是注册期间持锁时间稍长，但注册是低频操作，可以接受。

### 4.2 进程内用户表是什么

`g_users` 是 `std::map<std::string, std::string>`，保存「用户名 → 口令哈希」。启动时从 MySQL 一次性加载：

```cpp
// http_conn::initmysql_result
SELECT username, passwd FROM user
```

登录时只查内存表，不访问数据库。代价是**多进程部署时内存表不会自动同步**；本项目是单进程服务器，因此可以接受。

> 当前代码在进入登录/注册分支前会统一从连接池借一条连接，但登录分支实际并未使用它，离开作用域后自动归还。这是一处可以省掉的开销，不影响正确性。

### 4.3 加盐哈希

`password_hash::encode()` 生成：

```text
pbkdf2_sha256$100000$<base64 盐>$<base64 散列>
```

| 参数 | 取值 | 作用 |
|:--|:--|:--|
| 算法 | PBKDF2-HMAC-SHA256 | 专为口令设计的慢哈希 |
| 迭代次数 | 100000 | 提高离线穷举成本 |
| 盐 | 每条 16 字节随机数 | 相同口令在库中也会得到不同散列 |
| 输出长度 | 32 字节 | SHA-256 的输出长度 |

**迭代次数写在记录里**，而不是只写死在代码常量中。这样将来提高安全参数时，旧记录仍按各自的次数校验，不需要重算全表。

## 五、登录：查表与校验

登录分支：

```cpp
std::string stored_passwd;
if (lookup_user(name, stored_passwd) &&
    password_hash::verify(password, stored_passwd))
    strcpy(m_url, "/welcome.html");
else
    strcpy(m_url, "/logError.html");
```

`lookup_user()` 在锁内查 `g_users`；`verify()` 重新按记录里的参数计算哈希，并用**定长比较**判断：

```cpp
return CRYPTO_memcmp(expected.data(), key.data(), expected.size()) == 0;
```

普通 `memcmp` 遇到第一个不同字节就返回，比较耗时与「前缀匹配了多少」有关；定长比较的耗时固定，不泄漏前缀信息。

两个容易忽略的规则：

- **不是本模块格式的存储值一律返回 false**：例如数据库里仍然是明文 `123456`，`verify("123456", "123456")` 必须为假；
- **迭代次数要有上界**：防止一条被篡改的记录（例如写成一亿次）让登录陷入长时间计算。

### 5.1 为什么登录成功不是 302 跳转

服务器把 `m_url` 改写成 `/welcome.html`，然后继续走静态文件映射与发送流程。浏览器收到的是一条 `200 OK` 的页面响应，而不是 `302 Location`。

这是本项目沿用的既有结构，好处是实现简单、复用静态发送路径；代价是**地址栏不会变成 `/welcome.html`**，刷新时浏览器会重新提交登录表单。理解这一点即可，不必把它当成「标准做法」。

## 六、这条路径上做过的改造

### 6.1 明文口令 → 加盐哈希

**问题**：早期实现把口令原样写进数据库，登录时直接字符串比较。数据库一旦泄露，所有口令立即可用；即使用户复用口令，影响会扩散到其他系统。

**做法**：

1. 注册时计算 PBKDF2 哈希再入库；
2. 登录时按记录中的参数重新计算并定长比较；
3. 启动时扫描用户表，把仍是明文的记录逐条升级为哈希；
4. 旧表 `passwd` 列是 `char(50)`，装不下哈希串，启动时先查列宽，不足则 `ALTER TABLE ... MODIFY passwd VARCHAR(255)`。

**结果**（80 条明文记录实测）：

| 项 | 结果 |
|:--|:--|
| 列定义 | `char(50)` → `varchar(255)` |
| 明文行数 | **80 → 0** |
| 迁移耗时 | 4.15 s（约 52 ms/行） |
| 二次启动 | 不重复升级，幂等 |
| 原明文口令登录 | 正常 |
| 错误口令 | 被拒 |

### 6.2 拼接 SQL → 参数化查询

**问题**：早期把用户名和口令直接拼进 SQL 文本：

```sql
SELECT passwd FROM user WHERE username = 'alice'
```

如果用户名输入 `' OR '1'='1`，语义就被改变了（SQL 注入）。

**做法**：使用 MySQL 预处理语句：

```cpp
MYSQL_STMT *stmt = mysql_stmt_init(conn);
mysql_stmt_prepare(stmt, "INSERT INTO user(username, passwd) VALUES(?, ?)", ...);
StringBinder binder(2);
binder.set(0, name);
binder.set(1, encoded);
mysql_stmt_bind_param(stmt, binder.data());
mysql_stmt_execute(stmt);
```

参数只作为数据传递，不参与 SQL 语法解析。`StringBinder` 把绑定数组和长度变量放在同一对象里，避免 `MYSQL_BIND::length` 指向临时变量形成悬垂指针。

### 6.3 固定偏移 → 通用键值解析

**问题**：早期解析表单时依赖字段在请求体中的固定位置，字段顺序或形式一变就解析错位，且无法正确处理 URL 编码的用户名/口令。

**做法**：`parse_form_body()` 按 `&` 与 `=` 切分，对键和值分别做 URL 解码，结果放进 `map` 按名字取。

**结果**：字段顺序、字段名、值中包含编码字符都不再影响解析；缺失字段回 `400`。

### 6.4 从未取连接池连接

**问题**：早期登录/注册代码直接使用成员 `mysql`，但从未给它赋过连接池借出的连接，它恒为空指针，`mysql_stmt_init(nullptr)` 会直接段错误。

**做法**：在处理分支内用 `connectionRAII` 明确借连接；借不到（池为空）时返回 `INTERNAL_ERROR`，而不是把空指针交给后面的查询。

**结果**：注册登录在 ASan 全链路与冒烟测试中稳定通过。

## 七、验证方式

```bash
# 启动服务端后，先注册
curl -i -X POST http://127.0.0.1:9006/3CGISQL.cgi \
     -H "Content-Type: application/x-www-form-urlencoded" \
     --data 'user=alice&password=123456'

# 用正确口令登录
curl -i -X POST http://127.0.0.1:9006/2CGISQL.cgi \
     -H "Content-Type: application/x-www-form-urlencoded" \
     --data 'user=alice&password=123456'

# 用错误口令登录
curl -i -X POST http://127.0.0.1:9006/2CGISQL.cgi \
     -H "Content-Type: application/x-www-form-urlencoded" \
     --data 'user=alice&password=wrong'

# 查看数据库中的存储形式（应为 pbkdf2_sha256$...）
mysql -e "SELECT username, passwd FROM yourdb.user;"
```

预期：注册成功返回登录页；正确口令返回欢迎页；错误口令返回登录错误页；数据库中看不到明文口令。

## 八、关键接口与字段

| 接口 / 字段 | 位置 | 作用 | 设计要点 |
|:--|:--|:--|:--|
| `parse_form_body()` | `http_conn.cpp` | 解析 `application/x-www-form-urlencoded` | 按键值解析，不依赖字段顺序；键值都做 URL 解码 |
| `register_user()` | `http_conn.cpp` | 注册 | 锁内完成查重、写库、更新内存 |
| `lookup_user()` | `http_conn.cpp` | 查进程内用户表 | 读侧也加锁，避免与写侧不对称 |
| `password_hash::encode()` | `password_hash.cpp` | 生成加盐哈希 | 每条随机盐；参数写入记录 |
| `password_hash::verify()` | `password_hash.cpp` | 校验口令 | 参数取自记录且有上界；定长比较；非本格式一律 false |
| `connectionRAII` | `sql_connection_pool.cpp` | 借还连接的作用域守卫 | 构造借、析构还 |
| `GetConnection()` | `sql_connection_pool.cpp` | 从池中取连接 | 信号量等待 + 锁内取队首；取空时归还信号量 |
| `g_users` / `g_users_lock` | `http_conn.cpp` | 进程内用户表 | 读写都经加锁封装 |
| `m_connPool` | `http_conn` | 连接池指针 | 不拥有连接池，生命周期覆盖所有请求 |

## 九、通用知识

**HTTP 表单**

- **`application/x-www-form-urlencoded`**：`key=value&key2=value2`；键值需要 URL 解码，`+` 表示空格
- **`Content-Length` 决定请求体边界**：服务器必须按长度读，不能假设「一次 read 就是一条表单」
- **`multipart/form-data`** 是另一种表单编码，用于文件上传（见 [05](05-文件上传与下载.md)）

**数据库**

- **连接池解决的是连接建立成本**：TCP + 认证 + 会话初始化，复用比每次新建便宜得多
- **信号量 + 队列**是连接池的经典组合：信号量控制数量，队列保存连接
- **RAII 管理借还**：把归还绑定到作用域，避免提前 `return` 泄漏连接
- **参数化查询**：SQL 文本与数据分开传输，数据永远不参与语法解析
- **预处理语句中的指针成员**：`MYSQL_BIND::length` 是 `unsigned long*`，必须指向生命周期足够长的变量

**口令存储**

- **不要明文存口令**，也不要只用一次普通哈希：普通哈希太快，离线穷举可行
- **每条记录独立加盐**：防止相同口令产生相同散列
- **参数随记录存储**：为将来提高迭代次数留出兼容空间
- **定长比较**：避免比较耗时泄漏前缀信息
- **迁移要幂等**：启动时检查、升级、再次启动不重复处理
