# 10 · 性能度量

> **本章讲什么**：怎么证明「优化生效了」。这件事的难点不在压测工具，而在**可比性**——同一份代码在不同时段测量可以差 27%，跨时段搬数字做对比是不成立的。
>
> **对应文件**：`docs/performance.md`、`test_pressure/`、`test_pressure/results/`
> **对应记录**：`docs/changes/000`、`013`、`021`、`027`、`029`、`030`、`031`、`034`

---

## 速览

1. **优化开始前的第一件事是测量，而不是改代码**。没有基线，任何优化都只能凭感觉说「变快了」。
2. **四项指标在动手前就定死**：默认 QPS（期望提升）、P99 延迟（期望显著下降）、常驻内存（期望明显下降）、线程数对吞吐的影响（期望出现正相关）。**指标先定，结论才可检验。**
3. **三类对比的可信度完全不同**：**只有「同时段 A/B」能做定量结论**；跨日分段对比含 ±10%~27% 的时段差异，只能作方向性参考；单次测量只回答问题「某项改动是否导致退化」。
4. **同时段 A/B 的做法**：把优化前的代码用 `git worktree` 重建，与当前代码在**同一时段**背靠背测量。
5. **最终结果**：QPS **19808 → 33151（+67%）**，P99 **899.99 ms → 16.79 ms**，常驻内存 **262.8 MB → 12.6 MB（−95%）**；实测最优点 `-m 0 -t 2` 为 **48185 QPS，约为优化前基线的 2.4 倍**。
6. **代价必须一起讲**：`-t 1` 在两次独立测量中都回退（−15% / −12.4%），原因是新架构为每个连接维护独立的定时器与事件源。**这是明确的取舍，不是缺陷。**
7. **有一处至今没有定论**：`-t 8` 的 P99 反而高于旧架构；还有一处只有推测、未经验证（P50 的反常）。

## 一、背景知识速查

| 指标 | 含义 | 为什么看它 |
|:--|:--|:--|
| **QPS** | 每秒完成的请求数 | 吞吐能力 |
| **P50（中位延迟）** | 一半请求的延迟低于它 | 典型用户体验 |
| **P99（尾部延迟）** | 99% 的请求延迟低于它 | **服务端最该关注的指标**——平均值会掩盖「1% 的请求慢到不可用」 |
| **RSS** | 常驻内存（Resident Set Size） | 内存占用，与并发上限直接相关 |
| **噪声** | 同配置重复测量之间的波动 | 决定「多大的差异才算差异」 |

**为什么尾部延迟比平均值重要**：一个服务若 99% 的请求 1 ms、1% 的请求 1 秒，平均只有 11 ms，看起来很好——但对那 1% 的用户来说服务是坏的。而且尾部延迟往往来自**排队**，一旦出现，负载稍高就会迅速恶化。

---

## 二、S · 背景：没有基线

改造开始前，项目**没有任何性能数据**。这意味着：

- 任何优化都无法证明有效
- 任何「重构之后更快」的说法都只是感觉
- 更危险的是：**重构可能让某些场景变慢，而没人会发现**

> 阶段零在整份记录里被评价为「**性价比最高的一步**」——它花掉的时间远少于后面任何一次重构，却让后面所有结论都变得可检验。

---

## 三、T · 目标：先定指标，再动手

在改动任何代码之前，**把后续对比要用的四项指标提前定死**：

| 指标 | 基线值 | 期望方向 |
|:--|--:|:--|
| 默认配置 QPS | 19808 | 提升 |
| P99 延迟 | 899.99 ms | 显著下降 |
| 常驻内存 | 262.8 MB | 明显下降 |
| 线程数对吞吐的影响 | 无差异（1.3% 以内） | 出现可观测的正相关 |

第四项最特别——它不是「越大越好」的指标，而是一个**结构性的判据**：如果主线程只 `accept`、子线程处理连接的设计真的生效，那么增加子线程数**应该**带来吞吐提升。**当时测出来是「无差异」，这本身就是原架构的病灶之一。**

同时明确记录了这个测量环境的局限（见 §六）——**这条自我限定在后续所有对比中都被沿用**。

## 四、A · 做法

### 4.1 测量环境与工具

| 项 | 值 |
|:--|:--|
| 主机 | Ubuntu 22.04 虚拟机（VMware），Intel Core i5-13500H，**4 vCPU（2 物理核 + 超线程）/ 3.8 GiB** |
| 编译 | `-O2 -DNDEBUG`（CMake `Release`） |
| 工具 | `wrk` 4.1.0，`-t2 -c100 -d5s`，**每组 5 次取中位数** |
| 目标 | `http://127.0.0.1:9006/judge.html`（静态资源路径） |

**为什么编译选项要固定**：CMake 的 Release 默认是 `-O3`，而基线以 `-O2` 采集。不显式固定的话，**后续所有性能对比都会混入优化级别的差异**（见 [09](09-工程基础.md) §3.1）。

### 4.2 三类对比，三种可信度

这是本章最核心的一张表：

| 形式 | 做法 | 能得出什么结论 |
|:--|:--|:--|
| **① 同时段 A/B** | 把优化前的代码用 `git worktree` 重建，与当前代码**在同一时段背靠背测量** | **唯一能做定量结论的形式** |
| **② 跨日分段对比** | 不同日期采集的两份数据 | 含约 **±10%~27%** 的时段差异，**只能作方向性参考** |
| **③ 单次测量** | 只测一次 | 只能回答「某项改动是否导致退化」，结论限定在该次测量内 |

**②的 ±10%~27% 不是估计值，是实测值**——同一份代码跨日测量可以差 **27%**。这个数字本身就说明了为什么「拿上个月的数字和这个月的数字比」不成立。

**同时段 A/B 的具体做法**：用 `git worktree` 把旧代码重建出来，编译出二进制（记录大小用于核对，如 `031`/`034` 的旧二进制均为 **173136 字节**），两个服务端交替启停、背靠背测量。

**还有一条容易混用的注意点**：`030`（日志改造）的「改动前」是**新架构 + 旧日志**，隔离出的是**日志改造单独的收益**；而 `034` 的 B 组「旧」是**旧架构 + 旧日志**，其差值同时含架构重构与日志重写两项。**两者不可混用。**

### 4.3 验收测试的分层

性能之外，功能与正确性走一套分层验收（`test_pressure/results/acceptance_2026-10-02/`）：

| 层 | 内容 |
|:--|:--|
| L1–L2 | 构建与单元测试 |
| L3 | 功能冒烟（`test_pressure/smoke.sh`） |
| L4 | 回归（管线化、路径穿越、上传闭环等） |
| L5 | 协议（URL 转义、HEAD、`Content-Length`、半关闭） |
| L6 | 资源（描述符耗尽兜底、空闲回收） |
| L7 | AddressSanitizer 全链路 |
| L8 | 压测 |
| L9 | 清理与收尾 |

**分层的价值在于「每层拦下不同种类的问题」**，而且原始输出全部入库，任何数字都能回溯到当时的终端记录。

## 六、对结果的评价

**这部分比数字本身更重要**——把「达成的」「付了代价的」「还没搞清的」分开说。

### 6.1 达成的

1. **吞吐**：默认配置 +67%；最优点 `-m 0 -t 2` 达 48185 QPS，约为基线的 **2.4 倍**
2. **尾部延迟**：P99 从接近 1 秒降到十几毫秒——**这是最显著的一项**。原架构在 `-t 8` 下 P99 长期在 800~1200 ms，说明存在严重的排队/尾延迟问题
3. **内存**：−95%，且**「与负载无关的固定占用」这一特征被消除**（这比数值下降更重要）
4. **架构可扩展性**：线程数从「对吞吐无影响」变为「有明确影响」
5. **日志路径**：异步写入提升约 4 倍

### 6.2 代价

| 项 | 表现 | 解释 |
|:--|:--|:--|
| **`-t 1` 回退** | 两次独立测量均回退（`031` −15%，`034` −12.4%） | 新架构为**每个连接**维护独立的定时器与事件源，单线程时开销高于旧的半同步模型。**这是明确的取舍，不是缺陷**——默认的 `-t 2` 才是新架构的最优点 |
| **`-m 3 -t 8` 仅 +2.0%** | 落在噪声内 | **不能计入收益** |
| **`-t 8` 的 P99 反而更高** | 9.57 → 16.79 ms | 旧架构 `-t 8` 时 `-t` **实际未生效**（所有连接走同一路径），其 P99 不可与新架构的同名配置直接类比。**此项尚无定论** |

### 6.3 尚未解释的一处（如实记录为推测）

`000` 的 **P50（0.323 ms）反而优于 `021` 的 3.690 ms**——与 P99 的改善方向**相反**。

一个**可能的**原因是 `013` 把每请求从预分配缓冲改为按需 `mmap` / `munmap`，降低了内存却增加了中位延迟（空间换时间）。

> **这只是推测，尚未验证**，记录中明确标注「不应作为结论使用」。**把它写下来而不是略过，是因为「已知未解释的现象」本身就是有价值的信息。**

## 七、测量局限与后续建议

1. **客户端与服务端同机**是本环境最大的方法学缺陷：`wrk` 与服务端争夺同一组 CPU 核心，**吞吐上限可能由客户端而非服务端决定**。因此**上表的绝对 QPS 不具备横向参考价值**，其价值在于同环境的前后对比。
2. **4 vCPU（2 物理核 + 超线程）** 决定了「`-t 2` 最优」这一结论有很强的**环境成分**，换硬件后结论会变。
3. **低成本的改进方向**：用 `taskset` 把 `wrk` 与服务端绑到不同核心，可部分消除同机竞争；再进一步则需要在两台机器上分离客户端与服务端。
4. 若将来在云主机复测，应以**相同脚本**重跑 `021` 与当前版本，形成独立闭环的同时段 A/B，**而不是把本文的绝对值搬过去比较**。

**还有一条来自记录的自我纠错**：README 中曾有一张 `-t` 对照表（29825 / 27868 / 50270 / 37705），在仓库中**找不到任何出处**——它与 `027`、`029`、`034` 三份记录的数值均不符，其中 `-t 1` 的 27868 在任何文档中都没有对应测量。该表已改用 `034` 中带原始输出的数值。

> **「数值必须有出处」是这套方法的一部分**：一个无法回溯到测量记录的漂亮数字，比一个难看的真实数字更有害。

## 八、通用知识

**性能方法论**

- **先建基线再优化**：没有基线，一切「变快了」都不可检验
- **指标要在动手前定死**：否则容易在事后挑对自己有利的指标
- **同时段 A/B 是唯一可靠的对照形式**：同一份代码跨时段可差 27%
- **用 `git worktree` 重建旧版本**做背靠背对比
- **区分「隔离单项改动」与「累计效果」**：不同实验组的「改动前」可能不是同一个东西，不可混用
- **优化必须连同代价一起讲**，且代价要能解释成因

**指标与解读**

- **P99 比平均值更能反映服务端问题**；尾延迟往往来自排队
- **RSS vs VSZ**；「固定占用」与「随负载变化的占用」是两种性质
- **噪声的量化**：±10% 是这套环境的噪声水平，比它小的差异不能下结论
- **测量环境要连同局限一起记录**：同机、核数、工具线程数都会限制结论的适用范围

**工程纪律**

- **每个数字都要有出处**：能回溯到原始输出
- **已知未解释的现象要如实记录**，并标注「推测，未验证」
- **把绝对值与相对对照分开对待**：绝对值不可跨环境搬运，相对对照可以
