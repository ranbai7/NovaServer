# 03 · 静态资源服务：浏览器如何看到页面

> **本章讲什么**：用户在浏览器里打开首页、点开图片或视频时，服务器如何把 `root/` 目录下的文件找出来、组织成 HTTP 响应并发送回去。这是本项目最基础的功能，也是理解后续优化（零拷贝、动态缓冲、长连接）的入口。
>
> **读完能回答**：
>
> - 一个静态文件从磁盘到浏览器，中间经过哪些步骤？
> - `mmap` 是什么？为什么说它避免了「把文件读进内存」？
> - `writev` 为什么能一次发出「响应头 + 文件正文」？
> - 路径里的 `..` 和 `%2e%2e` 为什么必须被拦住？
>
> **对应源码**：`http/http_conn.cpp` 的 `parse_request_line`、`do_request`、`process_write`、`write`；`http/url_codec.h`；`net/tcp_connection.cpp`
> **前置知识**：[01](01-看懂一个Web服务器.md) 的 fd、HTTP 报文、事件循环。

---

## 速览

1. 浏览器发来 `GET /judge.html`，服务器先把它**解码、规范化**，再拼成 `root/judge.html`。
2. 用 `stat` 检查文件是否存在、是否可读、是不是目录；然后用 `open` + `mmap` 把文件映射进内存。
3. 响应头写进 `m_write_buf`，文件正文留在映射区；两者用 `writev` 一次发出，正文不经过用户态拷贝。
4. 如果一次没发完（发送缓冲区满），连接转去关注「可写」，下次接着发。
5. 发送完成后 `munmap` 释放映射，`reset()` 复位状态，同一条连接可以继续处理下一个请求。
6. 这条路径上有几处关键加固：路径穿越拦截、`404` 分支、正确的状态码、`Content-Type`、默认长连接、动态读缓冲。

## 一、用户看到的一个页面

打开 `http://127.0.0.1:9006/` 时，浏览器实际发出的是：

```http
GET / HTTP/1.1
Host: 127.0.0.1:9006
Accept: text/html
```

服务器把 `/` 当作站点首页，返回 `root/judge.html`。浏览器解析 HTML 之后，又会为页面里的图片、CSS 发起新的请求，例如：

```http
GET /judge.png HTTP/1.1
GET /favicon.ico HTTP/1.1
```

**这些请求走的是同一条代码路径**：不管是 `.html`、`.png` 还是 `.mp4`，服务器只负责找到文件、声明类型、把字节发出去。文件内容是什么，服务器并不关心。

## 二、从连接 fd 到协议对象

### 2.1 事件来了

前面讲过，子线程的 `epoll_wait` 发现某个连接 fd 可读，会调用这个 fd 对应的读回调：

```cpp
// net/tcp_connection.cpp
void TcpConnection::handle_read()
{
    if (!m_conn.read_once()) { close(); return; }
    refresh_idle_timer();
    if (!m_conn.process()) close();
}
```

连接层只做三件事：读、刷新空闲定时器、交给协议层处理。它不知道读到的字节是 HTTP 还是别的协议。

### 2.2 读入缓冲区

`http_conn::read_once()` 把内核接收缓冲区里的字节读进 `m_read_buf`：

```cpp
bytes_read = recv(m_sockfd, m_read_buf.data() + m_read_idx,
                  m_read_buf.size() - m_read_idx, 0);
```

这里有几个细节：

- **返回值先判断再累加**：`recv` 返回负数时直接加进 `m_read_idx` 会破坏缓冲区状态。
- **`EAGAIN` 不是错误**：非阻塞 fd 上暂时没有数据，连接仍然有效。
- **返回 0 表示对端关闭**：客户端发完请求后关闭写端，服务器读完剩余数据后要把已收到的请求处理完。
- **缓冲区可能不够**：读满后按两倍扩容，直到 `MAX_REQUEST_SIZE`（8 MiB）。扩容会让缓冲区地址变化，指向缓冲区内部的指针必须同步重定位（见 [10](10-协议实现.md)）。

### 2.3 解析请求行

`process_read()` 先把字节按 `\r\n` 切成一行一行，第一条就是请求行：

```http
GET /judge.html HTTP/1.1
```

`parse_request_line()` 从中取出三样东西：

| 字段 | 例子 | 后续用途 |
|:--|:--|:--|
| 方法 | `GET` | 决定是否需要请求体、是否只发头部 |
| URL | `/judge.html` | 映射到站点根目录下的文件 |
| 版本 | `HTTP/1.1` | 本服务端只接受 1.1 |

然后对 URL 做两步处理，**顺序不能颠倒**：

```cpp
// 1. 解码：把 %2e%2e%2f 还原成 ../
const std::string decoded = url_codec::decode(m_url, false);
if (decoded.find('\0') != std::string::npos) return BAD_REQUEST;

// 2. 规范化：消掉 . 和 ..，并拒绝越出根目录的路径
const std::string normalized = url_codec::normalize_path(m_url);
if (normalized.empty()) return BAD_REQUEST;
```

为什么必须先解码、再规范化？看一个具体输入：

```text
%2e%2e%2fetc%2fpasswd
```

- 先规范化：此时字符串里还没有 `..`，会被当成普通文件名放行；
- 再解码：它变成了 `../etc/passwd`——校验已经做完了。

所以「只加解码、不做规范化」或「先规范化、后解码」都会**新增一条绕过路径**。第 [11](11-安全加固.md) 册会把这条作为安全案例再讲一次。

`normalize_path` 是纯函数：输入一个字符串，输出规范化后的路径；不依赖连接状态，因此可以直接写单元测试（`tests/test_url_codec.cpp`，10 个用例）。

## 三、路由：URL 变成磁盘路径

### 3.1 特殊路径

`do_request()` 先处理几个固定的页面别名：

| URL | 文件 |
|:--|:--|
| `/` 或 `/judge.html` | `root/judge.html` |
| `/0` | `root/register.html` |
| `/1` | `root/log.html` |
| `/5` / `/6` / `/7` / `/8` | `root/picture.html` / `video.html` / `fans.html` / `upload.html` |

这些别名让页面之间的链接更短，也方便替换实际页面文件。

登录、注册和上传还会先把 `m_url` 改写成某个页面路径，再走同一套静态映射逻辑（见 [04](04-注册与登录.md)、[05](05-文件上传与下载.md)）。

### 3.2 普通静态路径

其他路径直接拼到站点根目录后面：

```cpp
bool http_conn::set_real_file(const char *relative_path)
{
    const int written = snprintf(m_real_file, sizeof(m_real_file),
                                 "%s%s", doc_root, relative_path);
    return written > 0 && written < static_cast<int>(sizeof(m_real_file));
}
```

`doc_root` 是启动时用 `realpath()` 解析出的**绝对路径**，例如 `/home/user/NovaServer/root`。因此 `/judge.png` 会变成：

```text
/home/user/NovaServer/root/judge.png
```

`m_real_file` 只有 200 字节。**装不下就判为错误请求**，而不是截断后继续用——截断后的路径已经不是用户请求的那个文件了。

### 3.3 文件检查

拼出路径后，依次检查：

```cpp
if (stat(m_real_file, &m_file_stat) < 0)        return NO_RESOURCE;      // 不存在 → 404
if (!(m_file_stat.st_mode & S_IROTH))           return FORBIDDEN_REQUEST; // 其他用户可读位未置位 → 403
if (S_ISDIR(m_file_stat.st_mode))               return BAD_REQUEST;      // 目录不直接返回 → 400
```

`stat` 把文件的信息（大小、权限、类型）填进 `m_file_stat`，后面组织响应时要用到文件大小。

**空文件单独处理**：长度为 0 的 `mmap` 会失败，所以大小为 0 时不建立映射；`process_write` 对空文件返回一个固定的空页面 `<html><body></body></html>`，而不是零字节正文。

## 四、把文件映射进内存：`mmap`

### 4.1 不用 `mmap` 会怎样

最直接的做法是：

```cpp
std::vector<char> buf(size);
read(file_fd, buf.data(), size);   // 文件内容拷进用户态内存
write(conn_fd, buf.data(), size);  // 再拷进内核发送缓冲区
```

问题是：文件有多大，就要先分配多大的用户态内存，还要多一次「内核 → 用户 → 内核」的拷贝。一个 100 MB 的视频会给每个正在下载它的连接都带来 100 MB 的常驻内存。

### 4.2 `mmap` 的做法

```cpp
m_file_address = (char *)mmap(nullptr, m_file_stat.st_size,
                              PROT_READ, MAP_PRIVATE, file_fd, 0);
close(file_fd);
```

`mmap` 把文件的一段映射到进程地址空间。之后：

- 访问 `m_file_address[i]` 就像访问内存；
- 实际上由内核在缺页时从磁盘加载，不需要应用程序先 `read` 一整份；
- 多个连接读同一个文件时，物理内存中的文件页可以共享。

**映射失败要置空**，否则后面的 `munmap` 或 `writev` 会作用在无效地址上：

```cpp
if (m_file_address == MAP_FAILED) {
    m_file_address = nullptr;
    return INTERNAL_ERROR;
}
```

### 4.3 什么时候解除映射

响应发完、连接关闭、或者 `reset()` 复用时都要 `munmap`：

```cpp
void http_conn::unmap()
{
    if (m_file_address) {
        munmap(m_file_address, m_file_stat.st_size);
        m_file_address = 0;
    }
}
```

这里有一个真实踩过的坑：`reset()` 的第一步就是 `unmap()`，而连接对象可能复用了上一份堆内存。如果构造函数没有把 `m_file_address` 初始化为空，`reset()` 会读到**上一个连接残留的地址**，去 `munmap` 一块不属于自己的映射，破坏堆。完整定位过程见 [07](07-并发模型重构.md) §十二。

## 五、组装响应

### 5.1 响应头

`process_write(FILE_REQUEST)` 负责写响应头：

```http
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Content-Length: 12345
Connection: keep-alive

```

| 头部 | 作用 | 本项目的实现 |
|:--|:--|:--|
| `Content-Type` | 告诉浏览器正文是什么 | 按扩展名查表（`get_mime_type`） |
| `Content-Length` | 正文有多少字节 | 静态文件取 `stat.st_size` |
| `Connection` | 是否复用连接 | HTTP/1.1 默认 `keep-alive`，请求显式 `close` 才关闭 |

`Content-Type` 很重要：没有它，浏览器只能猜。本项目对 `.html`、`.css`、`.js`、常见图片/视频、`.json`、`.txt` 等都给出了明确类型；未知类型回退为 `application/octet-stream`（二进制下载）。

### 5.2 两段数据：头在内存，正文在映射区

响应由两部分组成，它们在内存里并不相邻：

```text
m_write_buf:  [ HTTP/1.1 200 OK\r\n ... \r\n\r\n ]      ← 响应头
m_file_address: [ 文件正文 ... ]                         ← mmap 映射
```

如果分两次 `write`，就是两次系统调用；如果先把文件读进用户态拼成一块，又会有一次大拷贝。`writev` 提供了第三种选择：**一次系统调用，写出多段不连续的数据**。

```cpp
m_iv[0].iov_base = m_write_buf.data();
m_iv[0].iov_len  = m_write_idx;
m_iv[1].iov_base = m_file_address;
m_iv[1].iov_len  = m_file_stat.st_size;
m_iv_count = 2;

writev(m_sockfd, m_iv, m_iv_count);
```

`iovec` 是一个「地址 + 长度」的描述结构，`writev` 按顺序把它们写出去。内核从映射区读取数据并写入 socket 的发送缓冲区，**正文不需要先经过应用层的用户态缓冲**；常说的「零拷贝发送」在这里指的是省掉这一次用户态拷贝，而不是完全没有内核拷贝。

### 5.3 没发完怎么办

`writev` 不保证一次把 `bytes_to_send` 全部写完。内核发送缓冲区满了，它会返回已写出的字节数。此时：

1. 累加 `bytes_have_send`，扣减 `bytes_to_send`；
2. 协议层调用 `m_want_write()`，连接层把 fd 改成关注可写；
3. 下一次 `EPOLLOUT` 事件到来时继续 `writev`；
4. 发完后再切回关注可读，等待下一个请求。

```cpp
if (bytes_to_send <= 0) {
    unmap();
    m_want_read();
    if (m_linger) { reset(); return true; }  // 长连接：等下一个请求
    return false;                            // 短连接：交给连接层关闭
}
```

推进 `iovec` 时有一个容易写错的地方：**必须先判断响应头是否已经发完**，再决定是推进 `iov[0]` 还是把 `iov[1]` 指向文件正文的剩余部分。HEAD 响应只有一段（`iov_count = 1`），如果无条件去操作 `iov[1]`，就会在从未设置过的指针上做运算。

## 六、连接复用：`reset()` 做了什么

一个长连接处理完一个请求后，不能直接把对象销毁，而要复位到「可以处理下一个请求」的状态：

| 复位项 | 原因 |
|:--|:--|
| `unmap()` | 释放上一个请求的文件映射 |
| 保留读缓冲里剩余的字节 | 可能是下一个请求（HTTP 管线化） |
| 清空解析游标、状态机 | 从请求行重新开始 |
| `m_linger = true` | HTTP/1.1 默认保持连接 |
| 清空上传状态 | 避免上一个请求的 boundary/文件名残留 |
| 必要时缩容缓冲区 | 防止一次大请求之后长期占着大块内存 |

读缓冲的缩容有一个前提：**里面没有压着下一个请求的字节**。如果有，缩容会丢掉它们：

```cpp
// 只有没有剩余字节时才缩容
if (0 == leftover && m_read_buf.capacity() > READ_BUFFER_SIZE * 4)
    std::vector<char>().swap(m_read_buf);
```

## 七、这条路径上做过的改造

下面几项都是本项目在静态资源路径上做过、且能从行为或数据上看到结果的改动。每一项都按「问题 → 做法 → 结果」说明。

### 7.1 路径穿越

**问题**：直接把 URL 拼到根目录后面，`GET /../etc/passwd` 或 `GET /%2e%2e%2fetc%2fpasswd` 可以读到站点目录之外的文件。

**做法**：先 URL 解码，再规范化路径，任何试图越过根目录的路径直接拒绝；解码结果含 `\0` 也拒绝（防止 C 字符串截断）。

**结果**：`../` 与 `%2e%2e%2f` 两种形式均被拒绝，`url_codec_tests` 的 10 个用例覆盖了编码绕过组合。

### 7.2 错误响应不完整

**问题**：文件不存在时没有 `404` 分支，控制流落到 `default` 后直接关闭连接，客户端收不到任何响应；其他错误响应的状态码与语义也不匹配。

**做法**：补齐 `404`、`400`、`403`、`500`、`413`、`415`、`417`、`431`、`501` 等分支，并给错误正文统一加 `Content-Type`。

**结果**：错误请求都能得到一条可读的 HTTP 响应，而不是连接被静默关闭。

### 7.3 固定缓冲区

**问题**：读缓冲固定 2 KB，写缓冲固定 1 KB；请求稍大就关闭连接，而且每个连接无论用不用都要占着这两块内存。

**做法**：改成 `std::vector<char>` 按需扩容，读缓冲上限 8 MiB、响应上限 64 KiB；扩容时重定位内部指针；请求超限返回 `413` 而不是直接断开。

**结果**：20 KB 请求体可正常处理，9 MB 请求体得到 `413`；该次记录中常驻内存从 264 MB 降到 76 MB（后续基线复测为 60.0 MB；剩余部分由连接对象按需化继续降到 12.6 MB，见 [09](09-生命周期与资源管理.md)）。

### 7.4 长连接

**问题**：最初只有请求显式带 `Connection: keep-alive` 才保持连接，而 `curl`、`wrk` 等多数客户端默认不发这个头，导致每个请求都重新建连。

**做法**：按 HTTP/1.1 语义改为默认保持连接，只有显式 `Connection: close` 才关闭。

**结果**：普通客户端可以复用连接；压测时的建连开销显著下降。

### 7.5 发送路径的边界

**问题**：HEAD 响应只有一段 `iovec`，但推进逻辑会去访问从未设置的 `iov[1]`，构成指针运算越界。

**做法**：先判断「是否已发完」，再区分「响应头是否发完」，只在确有剩余数据时推进指针。

**结果**：HEAD 在全部触发模式下通过；发送路径的边界用例纳入回归测试。

## 八、验证方式

```bash
# 启动服务端（仓库根目录）
./build/server

# 查看完整响应头
curl -v http://127.0.0.1:9006/

# 请求一张图片，确认 Content-Type
curl -I http://127.0.0.1:9006/judge.png

# 不存在的文件，确认 404
curl -i http://127.0.0.1:9006/not-exist.html

# 路径穿越，确认被拒绝
curl -i --path-as-is http://127.0.0.1:9006/../etc/passwd
curl -i --path-as-is http://127.0.0.1:9006/%2e%2e%2fetc%2fpasswd

# 只发头部
curl -I http://127.0.0.1:9006/judge.html
```

预期：首页返回 `200` 与 `text/html`；图片返回 `image/png`；不存在的文件返回 `404`；两种穿越形式都被拒绝。

## 九、关键接口与字段

| 接口 / 字段 | 位置 | 作用 | 设计要点 |
|:--|:--|:--|:--|
| `parse_request_line()` | `http_conn.cpp` | 解析方法、URL、版本 | 绝对 URI 剥协议后必须检查 `/`，否则空指针解引用 |

## 十、通用知识

**文件与 IO**

- **`stat` 能拿到什么**：文件大小、权限位、类型（普通文件/目录/符号链接）；判断「能不能返回」至少要查存在性、可读性、是否目录
- **`mmap` 的适用场景**：只读、大文件、多连接共享同一文件时收益明显；小文件未必比 `read` 更快
- **`munmap` 必须与 `mmap` 的大小一致**；映射地址不能重复释放
- **`writev` 的 iovec 语义**：按数组顺序写出；部分写回后要正确推进尚未写完的那一段

**HTTP**

- **`Content-Type` 与 `Content-Length` 是响应正确性的基础**：前者决定浏览器如何解释正文，后者决定读到哪算结束
- **HEAD 与 GET 的响应头应一致**，只是不发正文
- **HTTP/1.1 默认长连接**；`Connection: close` 才显式关闭
- **错误响应也要有完整的状态行、头部与正文**，不能只关闭连接

**安全**

- **路径穿越的两种形式**：明文 `../` 与编码后的 `%2e%2e%2f`；解码与规范化的顺序决定防线是否成立
- **解码结果含 `\0` 要拒绝**：后续按 C 字符串处理时会被提前截断
- **路径拼接后要检查长度**：截断后的路径可能指向另一个文件
