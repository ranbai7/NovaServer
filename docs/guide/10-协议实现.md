## 速览

1. **三状态机解析**：请求行 → 头部 → 内容。行由「从状态机」`parse_line()` 切出，切不出完整行就返回 `LINE_OPEN` 等下次读事件——**解析状态因此保存在连接对象里**，必须随连接归属同一线程。
2. **路径处理有一条不可颠倒的顺序：先解码、再规范化。** 先规范化后解码会让 `%2e%2e%2f` 绕过全部路径校验。
3. **状态码语义被补齐**：区分 `501`（规范定义但未实现的方法）与 `400`（无法识别的记号），补齐 `404` / `413` / `415` / `431` / `417`。
4. **缓冲区从固定改为动态**，随之暴露并修正了三个**只在跨多次读取时才成立**的解析缺陷。
5. **请求体用 `m_body_start` 定界，且内容阶段不再按行扫描**——用游标 `m_checked_idx` 推算请求体位置会在跨读时漂移。
6. **发送路径省去了应用层拷贝**：静态文件 `mmap` 到地址空间，`writev` 一次写出「响应头 + 文件正文」两段，正文不经过应用层缓冲区。
7. **`mmap` + `writev` 这个设计被完整保留**，是本项目发送路径的核心。

## 一、协议解析器在解决什么问题

### 1.1 TCP 不提供消息边界

浏览器发送的 HTTP 请求在 TCP 看来只是一串字节。一次 `read` 可能得到：

```text
情况 A：GET /judge.html HTTP/1.1\r\nHost: ...\r\n\r\n        ← 完整请求
情况 B：GET /judge.html HTTP/1.1\r\nHo                      ← 只有半行
情况 C：GET /a HTTP/1.1\r\n...\r\n\r\nGET /b HTTP/1.1...    ← 两个请求
```

服务器必须自己维护一个**读缓冲区**，把字节累积起来，按协议规则判断「哪里是一条完整请求的结束」。

### 1.2 状态机的思路

HTTP 请求的结构是固定的：

```text
请求行\r\n
头部行 1\r\n
头部行 2\r\n
...
\r\n
请求体（长度由 Content-Length 决定）
```

于是解析器可以分成三个状态，逐段推进：

```text
CHECK_STATE_REQUESTLINE  → 解析请求行
CHECK_STATE_HEADER       → 逐行解析头部，直到空行
CHECK_STATE_CONTENT      → 按长度收请求体
```

每解析完一段，就把状态推进到下一段；数据不够时，**保留当前状态**，等下一次读事件。

这个「当前解析到哪」的状态必须存在连接对象里，而连接对象归属某个线程——这就是为什么协议状态也必须遵守 [07](07-并发模型重构.md) 的连接归属约定。

## 二、从状态机：切出一行

### 2.1 `parse_line`

`parse_line()` 从 `m_checked_idx` 开始扫描，找 `\r\n`：

```cpp
for (; m_checked_idx < m_read_idx; ++m_checked_idx) {
    if (temp == '\r') {
        if ((m_checked_idx + 1) == m_read_idx)
            return LINE_OPEN;          // 只有 \r，\n 还没到
        else if (m_read_buf[m_checked_idx + 1] == '\n') {
            m_read_buf[m_checked_idx++] = '\0';   // 就地改写
            m_read_buf[m_checked_idx++] = '\0';
            return LINE_OK;
        }
        return LINE_BAD;
    }
    ...
}
return LINE_OPEN;
```

三种返回：

| 返回 | 含义 | 调用方动作 |
|:--|:--|:--|
| `LINE_OK` | 找到完整一行 | 交给主状态机解析 |
| `LINE_OPEN` | 行还没收完 | 等下一次读事件 |
| `LINE_BAD` | 行格式非法 | 返回 `400` |

### 2.2 就地改写 `\r\n` 的后果

找到一行后，代码把 `\r\n` 改成 `\0\0`，这样该行就可以直接当 C 字符串处理。

这个做法有一个重要后果：**缓冲区被改写后，无法重新切分出原来的行**。所以「解析出错就清空状态、从头重解析」这条路走不通。后面的动态缓冲方案必须考虑这一点。

### 2.3 主状态机

```cpp
switch (m_check_state) {
case CHECK_STATE_REQUESTLINE:
    ret = parse_request_line(text);
    if (ret != NO_REQUEST) return ret;   // 一旦有结果就是最终结果
    break;
case CHECK_STATE_HEADER:
    ret = parse_headers(text);
    if (ret == GET_REQUEST) return do_request();
    ...
case CHECK_STATE_CONTENT:
    ret = parse_content(text);
    if (ret == GET_REQUEST) return do_request();
    ...
}
```

一个容易写错的地方：请求行的结果**一旦非 `NO_REQUEST` 就是最终结果**，必须立即返回。

```cpp
if (ret != NO_REQUEST) return ret;
```

只判 `BAD_REQUEST` 是不够的：像 `501 METHOD_NOT_IMPLEMENTED` 这样的取值会被当作「还没解析完」，于是**下一行（例如 `Host` 头）会被当成请求行继续解析**。

## 三、路径处理：顺序不可颠倒

这是本章最需要记住的一条。

```cpp
// 解码必须在规范化之前：%2e%2e%2f 解码后才是 '..'
const std::string decoded = url_codec::decode(m_url, false);

// %00 解码后是字符串结束符，会让后续按 C 字符串处理的逻辑提前截断
if (decoded.find('\0') != std::string::npos) return BAD_REQUEST;

m_url = overwrite_url(m_url, decoded);          // 就地写回（只会变短）

const std::string normalized = url_codec::normalize_path(m_url);
if (normalized.empty()) return BAD_REQUEST;     // 试图越过根目录
m_url = overwrite_url(m_url, normalized);
```

**为什么顺序如此**：`normalize_path` 靠识别 `..` 段来拒绝越界。如果先规范化再解码，那么 `%2e%2e%2f` 这一串在规范化时**还不是** `../`，会被当作普通文件名放行；**解码之后它才变成 `../`**——此时校验已经做完了。结果就是「只加解码、不做规范化」等于**新增了一条绕过途径**。

两个函数都在 [`http/url_codec.h`](../../http/url_codec.h) 里，是**纯字符串变换**（不依赖连接状态与全局配置），因此被提取到头文件中直接单测——路径规范化是安全边界，仅靠端到端测试难以覆盖「编码后被绕过」的输入组合，必须有 10 个用例的单元测试逐项钉住。

另外两处细节：

- `decode` 只对路径做 `%XX` 还原，**不把 `+` 还原为空格**（那是表单体的约定，路径中的 `+` 是字面量）；
- 非法转义（`%ZZ`、结尾不完整的 `%A`）按字面量保留，而不是报错——这样不会因为一个畸形序列就把正常路径判为非法。

## 四、头部校验与状态码语义

### 4.1 头部校验

每一项都对应一个真实缺陷：

| 检查 | 处理 | 为什么 |
|:--|:--|:--|
| 头部长度 | 超过 `MAX_HEADER_SIZE`（8 KB）→ **431** | 此前没有上限 |
| `Host` 缺失 | → **400** | HTTP/1.1 要求请求必须携带 `Host` |
| `Content-Length` 重复 | → **400** | 长度有两种解释，是请求走私的常见手法 |
| `Content-Length` 非十进制数字 | → **400** | `atol` 会把 `"abc"` 静默当作 `0`、把 `"12abc"` 当作 `12` |
| `Content-Length` 超上限 | → **413** | 长度本身就超了，无需再传输请求体 |
| `Expect` 非 `100-continue` | → **417** | 其余期望值本服务端无法满足 |

### 4.2 状态码语义

`is_known_method()` 区分两类情况：

- **规范定义了但本服务端未实现的方法**（`PUT`/`DELETE`/`TRACE`/`OPTIONS`/`CONNECT`/`PATCH`）→ **501**，并带 `Allow` 头；
- **根本无法识别的请求记号**（例如 `FOO`）→ **400**。

这两者此前都被当成错误请求处理，语义不准确。错误响应现在也统一补上 `Content-Type`，避免客户端自行猜测。

## 五、动态缓冲与指针重定位

### 5.1 为什么改动态缓冲

最初的读缓冲固定 2 KB、写缓冲固定 1 KB。请求稍大就直接关闭连接。改成 `std::vector<char>` 按需扩容后：

- 读缓冲上限 `MAX_REQUEST_SIZE`（8 MiB）；
- 写缓冲上限 `MAX_RESPONSE_SIZE`（64 KiB）；
- 超限返回 `413`，而不是断开连接。

### 5.2 扩容带来的指针问题

协议对象里有很多指针指向读缓冲区内部：

```cpp
char *m_url;
char *m_version;
char *m_host;
char *m_string;
```

`std::vector` 扩容时可能重新分配内存，**旧地址全部失效**。因此扩容函数必须按同样的偏移量重新指向：

```cpp
void http_conn::grow_read_buffer(size_t size)
{
    const char *old_data = m_read_buf.data();
    m_read_buf.resize(size);

    const ptrdiff_t delta = m_read_buf.data() - old_data;
    if (delta == 0) return;

    if (m_url != nullptr)     m_url += delta;
    if (m_version != nullptr) m_version += delta;
    if (m_host != nullptr)    m_host += delta;
    if (m_string != nullptr)  m_string += delta;
}
```

必要性有 ASan 对照：**临时去掉重定位**后，4 KB 跨读请求体在 AddressSanitizer 下立刻报 `heap-use-after-free`，定位到 `do_request` 中读取已失效的 `m_url`。

### 5.3 动态缓冲暴露的三个解析缺陷

这三个缺陷原本被固定尺寸掩盖，它们的共同点是**只在请求跨越多次读取时才成立**：

| 缺陷 | 现象 | 修法 |
|:--|:--|:--|
| **请求体起点随读取漂移** | `m_checked_idx` 被 `parse_line` 一路推到读索引处，用它推算的「请求体是否收完」基准随每次读取增长。实测 20 KB 请求体到第 5 轮数据已全到齐，判定基准却涨到 36417 → **请求永远无法完成**，连接挂到超时 | 新增 `m_body_start`，在头部解析完时记录一次；内容阶段**不再调用 `parse_line`** |
| **内容阶段补写结束符破坏后续字节** | `text[m_content_length] = '\0'` 写的位置紧随请求体之后，那里可能正是**流水线中下一个请求**的起始字节 | 去掉这行；消费方都带长度读取，不依赖 C 字符串语义 |
| **扩容后指针失效** | `m_url` / `m_version` / `m_host` / `m_string` 都指向读缓冲内部，`vector` 扩容重分配后全部变成悬垂指针 | `grow_read_buffer` 按同一偏移量重新指向 |

**备选方案是「扩容后重置解析状态、从头重解析」**，未采用——因为解析过程会**就地改写**缓冲区（`parse_line` 把 `\r\n` 改成 `\0`），缓冲区已被改动后无法重新切分出原来的行。

### 5.4 超限为什么不返回 `false`

`read_once` 返回 `false` 的既有含义是「连接该结束了」。如果「请求体超限」也走这条路，那么要在那一刻发出 `413`，需要同时改动两条调用路径。

因此本项目把「超限」表达为一种**解析结果**：

```text
m_oversized 置位
  → process_read 返回 REQUEST_TOO_LARGE
  → process_write 回应 413 并强制 Connection: close
```

这样调用方无需区分「读失败」与「请求太大」。

### 5.5 连接复用时归还大缓冲

`reset()` 里若读缓冲容量远大于初始值（> 4 倍）则释放重分配，避免一次大请求之后连接对象长期占着大块内存。但**缓冲里还压着下一个请求的字节时不能缩容**。

## 六、长连接、半关闭与 `Expect`

### 6.1 长连接改为默认

最初的实现只在收到 `Connection: keep-alive` 时才保持连接，于是**不带该头的客户端**（`curl`、`wrk` 等多数实现）每个请求都要重连。

正确语义是：HTTP/1.1 **默认保持连接**，只在显式收到 `Connection: close` 时才关闭。

### 6.2 半关闭

对端关闭写端时，事件通常同时带 `EPOLLIN` 与 `EPOLLRDHUP`。处理顺序必须是「读 → 写 → 关闭」，关闭前还要判断 `has_pending_work()`。详见 [09](09-生命周期与资源管理.md) §4.6。

### 6.3 `Expect: 100-continue`

客户端在发送大请求体前先征求许可。回应时机有讲究——**放在「确定要收这个请求体」的时刻**（头部解析完、`Content-Length` 已校验），而不是解析到 `Expect` 头时立刻发。因为如果长度字段本身已超限（解析 `Content-Length` 时已返回 413），就不该再让客户端开始传数据。

而且 `100 Continue` **不参与写缓冲的组装**：它是一条中间响应，写完即被后续的最终响应覆盖，直接 `send` 即可。

## 七、管线化：一个 TCP 段里的多个请求

### 7.1 读侧：保留剩余字节

一个 TCP 段里可能有多个完整请求。`reset()` 在复位状态时**保留已完整解析后剩下的字节**：

```cpp
const size_t leftover = (m_request_parsed && m_read_idx > m_checked_idx)
                        ? static_cast<size_t>(m_read_idx - m_checked_idx) : 0;
if (leftover > 0 && m_checked_idx > 0)
    memmove(m_read_buf.data(), m_read_buf.data() + m_checked_idx, leftover);
```

`m_request_parsed` 是「本次是否已完整解析出一个请求」的标志：只有置位后，读缓冲里剩余的字节才**属于下一个请求**；没走完时保留会让同一段被反复重解析。

### 7.2 写侧：发完立刻处理下一个

响应发完后立刻检查是否还有待处理的请求：

```cpp
// tcp_connection.cpp  handle_write()
if (m_conn.has_pending_work() && !m_conn.process()) close();
```

否则要等对端再发数据才会动。

## 八、响应的零拷贝发送

### 8.1 两段数据

静态文件的响应由两部分组成：

```text
m_write_buf:     [ HTTP/1.1 200 OK\r\n ... \r\n\r\n ]   ← 响应头（用户态）
m_file_address:  [ 文件正文 ... ]                        ← mmap 映射
```

`writev` 一次系统调用写出两段：

```cpp
m_iv[0].iov_base = m_write_buf.data();
m_iv[0].iov_len  = m_write_idx;
m_iv[1].iov_base = m_file_address;
m_iv[1].iov_len  = m_file_stat.st_size;
writev(m_sockfd, m_iv, 2);
```

正文不需要先经过应用层的用户态缓冲区，这就是「零拷贝发送」在本项目里的实际含义——**省掉了一次用户态拷贝**；内核仍需把数据写入 socket 发送缓冲区。

### 8.2 部分写

`writev` 可能只写出一部分。推进 `iovec` 时有一个容易写错的地方：**必须先判断响应头是否已经发完**，再决定是推进 `iov[0]` 还是让 `iov[1]` 指向文件正文的剩余部分。HEAD 响应只有一段（`iov_count = 1`），如果无条件去操作 `iov[1]`，就会在从未设置过的指针上做运算。

## 九、结果

### 9.1 行为验证

| 用例 | 结果 |
|:--|:--|
| 4 KB 请求体，先送头部、停顿 0.4 s 再送体（跨两次读取，触发扩容） | 正确路由到主面板 |

| 半关闭（发送后立即 `shutdown(SHUT_WR)`） | 4 种触发模式各 **15/15** 成功，正文 md5 与源文件一致 |

| 版本 | 4 KB 跨读请求体在 ASan 下 |
|:--|:--|
| 保留重定位 | 无报告 |
| **临时去掉重定位** | `heap-use-after-free`，定位到 `do_request` 读取已失效的 `m_url` |

|:--|--:|

## 十、关键接口与字段

| 接口 / 字段 | 语义 | 设计要点 |
|:--|:--|:--|
| `parse_line()` | 从状态机，切一行 | 就地改写 `\r\n` 为 `\0\0`；切不出完整行返回 `LINE_OPEN` |
| `process_read()` | 主状态机 | 请求行的结果一旦非 `NO_REQUEST` 必须立即返回 |
| `process_write(ret)` | 按解析结果组装响应 | 每个 `HTTP_CODE` 一个分支；`default` 返回 false 交由上层关闭 |
| `m_check_state` | 当前解析状态 | `REQUESTLINE` / `HEADER` / `CONTENT` |
| `m_body_start` | 请求体起点 | 头部解析完记录一次；**不能**用游标 `m_checked_idx` 推算 |
| `m_request_parsed` | 本次是否已完整解析出一个请求 | 决定 `reset()` 时读缓冲剩余字节的去留（管线化） |
| `m_has_content_length` | 是否已出现过 `Content-Length` | 重复即 400（请求走私） |
| `m_oversized` | 请求体已超上限 | 把「超限」表达为解析结果，而非读失败 |
| `m_expect_continue` | 是否需回应 100 Continue | 在「确定要收请求体」的时刻才回 |
| `m_iv[2]` / `m_iv_count` | `writev` 的两段 | `[0]` 响应头，`[1]` 文件正文；HEAD 时 `count` 为 1 |
| `m_real_file[200]` | 拼好的实际文件路径 | 一次 `snprintf` 完成，装不下即判错误 |

## 十一、通用知识

**HTTP 与协议实现**

- **HTTP/1.1 报文结构**：请求行 / 头部 / 空行 / 请求体；**行以 `\r\n` 结束**（单独 `\n` 按非法处理）
- **HTTP/1.1 默认长连接**，`Connection: close` 才关闭
- **`Host` 头是 HTTP/1.1 的强制要求**
- **`Content-Length` 必须严格解析**：非数字要报错，不能用 `atol` 静默吞掉
- **重复 `Content-Length` 与请求走私**的关系
- **`Expect: 100-continue`** 的用途与回应时机
- **`Transfer-Encoding: chunked`** 本服务端尚未支持（见 [15 · 附录](15-附录.md)）
- **状态码语义边界**：`400`（语法错）vs `501`（未实现）vs `405`（方法不允许）；`413` / `415` / `431` / `417`

**解析器设计**

- **状态机 + 累积缓冲**是处理流式协议的基本结构：状态必须随连接保存
- **「一层没收全」与「格式非法」要区分**：前者等待，后者报错
- **就地改写缓冲区的代价**：无法从头重解析
- **跨越多次读取时，任何「位置」都必须显式记录**，不能从会移动的游标推算

**C++ 系统编程**

- **`std::vector` 扩容导致地址变化**：指向其内部的裸指针/引用会失效，必须重定位
- **`vsnprintf` 的返回值语义**：截断时返回「本该写入的长度」；**重试前必须 `va_copy`**
- **`std::string_view` 避免拷贝**：解析大请求体时只取视图
- **`mmap` + `writev` 零拷贝发送**：`iovec` 描述「头部 + 正文」两段
- **`writev` 部分写**：`EAGAIN` 时转关注可写；推进 `iovec` 前先判「是否已发完」
