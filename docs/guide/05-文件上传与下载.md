# 05 · 文件上传与下载

> **本章讲什么**：用户在页面上选择一个文件、点击上传，浏览器如何把它包装成 HTTP 请求体，服务器如何从这堆字节里找出文件名和内容、校验后写入磁盘，之后又如何通过一个链接把文件取回。这是本项目里**用户向服务器上传文件内容的唯一路径**，也是安全约束最密集的功能。
>
> **读完能回答**：
>
> - `multipart/form-data` 到底长什么样？`boundary` 是干什么的？
> - 文件内容可能分多次到达，服务器如何判断「收全了」？
> - 为什么上传目录和站点根目录要分开？
> - 为什么下载一定要加 `Content-Disposition: attachment`？
> - 扩展名白名单、体积上限、文件名剥离分别防的是什么？
>
> **对应源码**：`http/http_conn.cpp` 的 `parse_headers`、`parse_content`、`do_request`、`parse_multipart_content`、`save_uploaded_file`、`serve_uploaded_file`、`build_upload_list`；`root/upload.html`
> **前置知识**：[04](04-注册与登录.md) 的请求体与表单；[03](03-静态资源服务.md) 的 `mmap` 与响应组装。

## 速览

1. 上传页使用 `<form action="/upload" method="post" enctype="multipart/form-data">`，浏览器把文件内容按 `boundary` 分隔成若干 part。
2. 服务器从 `Content-Type` 里取出 boundary，在第一个 part 的头部里找文件名；**文件名一旦可判定就先校验**：类型不在白名单时立刻返回 `415`，空名或以点开头时返回 `400`，不必等整个文件传完。
3. 请求体收全后，服务器定位文件内容的起点与下一个 boundary，截出内容，再校验一次文件名和体积，写入 `./upload/`。
4. 上传成功后把路径改写为 `/Upload-Success.html`；`GET /upload` 动态生成文件列表；`GET /upload/<名字>` 以附件形式返回文件。
5. 约束有四道：扩展名白名单、单文件 4 MiB 上限、文件名只取最后一段、下载一律 `attachment`；列表页还要做 HTML 转义与 URL 编码。
6. 这条路径原本是「写进去了但取不回来」：文件落在 `./upload/`，而静态根目录是 `./root/`。本项目把上传、列表、下载三件事补齐成闭环。

## 一、用户看到的上传与下载

### 1.1 上传页

`/8` 返回 `root/upload.html`，核心表单是：

```html
<form action="/upload" method="post" enctype="multipart/form-data">
    <input type="file" name="file" required>
    <button type="submit">上传</button>
</form>
```

关键是 `enctype="multipart/form-data"`。普通的 `application/x-www-form-urlencoded` 会把所有字符编码成文本，不适合二进制文件；`multipart/form-data` 则把每个字段/文件当作独立的「部分」（part），用一段随机字符串作为分隔符。

### 1.2 浏览器发出的请求

假设上传 `photo.png`，内容是一小段 PNG 字节。浏览器发出的请求大致是：

```http
POST /upload HTTP/1.1
Host: 127.0.0.1:9006
Content-Type: multipart/form-data; boundary=----WebKitFormBoundary7MA4YWxkTrZu0gW
Content-Length: 12345

------WebKitFormBoundary7MA4YWxkTrZu0gW
Content-Disposition: form-data; name="file"; filename="photo.png"
Content-Type: image/png

<PNG 二进制内容>
------WebKitFormBoundary7MA4YWxkTrZu0gW--
```

拆开看：

| 片段 | 含义 |
|:--|:--|
| `boundary=...` | 分隔符，出现在每个 part 前面，前面加 `--` |
| `Content-Disposition: form-data; name="file"; filename="photo.png"` | 这个 part 的字段名和文件名 |
| 空行 | part 头部结束，后面是内容 |
| `<PNG 二进制内容>` | 文件本身 |
| 最后的 `--boundary--` | 所有 part 结束 |

服务器不需要理解 PNG 格式，只需要找到 boundary、找到 `filename="..."`、截出两个 boundary 之间的字节。

## 二、服务器如何接收上传

### 2.1 头部阶段：识别上传并提取 boundary

`parse_headers()` 遇到 `Content-Type` 时：

```cpp
if (content_type.find("multipart/form-data") != std::string::npos) {
    m_is_file_upload = true;
    size_t pos = content_type.find("boundary=");
    if (pos != std::string::npos) {
        m_boundary = "--";
        m_boundary += content_type.substr(pos + 9);
        // 去掉可能存在的双引号
        if (...) m_boundary = "--" + m_boundary.substr(3, m_boundary.size() - 4);
    }
}
```

注意 `m_boundary` 存的是**带 `--` 前缀**的完整分隔符，后续查找时可以直接用。有些客户端会把 boundary 用双引号括起来，代码也做了兼容。

### 2.2 内容阶段：边收边判文件名

上传文件可能很大，请求体会分成多次 `read` 到达。服务器不可能等全部收完再决定「这个文件类型允不允许」——那样客户端要白传几 MB 才收到 `415`。

因此 `parse_content()` 在请求体还没收全时，就尝试定位第一个 part 的头部：

```cpp
if (m_is_file_upload) {
    const HTTP_CODE verdict = check_upload_name_early();
    if (verdict != NO_REQUEST) return verdict;
}
```

`locate_first_part()` 只做一件事：在已收到的字节里找 boundary、找 `filename="..."`。它有三种结果：

| 结果 | 含义 | 服务器动作 |
|:--|:--|:--|
| 还没找到完整 part 头 | 数据不够 | 继续读 |
| 找到且文件名合格 | 可以继续 | 继续读 |
| 找到且文件名不合格 | 空名、以点开头 → `400`；类型不在白名单 → `415` | 立刻拒绝，并关闭连接 |

「连接必然还有未处理的字节，不能复用」——所以提前拒绝时会把 `m_linger` 置为 `false`，响应发完就关闭。

### 2.3 请求体收全后：解析 multipart

`do_request()` 检测到「`POST` + 上传 + 路径以 `/upload` 开头」，调用 `parse_multipart_content()`：

```cpp
const std::string_view body(m_string, m_content_length);   // 不拷贝整个请求体
const MultipartPart part = locate_first_part(body, m_boundary);

m_file_name = part.filename;

// 文件内容止于下一个 boundary
const size_t marker = body.find(m_boundary, part.content_start);
size_t content_end = marker;
if (content_end >= 2 && body.substr(content_end - 2, 2) == "\r\n")
    content_end -= 2;                                      // 去掉 boundary 前的 CRLF

const std::string_view content =
    body.substr(part.content_start, content_end - part.content_start);
m_file_content.assign(content.data(), content.size());
```

几个设计点：

- **定位阶段用 `string_view`，不先拷贝整个请求体**：请求体上限 8 MiB，若在查找 boundary 前就复制一份，上传期间会多 8 MiB 常驻；`string_view` 只是在原缓冲区上取视图。校验通过后，再把文件内容复制到 `m_file_content` 以便落盘——这一步的拷贝无法避免，但只发生在确定要接收这个文件之后。
- **内容区间是「part 头结束」到「下一个 boundary 前」**；boundary 前面固定有一个 `\r\n`，要去掉。
- **本项目只解析第一个 part，并假定它就是文件 part**（上传页也只有 `file` 一个字段）；不支持多文件或「普通字段 + 文件」混合提交。这是功能边界，不是遗漏。
- **空文件是合法输入**：只要求存在内容分隔，不要求内容非空。

### 2.4 校验、落盘

解析出文件名和内容后，依次校验：

```cpp
// ① 文件名准入（与提前判定共用同一函数，保证两侧结论一致）
const HTTP_CODE name_verdict = check_upload_name(m_file_name);
if (name_verdict != GET_REQUEST) return name_verdict;

// ② 文件体积上限（只能在内容截出来之后判）
if (m_file_content.size() > MAX_UPLOAD_SIZE) return REQUEST_TOO_LARGE;

// ③ 落盘
if (!save_uploaded_file()) return BAD_REQUEST;

// ④ 改写为成功页
strcpy(m_url, "/Upload-Success.html");
```

`save_uploaded_file()`：

```cpp
const std::string upload_dir("./upload");
if (access(upload_dir.c_str(), F_OK) != 0 && mkdir(upload_dir.c_str(), 0755) != 0)
    return false;

if (m_file_name.find('/') != std::string::npos) return false;

const std::string filepath = upload_dir + "/" + m_file_name;
std::ofstream ofs(filepath.c_str(), std::ios::binary);
ofs.write(m_file_content.data(), m_file_content.size());
```

上传目录在第一次上传时按需创建，不需要用户事先建好。

## 三、为什么文件名和体积的校验时机不同

这是本章最值得理解的一处设计。

### 3.1 文件名可以提前判定

part 头部一旦到达，`filename="photo.png"` 就已经完整。此时就能判断扩展名是否在白名单里。**不合格立刻拒绝**，避免客户端把整个 8 MiB 传完才收到错误。

### 3.2 体积不能提前判定

请求头里的 `Content-Length` 是**整个请求体**的长度，其中还包括：

- 每个 part 的头部（`Content-Disposition` 等）；
- boundary 分隔符；
- 可能的其他字段。

所以「请求体没超 8 MiB」**并不等于**「文件没超 4 MiB」。只能在内容截出来之后，用 `m_file_content.size()` 判断。

这就是 `check_upload_name()` 被两处调用的原因：提前判定和落盘前判定共用同一套规则，保证不会出现「前面放过、后面拒绝」的不一致。

## 四、约束与它们防的东西

| 约束 | 取值 / 做法 | 防的是什么 |
|:--|:--|:--|
| **扩展名白名单** | `.jpg .jpeg .png .gif .bmp .webp .mp4 .webm .mp3 .txt .pdf .zip` | 不接受 `.html` / `.svg` / `.js` 等可在浏览器中执行的内容 |
| **单文件体积上限** | 4 MiB（< 请求体上限 8 MiB） | 防止超大文件耗尽磁盘或内存 |
| **文件名只取最后一段** | 丢弃客户端带来的 `/` 或 `\` 之前的部分 | 防止目录穿越（如 `../../etc/passwd`） |
| **落盘前再检查 `/`** | 文件名中不允许出现 `/` | 保证文件只可能落在 `upload/` 内 |
| **下载一律加 `Content-Disposition: attachment`** | 浏览器按附件下载，不就地渲染 | 防止可携带脚本的类型被当作页面执行（存储型 XSS） |
| **列表页 HTML 转义** | `html_escape(filename)` | 文件名里的 `<script>` 不会变成页面结构 |
| **列表链接 URL 编码** | `url_encode_segment(filename)` | 文件名里的空格、`&`、`#` 不会改变链接语义 |
| **响应头取值过滤** | `sanitize_header_value(filename)` | 文件名里的换行、引号不能注入额外响应头 |

### 4.1 白名单和 `attachment` 为什么缺一不可

- 白名单限制**能传什么**；
- `attachment` 限制**取回时怎么用**。

即使白名单里全是图片，某些格式（例如 SVG）仍可能被浏览器当作可执行文档。虽然本项目直接排除了 `.svg`，`attachment` 仍然是第二道保险：**任何上传内容都不在浏览器里就地渲染**。

### 4.2 为什么上传目录不在站点根目录下

站点根目录 `root/` 提供的是**站点自身内容**，访问规则简单；上传目录 `upload/` 的内容来自用户，访问规则不同（一律附件下载、单独列表）。两者分开，避免用户内容混进静态资源路径，也让安全策略可以分别施加。

## 五、列表页与下载

### 5.1 `GET /upload`：动态生成列表

`build_upload_list()` 扫描 `./upload/`：

```cpp
DIR *dir = opendir("./upload");
while (struct dirent *entry = readdir(dir)) {
    if (name.empty() || name[0] == '.') continue;       // 跳过隐藏文件
    if (stat(path, &info) != 0 || !S_ISREG(info.st_mode)) continue;
    files.emplace_back(name, info.st_size);
}
std::sort(files.begin(), files.end());
```

然后拼出一段 HTML：

```html
<li><a href="/upload/photo.png">photo.png</a>（12345 字节）</li>
```

这段 HTML 不写入文件，而是作为**动态响应正文**放在 `m_inline_body` 里，由 `process_write(DYNAMIC_CONTENT)` 组装成 `200` 响应。文件名同时经过：

- `html_escape`：用于显示；
- `url_encode_segment`：用于链接。

目录不存在或不可读时按「暂无文件」处理，而不是 `500`：上传目录是运行期才创建的，服务刚启动时它确实可能不存在。

### 5.2 `GET /upload/<名字>`：返回文件

`serve_uploaded_file()` 的安全检查：

```cpp
if (filename.empty() || filename == "." || filename == ".." ||
    filename.find('/') != std::string::npos)
    return BAD_REQUEST;

const std::string path = "./upload/" + filename;
if (stat(path.c_str(), &m_file_stat) < 0) return NO_RESOURCE;
if (!S_ISREG(m_file_stat.st_mode))        return FORBIDDEN_REQUEST;
```

名称被限定为**单一路径段**，所以只可能落在 `upload/` 内。文件通过 `mmap` 映射，响应组装时额外加：

```http
Content-Disposition: attachment; filename="photo.png"
```

响应头里的文件名经过 `sanitize_header_value()`，控制字符和引号会被替换，防止响应头注入。

## 六、跨多次读取的上传

上传大文件时，请求体不会一次到齐。服务器的状态机需要处理：

```text
第 1 次读：请求行 + 头部到达
          → 记录 m_body_start，进入 CONTENT 状态
          → 尝试定位 part 头，文件名可判定就提前校验
第 2 次读：请求体的一部分到达
          → 还不够 Content-Length，继续关注可读
...
第 N 次读：请求体全部到达
          → m_read_idx >= m_body_start + m_content_length
          → 解析 multipart，截出内容
```

几个容易出错的地方：

- **请求体起点不能漂移**：必须用 `m_body_start`，不能用会被行扫描推走的 `m_checked_idx`（见 [10](10-协议实现.md)）；
- **缓冲区可能扩容**：扩容后 `m_string` 等指向缓冲区的指针要重定位；
- **内容阶段不能按行扫描**：文件是二进制，里面可能没有 `\r\n`，按行找会永远找不到；
- **提前拒绝要关闭连接**：请求体没读完，连接上还有未处理字节，不能复用。

## 七、这条路径上做过的改造

### 7.1 上传后无法访问

**问题**：早期实现把文件写入 `./upload/`，但服务器只从 `./root/` 提供静态资源，上传成功的文件没有任何 URL 能访问到。

**做法**：补全三条路由：

| 请求 | 行为 |
|:--|:--|
| `POST /upload` | 解析并落盘 |
| `GET /upload` | 列出已上传文件 |
| `GET /upload/<名>` | 下载文件 |

**结果**：上传、查看、下载形成闭环；`smoke.sh` 与手工 curl 均可验证。

### 7.2 上传没有任何约束

**问题**：早期只剥离路径分隔符，任何类型、任何大小都能写入。

**做法**：增加扩展名白名单、4 MiB 单文件上限、文件名单段限制、下载 `attachment`、列表转义。

**结果**：`.html` / `.svg` / `.js` 被拒绝；超大文件返回 `413`；恶意文件名不会改变写入目录或注入页面。

### 7.3 拒绝时机太晚

**问题**：如果等请求体全部收完才检查扩展名，客户端要白白上传最多 8 MiB 才会收到 `415`。

**做法**：`parse_content` 在 part 头部完整时提前判定文件名；类型不在白名单即拒绝并关闭连接。

**结果**：非法类型在只发送了很少字节时就被拒绝，节省带宽与处理时间。

### 7.4 固定读缓冲

**问题**：早期读缓冲固定 2 KB，稍大的文件直接无法上传。

**做法**：动态缓冲按需扩容，请求体上限 8 MiB；超限返回 `413` 而不是断开连接。

**结果**：普通图片、短视频、PDF 可以正常上传；超限请求得到明确的 `413`。

## 八、验证方式

```bash
# 准备一个测试文件
printf 'hello upload\n' > /tmp/hello.txt

# 上传
curl -i -F "file=@/tmp/hello.txt" http://127.0.0.1:9006/upload

# 查看列表
curl -s http://127.0.0.1:9006/upload

# 下载并核对内容
curl -OJ http://127.0.0.1:9006/upload/hello.txt
cat hello.txt

# 非法类型：应返回 415
printf '<script>alert(1)</script>' > /tmp/x.html
curl -i -F "file=@/tmp/x.html" http://127.0.0.1:9006/upload

# 超大文件：应返回 413
dd if=/dev/zero of=/tmp/big.bin bs=1M count=9
curl -i -F "file=@/tmp/big.bin;filename=big.zip" http://127.0.0.1:9006/upload
```

预期：合法文本上传成功并可原样下载；`.html` 被 `415` 拒绝；9 MiB 文件被 `413` 拒绝；`upload/` 目录只出现允许类型的文件。

## 十、通用知识

**multipart 与文件上传**

- **`multipart/form-data` 的核心是 boundary**：它把请求体分隔成多个 part，每个 part 有自己的头部和内容
- **文件内容是二进制**，不能按行或按 C 字符串处理；一律带长度读取
- **`Content-Length` 是整个请求体的长度**，不等于文件长度
- **边界字符串理论上可能出现在文件内容里**：生产级实现会生成足够随机的 boundary，并按规范处理边界匹配；本项目只处理第一个 part，边界风险在可接受范围内

**安全**

- **上传是「用户写服务器」的入口**：类型、大小、文件名、落盘位置、取回方式都要约束
- **白名单优于黑名单**：只允许明确需要的类型，而不是列举禁止的类型
- **`Content-Disposition: attachment` 是第二道防线**：即使类型被放行，也不在浏览器里就地渲染
- **展示用户输入要 HTML 转义，拼接链接要 URL 编码**：两者用途不同，不能互相替代
- **响应头中的用户输入要过滤控制字符与引号**：防止头部注入

**文件系统**

- **目录按需创建**：`mkdir` 返回 `EEXIST` 不是错误
- **`stat` + `S_ISREG`**：确认目标是普通文件，避免返回目录或设备
- **路径只保留单段**：是防止目录穿越最简单可靠的办法之一
