# 02 · 原项目解析

> **本章讲什么**：二次开发的出发点是理解原版。本章描述原项目 TinyWebServer 的结构、它在什么条件下能工作、又在哪里失效，以及**哪些设计被保留、哪些被替换**。
>
> **对应记录**：[ROADMAP](../ROADMAP.md) 第三节、[summary](../summary.md)、[changes/000](../changes/000-baseline.md)

---

## 速览

1. **原项目不是「写得差」，而是「在一个更小的目标下写得够用」**：它实现了半同步/半反应堆 + 线程池 + 状态机 + 定时器回收，结构和分层是清晰的。
2. **它的失效集中在一点上**：**没有「连接归属」约定**。连接状态被多线程共享，由此派生出忙等、`EPOLLONESHOT`、释放路径重叠等一系列附加机制与缺陷。
3. **整理出的 28 项问题分五类**：并发与生命周期（7）、正确性与健壮性（11）、协议实现（3）、功能完整性（2）、代码规范（5）。
4. **7 项与并发无关的改动被前置**（构建、规范、测试），因为「在架构重构之前，能修的都先修」——否则重构时会把老缺陷一起搬过去。
5. **有些缺陷更深**：最严重的一条（绝对形式 URI 无路径时空指针解引用）四轮优化都没碰到，因为它是**按条目推进的盲区**——没人按条目之外逐行走过请求行解析。
6. **原设计的相当一部分被保留**：三状态机、`mmap`+`writev` 发送、连接池 RAII、日志单例、命令行接口，甚至有意保留了无效果的 `-o` 参数以维持接口兼容。

---

## 一、原项目是什么

[TinyWebServer](https://github.com/qinguoyi/TinyWebServer) 是一个广泛传播的 Linux C++ 学习型 Web 服务器（MIT 协议），目标是「用一套经典结构把高并发服务器的主干讲清楚」。它提供：

- 静态资源服务（`mmap` + `writev` 发送）
- 用户注册与登录（直接访问 MySQL；代码里的 `cgi` 标志只表示「这是一个 POST 请求」，并不涉及外部 CGI 程序或进程池）
- 一个可交互的多页面站点
- 同步/异步两种日志写入方式

它的定位是**教学**，所以选择的结构都是教科书式的经典组合：**线程池 + 非阻塞 IO + epoll 事件驱动 + 状态机解析 + 升序链表定时器**。这套组合在教科书的假设下是自洽的。

## 二、原架构

### 2.1 运行结构

| 模块 | 位置 | 职责 |
|:--|:--|:--|
| 服务器主类 | `webserver.{h,cpp}` | 持有监听套接字与 **epoll 实例**，主循环中分发事件、调度定时器 |
| 协议处理 | `http/http_conn.{h,cpp}` | 每连接一个对象，三状态状态机解析，`mmap` + `writev` 发送 |
| 线程池 | `threadpool/threadpool.h` | 半同步/半反应堆，主线程 `accept` 后投递任务 |
| 定时器 | `timer/lst_timer.{h,cpp}` | 升序双向链表管理超时连接，`SIGALRM` + `socketpair` 触发检查 |
| 数据库 | `CGImysql/sql_connection_pool.{h,cpp}` | 连接池单例，RAII 方式借用与归还 |
| 日志 | `log/log.{h,cpp}` | 单例，支持同步与异步两种写入方式 |

### 2.2 请求处理流程

```
epoll_wait
  └─ 读事件 → http_conn::read_once()   读入缓冲区
       └─ process_read()   状态机解析：请求行 → 头部 → 内容
            └─ do_request()   路由：静态资源 / 登录注册 / 文件上传
       └─ process_write()  组装响应头，映射静态文件
  └─ 写事件 → http_conn::write()   writev 发送
       └─ 完成后重置连接状态或关闭
```

工作线程的两种模式由 `-a` 参数切换：**Reactor**（工作线程只处理业务，读写由主线程做）与 **Proactor**（工作线程连读写一起做）。

### 2.3 关键实现手法

| 手法 | 做法 | 评价 |
|:--|:--|:--|
| **事件注册** | `http_conn` 持有 `static int m_epollfd`（全局单例），7 处直接调 `modfd`/`addfd`/`removefd` | 简单直接，但**与「每线程一个 epoll」直接冲突** |
| **抑制重复投递** | 注册连接时带 `EPOLLONESHOT`，处理完再重新注册 | 在「连接可能被多个线程处理」的前提下是**正确**的解法 |
| **确认处理完成** | 主线程在 `while (true)` 里轮询 `improv` 标志位 | 引入 CPU 空转，且标志位无跨线程可见性保证 |
| **空闲回收** | `SIGALRM` 每 5 秒触发一次，全表扫描升序链表 | 精度受信号粒度限制（实测配置 15 秒、实际 18.6 秒才回收） |
| **定时器存储** | 静态数组 + 升序双向链表 | 按 fd 下标访问连接槽位，**fd 被复用后会命中另一条连接** |
| **发送** | `mmap` 静态文件 + `writev` 一次性发出响应头与正文 | **这个设计很好，被完整保留** |

## 三、原架构为什么能工作，又为什么不够

**它能工作**，是因为它有一套自洽的假设：

> 假设：连接的处理路径是短促的——一次事件、一段处理、很快结束。在这个假设下，用 `EPOLLONESHOT` 把连接「锁」给某个工作线程一段时间，是可行且简单的。

**它不够**，是因为这些假设在持续演进中逐条失效：

- **假设 1「事件处理是短的」**——当处理逻辑变多（文件上传、数据库查询），「锁」住连接的时间变长，主线程的忙等代价随之上升
- **假设 2「标志位的修改能被立刻看到」**——这在语言层面**从未成立**，只是低并发下没有暴露
- **假设 3「释放路径只有一条」**——随着定时器回收与连接关闭都变得常见，两条路径重叠的概率上升
- **假设 4「缓冲够用」**——固定 2 KB 读缓冲在遇到大请求体或上传时直接失效

**最根本的一点**：这些假设都是**隐含**的。代码里没有任何一处写明「连接状态只能由某一个线程访问」，因此也就没有任何机制去保证它。**正确性依赖的是运行时时序的偶然性，而不是结构性约束**——这是原架构与成熟服务器实现之间真正的差距。

## 四、28 项问题的归类

优化开始前整理的清单，按性质分五类：

### 4.1 并发与生命周期（7 项）

| # | 问题 | 后果 |
|--:|:--|:--|
| 1 | **触发模式未按配置生效** | 注册 fd 时读取的成员尚未赋值，实际始终按 LT 注册，`-m` 的 ET 组合**从未真正生效** |
| 2 | **定时器链表缺少线程约束** | 主线程遍历链表与工作线程修改链表之间没有同步 |
| 3 | **资源释放路径重叠** | 连接关闭与定时器回调均释放同一 fd，且无幂等保护 |
| 4 | **超时回调持有裸指针** | 定时器指向静态数组元素，缺少对象失效后的安全丢弃机制 |
| 5 | **读写路径存在忙等** | 主线程轮询标志位等待工作线程，占 CPU 且无可见性保证 |
| 6 | **描述符耗尽无兜底** | ET 下 `accept` 因 `EMFILE` 失败后不会再触发，服务**永久失去接受连接的能力** |
| 7 | **连接对象预分配** | 按最大连接数静态分配连接数组，每个携带固定缓冲区 |

### 4.2 正确性与健壮性（11 项）

日志缓冲区越界写、`recv` 返回值漏判、成员未初始化、共享用户表读写同步不对称、**静态资源路径未规范化**、**数据库查询字符串拼接**、**口令明文存储**、参数解析依赖固定偏移、错误响应状态码不匹配、**固定读缓冲区**、配置硬编码。

> 加粗的三项属于安全问题，详见 [07](07-安全加固.md)。

### 4.3 协议实现（3 项）

- **URL 未解码**——`%XX` 序列按字面处理，含转义字符或非 ASCII 的路径无法正确匹配
- **未支持 HEAD 方法**——解析阶段直接判定为错误请求
- **头部长度与 `Content-Length` 缺少校验**——未处理超长头部、非数字或异常取值的长度字段

### 4.4 功能完整性（2 项）

- **上传文件不可访问**——文件写入 `./upload/`，而静态根目录为 `./root/`，上传后无法通过 HTTP 查看
- **上传缺少类型与大小约束**——仅做路径分隔符剥离

### 4.5 代码规范（5 项）

大量 `strcpy`/`strcat`/`sprintf`、头文件里的全局 `using namespace std`、`malloc`/`free` 与 `new`/`delete` 混用、用 `assert` 承担运行时校验（Release 下失效）、只读方法普遍缺少 `const`。

### 4.6 分类的意义

这五类的**处理顺序**是有讲究的：并发与生命周期必须留到最后（要重构架构），其余四类可以在重构前修完。**先修与架构无关的部分**，重构时就只有架构本身在变，出问题时变量更少。

## 五、比「28 项」更深的地方

清单是「按条目」整理的，但**条目之外的代码从未被系统检查过**。四个阶段收口后，对全部源码做了一次独立审核，又查出 8 处缺陷，其中几条很值得记：

| 缺陷 | 性质 |
|:--|:--|
| **绝对形式 URI 且无路径时空指针解引用** | **一条请求即可打挂单进程服务端**。它**继承自原项目**，四轮优化从未触及 |
| 管线化请求被静默丢弃 | 一个 TCP 段内的多个完整请求只处理第一个 |
| 登录与注册从未取过连接池连接 | 直接把空 `MYSQL*` 交给 `mysql_stmt_init`，**直接段错误**；**自初始导入即存在** |

第一条尤其值得记：为什么四轮优化都没碰到它？因为**没人按条目之外去逐行走一遍请求行解析**。这是「按条目推进」这种工作方式的固有盲区——**清单能保证列出的都做完，但不能保证该列的都列了**。

> 对应的做法是：阶段收口后补一次**不限于清单**的全项目审核。这一步的价值不在于查出多少，而在于它覆盖了清单永远覆盖不到的地方。

## 六、哪些被保留，哪些被替换

### 6.1 被保留的设计

| 保留项 | 理由 |
|:--|:--|
| **三状态机解析结构**（请求行 → 头部 → 内容） | 结构正确，与大改无关 |
| **`mmap` + `writev` 发送** | 静态资源零拷贝，是原设计里最好的部分 |
| **CGI 式的路由改写**（`/2` `/3` 把 `m_url` 改成跳转页面） | 结构可用，只在参数解析上加固 |
| **连接池的 RAII 借用/归还** | 设计合理，保留接口 |
| **日志单例 + 同步/异步两种模式** | 语义保留，实现重写（见 [08](08-日志系统.md)） |
| **命令行参数接口**（`-p -l -m -o -s -t -c`） | 保持与原项目兼容，降低使用者的迁移成本 |
| **空闲超时 15 秒**（原为 3 × `TIMESLOT`） | 沿用取值使超时行为与改造前一致，便于对比 |

### 6.2 被替换的设计

| 原设计 | 替换为 | 触发原因 |
|:--|:--|:--|
| 线程池（半同步/半反应堆） | 主从 Reactor + `EventLoopThreadPool` | 消除共享状态，见 [03](03-并发模型重构.md) |
| 升序链表 + `SIGALRM` 定时器 | `TimerQueue`（`timerfd`） | 统一事件源、提升精度、去掉信号处理函数，见 [04](04-事件源统一.md) |
| `static m_epollfd` 全局单例 | 每线程一个 `EventLoop` | 「每线程一个 epoll」是主从 Reactor 的前提 |
| `EPOLLONESHOT` + 忙等标志位 | **直接删除** | 归属约定成立后不再需要 |
| 按 `MAX_FD` 预分配连接数组 | 按需 `make_shared` | 常驻内存 262.8 MB → 12.6 MB |
| 固定 2 KB 读缓冲 | 动态扩容缓冲 | 支持大请求体与上传 |
| `-a`（Proactor/Reactor 二选一） | **移除** | Linux `epoll` 是就绪通知，所谓 Proactor 路径并不成立 |
| Makefile | CMake | 支持 Debug/Release/Sanitizer 多种构建 |

### 6.3 一处「决定不做」

`-o`（`opt_linger`）参数**被有意保留为无效果**。

原实现把 `SO_LINGER` 施加在**监听描述符**上，本就没有效果。把它挪到连接描述符上会让它真正生效——而 `l_linger = 0` 的语义是「`close` 时发送 **RST** 而非 FIN，并丢弃未发送数据」，对 Web 服务端是**有害**的：会截断响应、破坏长连接。

处理方式是：保持无效果，并在配置文件与 README 中**写明理由**。保留该参数本身是为兼容原项目的命令行接口。

> **这一条的价值在于「区分『没做』与『决定不做』」**。状态被**决定**才算闭环，被**遗忘**则不是。项目里另有两处「延后到某阶段一并处置」的承诺，而那个阶段收口时无人回收——**延后等于遗忘**。

## 七、通用知识

**读一份既有代码**

- **先问「它在什么假设下成立」**：判断一段设计的优劣，不能脱离它被写出来时的目标
- **区分「缺陷」与「取舍」**：前者是错的，后者是当时条件下的合理选择。把取舍当缺陷批，是代码评审里最常见的误判
- **关注「结构约定」而非「单个 bug」**：一个有归属约定的架构，天然比一个靠时序侥幸正确的架构缺陷更少
- **清单的盲区**：按条目推进能保证列出的都做完，**不能保证该列的都列了**；收口时需要一次不限于条目的复查

**C++ 服务端编程**

- **`EPOLLONESHOT` 的用途与代价**：它服务于「一个连接可能被多个线程处理」这一前提；一旦改成 one loop per thread，它就变成了不必要的机制
- **前后端参数接口的兼容性**：改实现时保留 CLI 接口，能显著降低使用者的迁移成本
- **`SO_LINGER` 的两种语义**：`l_linger > 0` 是优雅关闭等待，`l_linger = 0` 是 RST——后者对服务端几乎总是错的
