# 06 · 日志系统：服务器如何记录自己做过什么

> **本章讲什么**：日志是服务器排障的主要依据。本章先讲清日志**怎么产生、写到哪里、同步与异步有什么区别**，再讲本项目的日志模块为什么把「每行落盘」改成「按块批量落盘」，以及这次改动的收益、代价与验证方式。
>
> **读完能回答**：
>
> - 一条日志长什么样？`LOG_INFO` 展开后做了什么？
> - 日志文件放在哪、什么时候按天或按行数切分？
> - 同步写和异步写的语义差别是什么？
> - 为什么「每行都 `fflush`」会严重拖慢吞吐？
> - 缓冲池、写盘线程、背压分别解决什么问题？
>
> **对应源码**：`log/log.{h,cpp}`、`config.{h,cpp}` 的 `[log]` 节
> **前置知识**：[01](01-看懂一个Web服务器.md) 的线程与系统调用；[02](02-项目总览.md) 的启动流程。

---

## 速览

1. **日志是写给人和工具看的流水账**：什么时间、什么级别、发生了什么。服务器出错时，日志往往是唯一能还原现场的东西。
2. 本项目提供 `LOG_DEBUG` / `LOG_INFO` / `LOG_WARN` / `LOG_ERROR` 四个宏，受 `-c` 开关统一控制。
3. 日志写入有两种模式：**同步**（每行直接写文件并刷出）与**异步**（先写进内存缓冲块，由专门的写盘线程批量落盘）。
4. 日志在请求热路径上被大量调用：**单次静态页面请求约 23 行**。因此它的写入代价会直接影响吞吐。
5. 最初的异步实现每行仍要 `fflush`、取锁三次，结果在 `-t 2` 下**比同步还慢**（9157 vs 15792 QPS）。
6. 改造后，调用线程只把整行 `memcpy` 进共享缓冲块，写盘线程按块落盘；异步 `-t 2` 提升到 **36209 QPS（约 4 倍）**，每行写系统调用降到约 **1/4.3**。
7. 写不过来时不阻塞请求线程，而是**丢弃并计数**，由写盘线程把「已丢弃 N 行」写进文件——**丢失可见**。
8. 代价是崩溃时最多丢一个刷新间隔（默认 1 秒）的日志；优雅退出仍会完整落盘。

## 一、日志是什么

### 1.1 一条日志的样子

本项目写出的每一行大致是：

```text
2026-10-02 20:41:07.123456 [info]: new connection, active: 3
2026-10-02 20:41:07.234567 [info]: GET /judge.html HTTP/1.1
2026-10-02 20:41:07.345678 [erro]: register user failed, mysql error: ...
```

拆开看：

| 部分 | 例子 | 作用 |
|:--|:--|:--|
| 时间 | `2026-10-02 20:41:07.123456` | 精确到微秒，便于还原时序 |
| 级别 | `[info]:` / `[warn]:` / `[erro]:` / `[debug]:` | 区分普通信息、警告、错误、调试 |
| 内容 | `GET /judge.html HTTP/1.1` | 调用点自己格式化 |

### 1.2 日志的用途

| 场景 | 日志能提供什么 |
|:--|:--|
| 请求排障 | 收到了什么请求、返回了什么 |
| 连接问题 | 何时建立、何时关闭、当前活跃连接数 |
| 数据库问题 | SQL 执行失败的原因 |
| 性能分析 | 日志行数、丢弃行数、写入是否跟得上 |
| 崩溃后复盘 | 崩溃前最后发生了什么（异步模式下最多丢一个刷新间隔） |

日志不是业务数据，**它出问题不应该拖垮主流程**。这句话是后面所有取舍的出发点。

## 二、在代码里怎么用

### 2.1 四个宏

```cpp
LOG_DEBUG("...");
LOG_INFO("new connection, active: %ld", m_conn_count.load());
LOG_WARN("send 100 continue failed, errno:%d", errno);
LOG_ERROR("mysql_store_result error:%s\n", mysql_error(mysql));
```

宏展开后，大致是：

```cpp
if (0 == m_close_log) {
    Log::get_instance()->write_log(level, format, ...);
}
```

`m_close_log` 来自当前作用域（连接对象、服务器对象等持有这个成员）。`-c 1` 关闭日志时，宏连函数调用都不会发生。

> 宏用 `do { ... } while (0)` 包住，避免 `if (x) LOG_INFO(...); else ...` 里的 `else` 错挂到宏内部的 `if` 上。

### 2.2 级别

| 级别 | 宏 | 典型用途 |
|:--|:--|:--|
| 0 | `LOG_DEBUG` | 调试信息，默认很少使用 |
| 1 | `LOG_INFO` | 请求行、响应、连接建立/关闭 |
| 2 | `LOG_WARN` | 可恢复的异常，如一次 `send` 失败 |
| 3 | `LOG_ERROR` | 需要人工关注的问题，写完立即刷出 |

`LOG_ERROR` 保留一次 `flush()`：错误行是排障时最不能丢的，而按间隔批量落盘意味着崩溃时最多丢一个间隔。错误路径罕见，这点开销可以接受。

## 三、日志在请求路径上的位置

日志不是只出现在出错时。一次普通的静态页面请求，大约会写 **23 行**：

| 位置 | 内容 |
|:--|:--|
| `parse_line` / `process_read` | 每解析一行请求行或头部记一条 |
| `add_response` | 每次追加响应内容记一条 |
| `TcpConnection` | 连接建立、关闭 |
| `do_request` | 路由相关记录 |
| 数据库/上传等分支 | 失败或关键动作 |

这个数字很重要：如果每行日志都产生一次系统调用，那么每次页面请求就会多出二十多次系统调用。**日志的写入方式会直接反映在 QPS 上**。

## 四、日志模块的整体结构

### 4.1 单例与初始化

`Log::get_instance()` 返回进程内唯一的日志对象：

```cpp
static Log *get_instance()
{
    static Log instance;
    return &instance;
}
```

启动时由 `WebServer::log_write()` 调用 `init(LogConfig)`：

```cpp
LogConfig config;
config.dir = m_log_dir;                 // 日志目录，默认 ./ServerLog
config.file = m_log_file;               // 文件名前缀，默认 server
config.write_mode = m_log_write;        // 0 同步 / 1 异步（默认）
config.log_buf_size = m_log_buf_size;   // 单行上限
config.split_lines = m_log_split_lines; // 单文件行数软上限
config.batch_buf_size = ...;            // 缓冲块大小，默认 64 KiB
config.flush_interval_ms = ...;         // 异步刷新间隔，默认 1 秒
```

初始化时还会做两件事：

- **创建日志目录**（如果不存在）；
- **`tzset()` 预热时区**：`localtime` 首次调用会改写全局时区状态，不是线程安全的；在单线程的 `init` 里先做一次，之后并发取时间就只剩读。

### 4.2 文件名与轮转

日志文件名由「日期前缀 + 配置的文件名」组成：

```text
ServerLog/2026_10_02_server
ServerLog/2026_10_02_server.1
ServerLog/2026_10_02_server.2
```

| 轮转条件 | 判据 |
|:--|:--|
| **按天** | 年、月、日三者变化（只比 `tm_mday` 会在跨月同日时漏切） |
| **按行数** | 当前文件行数 + 本块行数超过 `split_lines` 时换到 `.1`、`.2`…… |
| **行数上限是「软」的** | 判据是「整块写下去会不会越过」，文件可能多出不到一块的行数；换来写盘侧只做整块写出 |

### 4.3 写入一行：`write_log`

无论同步还是异步，格式化部分相同：

```cpp
if (!m_ready.load()) return;              // 未初始化/已停机：直接返回

gettimeofday(&now, NULL);                 // vDSO，不进入内核
localtime_r(&now.tv_sec, &my_tm);         // 可重入，写入调用方自己的 tm

snprintf(t_line, cap, "... [%s] ", level_tag(level));
vsnprintf(t_line + n, ..., format, valst);
t_line[n + m] = '\n';
```

`t_line` 是 `thread_local` 的定长数组：**每个线程有自己的格式化缓冲，不需要锁**。

之后按模式分流：

```cpp
if (sync_mode)
    write_line_direct(t_line, len, now.tv_sec);   // 同步：直接写文件
else
    // 异步：memcpy 进缓冲块，必要时唤醒写盘线程
```

## 五、同步模式：写入即落盘

同步模式的语义是：**`write_log` 返回时，这一行已经写进文件**。

```cpp
void Log::write_line_direct(const char *data, size_t len, time_t sec)
{
    std::lock_guard<std::mutex> guard(m_file_mutex);
    rotate_if_needed_locked(one);
    fwrite(data, 1, len, m_fp);
    fflush(m_fp);
}
```

优点：

- 进程崩溃时最多丢正在写的那一行；
- 行为直观，适合调试。

缺点：

- 每行一次 `fwrite` + `fflush`，约等于一次系统调用；
- 多线程写日志时，所有线程在 `m_file_mutex` 上串行；
- 请求路径上二十多行日志，就是二十多次串行写文件。

**同步模式至今仍保留，且不做缓冲**——它的价值就是「写入即落盘」，如果也走缓冲池，这个语义就没了。

## 六、异步模式：调用线程只负责放进内存

### 6.1 目标

把「写文件」从请求线程上移走：

- 请求线程只把日志行复制进一块内存；
- 由**一个专门的写盘线程**把内存块整体写进文件。

这样请求路径上**没有文件系统调用、没有内存分配**（取时间、格式化仍在；锁竞争时仍可能触发一次 futex）。

### 6.2 三个角色

简单的「前后两块缓冲」不够用：块写满后如果写盘线程还没取走，就需要第三块、第四块……于是本项目的做法是**固定大小的缓冲池**：

| 角色 | 说明 |
|:--|:--|
| `m_front` | 当前正在写入的块 |
| `m_pending` | 已写满、等待落盘，**先进先出**；有且只有写盘线程会取走 |
| `m_free` | 空闲块 |

池大小固定为 **9 块**（1 块写入 + 8 块排队），每块默认 64 KiB。内存上界是确定的：`9 × 64 KiB`。池在 `init` 时一次性分配，此后写入与落盘路径都不再申请内存。

### 6.3 写入路径

```text
1. 取时间（localtime_r）
2. 把时间前缀与内容格式化进线程私有缓冲 t_line
3. 取一次锁，memcpy 进 m_front
     ├─ 放得下 → 完事
     └─ 放不下 → 换块，并唤醒写盘线程
                 └─ 池中没有空闲块 → 丢弃并计数（背压）
```

**唤醒只在换块时做**。逐行唤醒会把刚省下的系统调用又按行加回来。

### 6.4 写盘路径

写盘线程在两种情况下醒来：

1. 被「换块」唤醒（有已写满的块在排队）；
2. `flush_interval` 到点（块没满，但等够久了）。

```cpp
while (!m_stopping) {
    m_cv.wait_for(lock, flush_interval, [] { return m_stopping || !m_pending.empty(); });
    retire_front_locked();   // 把未满的 front 也交出去
    drain_locked(lock);      // 取出 pending，锁外整块写文件
}
```

`drain_locked` 的关键动作：

```cpp
const std::vector<Batch *> drained = m_pending;   // 取走
m_pending.clear();
const uint64_t target = m_seq;                    // 在同一临界区记录目标序号
lock.unlock();

for (Batch *batch : drained)
    write_batch(*batch);                          // 锁外写文件

lock.lock();
// 归还块、推进 m_drained、唤醒 flush 等待者
```

**锁外写文件**是重点：写磁盘可能很慢，不应该让所有写日志的线程都陪着等。

### 6.5 背压：写不过来时怎么办

如果写盘线程持续跟不上，`m_free` 会耗尽。此时有三种选择：

| 方案 | 问题 |
|:--|:--|
| 阻塞调用线程等空闲块 | 把磁盘延迟压回 Reactor 线程，违背异步的初衷 |
| 调用线程直接写文件 | 同样把磁盘写压回 Reactor 线程 |
| **丢弃新行并计数** | 日志会丢，但主流程不受影响 |

本项目选第三种，并让写盘线程把丢弃数量写成文件里的一行：

```text
2026-10-02 20:41:07.123456 [warn]: 已丢弃 18432 行日志（落盘速度跟不上写入）
```

**丢失可见**，而不是无声无息。

## 七、为什么必须改造：每行落盘的三笔代价

最初的异步实现虽然也叫「异步」，但每一行仍然：

```text
LOG_INFO(...) → write_log
    ├─ 取锁：轮转判断
    ├─ 取锁：格式化到共享缓冲
    ├─ 取锁：写文件
    └─ flush() → fflush        ← 每行一次系统调用
```

| 代价 | 说明 |
|:--|:--|
| **每行一次 `fflush`** | `LOG_DEBUG/INFO/WARN` 宏内都调 `flush()` |
| **每行取锁三次** | 轮转、格式化、写文件各一次；异步路径还有队列的 `full()` / `push()` |
| **轮转在调用线程** | `fclose` + `fopen` 也持锁，一次轮转挡住所有写日志的线程 |

**实测印证了分析**：旧异步方式在 `-t 2` 下只有 **9157 QPS**，比同步方式的 **15792** 还低。异步本来是为了把写入代价移走，结果队列与锁的开销超过了它省下的写调用——**加了机制，却没有解决根因**。

## 八、改造结果

同一环境、同一时段、`-m 0`、开启日志：

| 写入方式 | 改动前 `-t 2` | 改动后 `-t 2` | 改动前 `-t 8` | 改动后 `-t 8` |
|:--|--:|--:|--:|--:|
| 同步 | 15792 | 14496 | 17403 | 16789 |
| 异步 | **9157** | **36209** | 24523 | 24053 |

- **异步 `-t 2` 提升约 4.0 倍**，P50 从 10.690 ms 降到 2.620 ms，P99 从 22.410 ms 降到 5.790 ms；
- **同步基本持平**（−8%，落在 ±10% 噪声内）——符合预期，它按设计仍是每行一次写入；
- **异步 `-t 8` 与改动前持平且方差很大**，且明显低于 `-t 2`。

最后一条本身是个有价值的发现：8 个子 Reactor + 1 个写盘线程共 10 个线程跑在 4 个逻辑核上，**超过核数之后日志的互斥量成为争用点**。这是「批量落盘下线程数并非越多越好」的一个可观测事实。

每行日志的成本（`-t 2`，读 `/proc/<pid>/io` 与 `/proc/<pid>/stat`）：

| 组 | QPS | 每行写调用 | 每行 CPU tick |
|:--|--:|--:|--:|
| 改动前 · 同步 | 16507 | 0.385 | 0.00041 |
| 改动前 · 异步 | 9375 | 0.195 | 0.00072 |
| 改动后 · 同步 | 14503 | 0.392 | 0.00048 |
| 改动后 · 异步 | **36632** | **0.045** | **0.00023** |

每行日志的写系统调用降到约 **1/4.3**，CPU 时间降到约 **1/3.1**。同步方式每行成本与改动前一致，说明**收益全部来自「不再逐行落盘」**。

还有一条最该守住的性质：改造前后**每请求日志行数一致**（23.1 → 23.2），说明调用点的行为没有因改造而变化。

## 九、正确性与代价

### 9.1 顺序

- 同一个线程写入的行，在块内保持顺序；
- 待写队列先进先出，且**只有一个写盘线程取走**；
- 因此文件内容的顺序等于写入顺序。

### 9.2 `flush()` 为什么要循环

池满时 `retire_front_locked()` 会失败，`m_front` 里还留着没交出去的行。`flush()` 必须反复「唤醒—等待—再试」：

```cpp
while (m_front->used > 0) {
    const bool retired = retire_front_locked();
    const uint64_t target = m_seq;
    m_cv.notify_all();
    m_flush_cv.wait(lock, [=] { return m_drained >= target && (retired || !m_free.empty()); });
}
```

只等一次就返回，会漏掉还留在 `m_front` 里的内容。

### 9.3 崩溃时会丢什么

异步模式下，崩溃时最多丢**一个刷新间隔**（默认 1 秒）的日志。这是批量落盘的固有代价。

进程正常退出时，`WebServer` 的析构函数最后调用 `Log::flush()`，写盘线程退出前也会做最后一次排空，因此**优雅退出不丢日志**。

### 9.4 配置项与边界

- `batch_buf_size` 的下限是单行上限：一行必须整体装进一个空块，否则写盘侧要处理「行跨块」；
- 所有日志配置在启动阶段校验范围，越界直接终止，而不是静默夹取；
- `init` 可重复调用：先停掉上一个写盘线程、排空并关闭上一个文件，避免句柄泄漏。

### 9.5 由配置取值触发的三处缺陷

日志模块有多个直接参与缓冲区下标计算的配置项。改造中对它们做了范围夹取，顺带修掉了三处**由配置取值过小触发**的既有缺陷：

| 缺陷 | 表现 | 证据 |
|:--|:--|:--|
| `snprintf(m_buf, 48, ...)` | 缓冲区只有 `buf_size` 字节，而时间前缀固定按 48 字节写；`buf_size < 48` 时是**堆越界写** | ASan 在 `buf_size = 16` 下报 `heap-buffer-overflow`，写入 36 字节到 16 字节的堆块 |
| 同一处的算术 | `n` 与前后的长度参数都基于 `m_log_buf_size` 作差，取值过小时 `n` 变负，指针与长度一并下溢 | 与上一条同源 |
| `init` 重复调用不 `fclose` | 每次 `init` 都重新 `fopen`，上一份文件句柄泄漏 | 单测直接以 `/proc/self/fd` 的条目数核对 |

> **配置项是缺陷的温床**：它们的取值组合几乎不可能被穷举测试。因此本项目在启动阶段统一校验范围，而不是等到运行期出错。

### 9.6 两把锁

| 锁 | 保护 | 谁用 |
|:--|:--|:--|
| `m_mutex` | 缓冲池（`m_front` / `m_pending` / `m_free` / 序号） | 所有写日志的线程 + 写盘线程 |
| `m_file_mutex` | **文件位置**（`m_fp`、行数、轮转状态） | 写盘线程、同步模式下的调用线程 |

**两把锁从不同时持有**（锁序规定）。后者的意义是把「**同一时刻只有一个写文件的人**」变成**结构约束而非约定**——两种写入方式都经 `write_batch` 进这把锁，将来即便出现第三种排空者也不会写坏文件。

## 十、验证与一次「测试写错了」的教训

### 10.1 单元测试（12 例）

| 用例 | 判据 |
|:--|:--|
| `LineNeverExceedsBufferSize` | 行长不超上限；ASan 下不报越界 |
| `AsyncFlushesOnIntervalWithoutExplicitFlush` | **不调用 `flush()`**，写盘线程按间隔自行落盘 |
| `AsyncDoesNotWriteBeforeFlush` | 间隔远大于用例时长时文件为空——批量而非逐行 |
| `ConcurrentLinesAreIntactAndOrdered` | 4 线程 × 2000 行：行数相符、每行完整、同一线程序号递增 |
| `RepeatedInitDoesNotLeakFd` | 20 次 `init` 后 fd 数不增长 |
| `RotationPreservesOrder` | 各后缀文件按序拼接后行序列与写入序列一致 |
| `BackpressureAccountIsBalanced` | 核对「普通行 + 丢弃 = 写入」，并确认丢弃路径确实被走到 |

### 10.2 一个断言「什么都不发生」的测试

改造后的第一版里，写盘线程定时醒来只排空 `m_pending`，没有处理 `m_front` 里未满的块。于是异步日志可能长期留在内存里——跑了三次请求、等过一个间隔，文件仍是空的。

而当时那条用例断言的恰恰是「**未调用 `flush()` 时文件应为空**」。它把**错误行为**写成了正确断言，所以**通过了**。

补上的正确判据是：不调用 `flush()`，按间隔等待后内容**必须可见**。

> **教训**：一个断言「什么都不发生」的测试，可能同时通过于「行为正确」与「功能完全没实现」。断言应该写成「某件事必须发生」，至少不要只用前者。

### 10.3 TSan 的成片误报

TSan 在本模块报出 31 条数据竞争与 1 条重复加锁，覆盖 `m_mutex` 保护下的几乎每一处访问。

**判据**：同一互斥量保护下的两处访问被报成竞争，本身不自洽，说明工具记错了锁的归属。

用一个**不含任何 `Log` 代码**的最小程序（`mutex` + `condition_variable` + 写线程）逐一替换等待写法，结果是：带超时的条件变量等待（`wait_for` / `wait_until` 等）各报 3 条，而不带超时的 `wait` 报 0 条。再把 `writer_loop` 里的定时等待临时换成轮询，报告归零、12 个用例仍全过，而实现本身不变。

**结论**：本工具链（GCC 11 的 libstdc++ 与 libtsan）在处理**带超时的条件变量等待**时会记错互斥量持有状态。考虑轮询会引入真实的落盘延迟与更多丢弃，**保留 `wait_for`**，并在源码与架构文档里留下说明，避免后来者追这个幽灵。

## 十二、通用知识

**日志系统设计**

- **同步 vs 异步的语义差别**：同步 = 写入即落盘（崩溃不丢）；异步 = 批量落盘（崩溃最多丢一个刷新间隔）
- **批量落盘为什么有效**：把 N 次写系统调用合并为 1 次
- **缓冲池 vs 双缓冲**：一旦需要排队，池化就是自然结果
- **背压要可见**：丢弃 + 计数 + 写出丢弃行，优于静默丢弃，也优于把写压回调用线程
- **文件轮转的判据**：按日切要取年月日；行数上限设为「软」可以简化写盘侧
- **只能有一个写盘线程**：这是「文件顺序 = 写入顺序」的保证

**并发编程**

- **`thread_local` 消除锁**：线程私有格式化缓冲让热路径无锁
- **`wait_for` 带谓词**：`notify` 早于 `wait` 也不会丢唤醒
- **用序号 + 条件变量表达「排空完成」**：目标序号必须在取队列的同一临界区内捕获
- **锁的次序约定**：两把锁从不同时持有；把「同时只有一个写文件的人」变成结构约束
- **工具误报要有判据、最小复现和取舍结论**，而不是直接忽略

**工程方法**

- **断言要写成「必须发生」**：断言「什么都不发生」的测试可能通过于「功能完全没实现」
- **用探针确认测试路径真的被走到**：触发不了背压的背压测试毫无价值
- **优化要能归因**：同步方式每行成本不变，才说明收益确实来自「不再逐行落盘」
- **配置项是缺陷的温床**：多处堆越界都由「取值过小」触发，应在启动阶段拦下
