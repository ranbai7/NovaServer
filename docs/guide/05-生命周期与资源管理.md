# 05 · 生命周期与资源管理

> **本章讲什么**：一条连接身上有四样资源——描述符、连接对象、内存映射、定时器。它们分别由谁拥有、在什么时刻释放、释放顺序为什么不能颠倒。这是 C++ 做服务端最容易出错的地方，也是本项目崩溃最多的一块。
>
> **对应源码**：`net/tcp_connection.{h,cpp}`、`net/channel.{h,cpp}` 的 `tie`、`net/event_loop.cpp` 的注册表、`webserver.cpp` 的析构
> **对应记录**：`docs/changes/013`、`017`、`020`、`024`、`029`

---

## 速览

1. **原实现把连接对象按最大连接数预分配**：`new http_conn[65536]`，每个自带 2 KB 读缓冲 + 1 KB 写缓冲 → 仅缓冲就约 **192 MB**，常驻内存恒为 262.8 MB、**与负载无关**。
2. **新实现按需创建**，每个连接一份 `make_shared<TcpConnection>`；`make_shared` 之后**对象地址固定**，协议对象内部指向自身缓冲的裸指针因此始终有效。
3. **释放收敛为唯一出口 `close()`，且幂等**。五个触发点（读失败 / 处理失败 / 写失败 / 对端关闭 / 空闲超时）全部用它。
4. **`std::weak_ptr` 有两处关键用法**：`Channel::tie` 保护回调期间的对象存活；定时器回调持有连接弱引用，连接先死则安静丢弃。
5. **两处必须理解的顺序**：`EPOLL_CTL_DEL` 先于 `close(fd)`；连接注册表用**延迟擦除**。
6. **内存三级下降**：262.8 MB → 76 MB（缓冲改按需）→ **12.6 MB**（连接对象改按需）。
7. **RAII 有一处明确的边界**：站点根路径 `m_root` 至今仍是 `strdup` / `free`，因为它带**析构顺序约束**——必须晚于所有子线程退出。这是「决定不改成 RAII」而不是「忘了改」。

---

## 一、S · 背景：四样资源与三个问题

### 1.1 一条连接身上有四样东西

| 资源 | 谁创建 | 何时该释放 |
|:--|:--|:--|
| **描述符** `connfd` | `accept` 返回 | 连接关闭时 |
| **连接对象** | 连接建立时 | 最后一个引用消失时 |
| **内存映射**（静态文件） | 处理文件请求时 `mmap` | 响应发完后 |
| **定时器** | 连接启动时登记 | 连接关闭时 |

四样资源里，**第三个最容易漏**：映射可能建立在一个**尚未写出响应**的请求上（比如映射成功后连接就出错了），那条路径不经过 `write()`，如果释放动作只挂在写路径上，这块映射就泄漏了。

### 1.2 原实现的三个问题

**问题一：按最大连接数预分配。**

```cpp
users = new http_conn[MAX_FD];    // MAX_FD = 65536
```

每个对象自带 2 KB 读缓冲与 1 KB 写缓冲，即 65536 × 3 KB ≈ **192 MB**，**与实际的连接数无关**。这就是基线里「常驻内存恒为 262.7~262.8 MB」的来源。

**问题二：释放路径重叠且不幂等。** 连接关闭与定时器回调都会释放同一个描述符，没有幂等保护。描述符被内核回收后可能立刻分配给新连接，一条迟到的释放就会**作用到别的连接上**。

**问题三：定时器按 fd 下标访问连接槽位。** 原实现里定时器回调指向静态数组的元素（裸指针）。fd 被复用后，同一个下标会命中**另一条连接**。

---

## 二、T · 目标

| 目标 | 手段 |
|:--|:--|
| 内存与负载相关 | 连接对象按需创建，不再预分配数组 |
| 释放只有一条路径 | 五个触发点收敛到唯一出口，且幂等 |
| 悬垂引用在结构上不可能 | 弱引用表达「不拥有」，强引用只在确实需要时提升 |
| 释放顺序正确 | 顺序固定并由唯一出口保证 |

**核心思路**：**用一个「唯一出口 + 幂等」的释放函数，把「谁在什么情况下释放」这个分散的问题，变成「只需保证出口正确」这一个局部问题。**

---

## 三、A · 做法

### 3.1 连接对象改为按需创建

```cpp
class TcpConnection : public std::enable_shared_from_this<TcpConnection>
{
    EventLoop *m_loop;
    int m_fd;                              // 本对象是它的唯一所有者
    std::unique_ptr<Channel> m_channel;
    http_conn m_conn;                      // 协议对象，按值持有
    uint64_t m_timer_id;                   // 0 表示没有登记
    bool m_closed;
    CloseCallback m_close_callback;
};
```

两个设计点：

- **继承 `enable_shared_from_this`**：对象由 `shared_ptr` 管理，才能在需要时把「自己」交给 `Channel` 或定时器做弱引用绑定。
- **协议对象按值持有**（`http_conn m_conn` 而非指针）。这有个容易被忽略的好处：`make_shared<TcpConnection>` 之后**对象地址固定**，`TcpConnection` 内部的协议对象地址也因此固定，而协议对象内部的裸指针（`m_url`、`m_host` 等）指向的是它自己的读缓冲——**地址稳定，指针就一直有效**。

### 3.2 释放的唯一出口

```cpp
void TcpConnection::close()
{
    if (m_closed) return;                  // 五个触发点可能同轮到达，这里必须幂等
    m_closed = true;
    release_fd();
    if (m_close_callback) m_close_callback(shared_from_this());
}
```

实际释放拆到 `release_fd()`，因为**析构函数里不能调 `shared_from_this()`**（对象已在销毁中）。析构函数只调 `release_fd()` 兜底：

```cpp
TcpConnection::~TcpConnection() { release_fd(); }   // 正常路径已释放过，这里因幂等而成为空操作
```

### 3.3 释放顺序不可颠倒

```cpp
void TcpConnection::release_fd()
{
    if (0 != m_timer_id) { m_loop->timer_queue()->cancel_timer(m_timer_id); m_timer_id = 0; }

    m_conn.unmap();        // 映射可能建立在尚未写出响应的请求上，必须先于描述符释放

    if (m_fd >= 0) {
        m_channel->disable_all();
        m_channel->remove();   // EPOLL_CTL_DEL——必须在 ::close 之前
        ::close(m_fd);
        m_fd = -1;
    }
}
```

三步各自的理由：

| 顺序 | 为什么是这个位置 |
|:--|:--|
| 先取消定时器 | 否则定时器可能在连接已释放后被触发 |
| 再 `unmap()` | 映射不依赖描述符，且可能属于「未写出响应」的请求，不能挂在写路径上 |
| **`EPOLL_CTL_DEL` 先于 `close(fd)`** | 描述符被内核复用之后，一条迟到的 `DEL` 会**作用到新连接上**。这是唯一能保证该顺序的地方 |

### 3.4 弱引用的两处用法

`weak_ptr` 表达的是「我引用你，但**不延长你的生命**」。本项目用它解决两个不同的问题：

**用法一：保护回调执行期间的对象存活（`Channel::tie`）**

关闭连接的回调从 `handle_event` 内部触发，而「关闭」往往意味着持有者的最后一个 `shared_ptr` 被释放。`Channel` 持有持有者的**弱引用**，在分派前提升为强引用：

```cpp
std::shared_ptr<void> guard;
if (m_tied) {
    guard = m_owner.lock();
    if (!guard) return;      // 持有者已销毁，这个描述符的事件不再有意义
}
```

**保护只写在一处**（分派点），而不是要求每个回调都记得先 `shared_from_this()`。

**用法二：定时器回调「对象死了就算了」**

```cpp
const std::weak_ptr<TcpConnection> weak = weak_from_this();
m_timer_id = m_loop->timer_queue()->add_timer(m_idle_timeout_ms, [weak] {
    if (const std::shared_ptr<TcpConnection> conn = weak.lock())
        conn->close();       // 连接还在，才去关它
});
```

连接先于定时器销毁时，`lock()` 拿到空指针，回调**直接丢弃**，而不会访问已释放的内存。这一条替换掉了原实现里「定时器指向静态数组元素」的裸指针写法——**也顺带消除了 fd 被复用后命中另一条连接的隐患**。

> **两处用法的区别值得分清**：用法一是「回调期间必须活着」，语义是**提升并保证**；用法二是「活着才处理，死了就算了」，语义是**尝试并丢弃**。同样用 `weak_ptr`，意图完全不同。

### 3.5 延迟擦除

`EventLoop` 维护一个连接注册表（`unordered_set<shared_ptr<void>>`）。连接的关闭由它**自己的回调**触发，如果在回调栈内直接 `erase`，注册表持有的那一份（可能也是最后一份）引用就会在**回调返回之前**析构连接对象——而调用栈上还站着这个对象的方法。

因此擦除必须延后：

```cpp
void EventLoop::remove_connection(const std::shared_ptr<void> &conn)
{
    // 按值捕获：入队后本函数返回，引用仍被任务持有
    queue_in_loop([this, conn] { m_connections.erase(conn); });
}
```

### 3.6 半关闭：先判断「还有没有活要干」

对端关闭写端（半关闭）时，事件通常**同时**带 `EPOLLIN`（缓冲区里还有最后一个请求）与 `EPOLLRDHUP`。此时不能直接关闭连接，否则那个请求就被丢掉了。

`Channel::handle_event` 的分派顺序是**读 → 写 → 关闭**，而关闭回调里还要再判一次：

```cpp
void TcpConnection::handle_close()
{
    if (m_conn.has_pending_work()) return;   // 由读或写路径收尾
    close();
}

// http_conn
bool has_pending_work() const { return m_read_idx > 0 || bytes_to_send > 0; }
```

`has_pending_work` 的含义是「已收到未处理的请求，或已生成未发完的响应」——**两者皆无才允许关闭**。这样「请求刚读完、响应还没发完」的连接不会被半关闭事件打断。

## 四、内存占用的三级下降

| 版本 | RSS | 原因 |
|:--|--:|:--|
| 优化前 | **262.8 MB** | 65536 × （2 KB 读缓冲 + 1 KB 写缓冲）≈ 192 MB 缓冲，加上对象本身的固定成员 |
| 动态缓冲改造后 | **76 MB** | 读/写缓冲改为 `std::vector` 按需扩容；剩余主要是**连接对象数组本身** |
| 连接对象按需后 | **12.6 MB** | `new http_conn[65536]` 整个去掉，改为按需 `make_shared` |

第三级之后，常驻内存**与负载相关**了——这是比「变小」更重要的性质变化：原实现的 262.8 MB 是**地板**，无论有没有连接都要占着。

---

## 五、RAII 的边界：`m_root` 为什么没改成 RAII

阶段一有一项「内存管理 RAII 化」，最终标为**部分完成**。缺口是一个指针：

```cpp
char *m_root;    // webserver.h —— 站点根路径，strdup / free 管理
```

它**不是忘了改**，而是有一个真实的约束。看析构函数：

```cpp
WebServer::~WebServer()
{
    // 线程池必须最先停：它会 join 所有子线程，而子线程的协议对象仍持有 m_root
    // （作为 doc_root），须等它们全部退出才能释放
    m_thread_pool.reset();
    m_acceptor.reset();
    m_signals.reset();
    m_loop.reset();
    free(m_root);                       // 必须在这里，不能交给成员析构
    Log::get_instance()->flush();
}
```

**关键点**：C++ 的析构顺序是「函数体先执行，然后成员按声明逆序析构」。如果 `m_root` 做成 RAII 成员（如 `std::string` 或 `unique_ptr<char[]>`），它的析构就会发生在**函数体之后**——看似更晚、更安全，但实际不然：

`m_root` 的释放必须**晚于子线程退出**。而让子线程退出的 `m_thread_pool.reset()` 在**函数体内**执行。若 `m_root` 是成员，它的析构确实在函数体之后——但那时其他成员（如 `m_loop`）也已析构，**顺序就变得依赖成员声明次序**，而这份次序本身是脆弱的、容易被后续改动打乱的隐含约定。

用显式 `free(m_root)` 写死在函数体的**最后一行**，把「它必须最晚释放」这条约束**写在了它应该待的位置**，可读性反而更好。

> **这是「RAII 并非万能」的一个真实案例**：RAII 的假设是「资源的生命周期与某个对象绑定」，而这里 `m_root` 的生命周期绑定的**不是某个对象，而是「所有子线程都退出了」这一条件**。当生命周期由外部条件决定时，显式管理 + 注释说明约束，比强行套 RAII 更诚实。
>
> 也因此，这一项在路线图里如实标注为「**部分完成**」，而不是假装完成。

## 六、关键接口与字段

| 接口 / 字段 | 位置 | 语义 | 设计要点 |
|:--|:--|:--|:--|
| `close()` | `TcpConnection` | 释放的唯一出口 | 幂等；五个触发点共用 |
| `release_fd()` | `TcpConnection` | 实际的释放动作 | 与 `close()` 分开，因为析构里不能调 `shared_from_this()` |
| `has_pending_work()` | `http_conn` | 是否还有未完成的活 | 半关闭时据此决定能不能立刻关 |
| `tie(weak_ptr)` | `Channel` | 绑定持有者弱引用 | 保护只在分派点写一处 |
| `remove_connection()` | `EventLoop` | 从注册表移除 | **延迟擦除**：投递到任务队列 |
| `m_connections` | `EventLoop` | 连接注册表，`unordered_set<shared_ptr<void>>` | 元素类型 `void` 以免事件循环依赖连接类型；只在循环线程内访问，无需加锁 |
| `m_closed` | `TcpConnection` | 幂等标志 | 多个触发点可能同轮到达 |
| `m_fd` | `TcpConnection` | 连接描述符，本对象是唯一所有者 | 释放后置为 `-1`，`-1` 兼作「已释放」标记，使 `release_fd` 可重复调用 |
| `m_timer_id` | `TcpConnection` | 定时器句柄，0 表示无 | 不用 fd 下标——fd 复用后会命中另一条连接 |
| `m_root` | `WebServer` | 站点根路径 | `strdup`/`free`，**带析构顺序约束**，见 §五 |

### 7.1 修复的缺陷

| 缺陷 | 现象 | 修法 |
|:--|:--|:--|
| **陈旧 `munmap`**（详见 [03](03-并发模型重构.md) §8） | 短连接风暴下必现的堆破坏、必崩 | 构造函数初始化 `m_file_address` 等成员 |

| **定时器按下标访问连接** | fd 复用后命中另一条连接 | 改为持 `weak_ptr` + 独立 `timer_id` |

## 八、通用知识

**C++ 对象生命周期**

- **`std::shared_ptr` / `std::weak_ptr` 的语义差别**：`weak_ptr` 不延长生命；`lock()` 是「尝试提升」，失败要处理
- **`shared_from_this()` 不能在析构函数里调用**；`enable_shared_from_this` 的适用场景
- **`weak_ptr` 的两种意图**：「回调期间保证存活」（提升并保证）与「活着才处理」（尝试并丢弃）
- **`make_shared` 之后对象地址固定**，因此对象内部的裸指针/引用保持有效——这是按值持有成员的一个实际收益
- **析构顺序**：函数体先于成员析构，成员按声明**逆序**析构；顺序约束应显式写在代码里而不是隐含在声明次序中
- **RAII 的适用边界**：当资源生命周期由**外部条件**（而非某个对象）决定时，显式管理 + 注释更合适
- **悬垂引用的两种来源**：对象已析构（use-after-free）、描述符已复用（语义错用）

**系统编程**

- **`EPOLL_CTL_DEL` 必须先于 `close(fd)`**：描述符复用是这类 bug 的根源
- **半关闭（`EPOLLRDHUP`）的语义**：只表示对端关闭**写端**，接收缓冲区里可能还有数据
- **延迟释放模式**：把「析构当前调用栈上的对象」推迟到下一轮循环，避免在回调返回前释放自己
- **fd 复用**：关闭的描述符会被内核立刻回收复用，任何以 fd 作为身份标识的设计都不安全（应改用「对象 + 句柄」）

**工程方法**

- **释放路径的唯一出口 + 幂等**：把「谁在什么情况下释放」的分散问题，变成「只需保证出口正确」的局部问题
- **验证要能构造出极端组合**：半关闭用例要用**原始套接字**构造，`curl` 会自动重连、`wrk` 不做半关闭，都看不到这类问题
- **如实标注「部分完成」**：把「决定不做」和「没做」区分开，比假装全部完成更有价值
