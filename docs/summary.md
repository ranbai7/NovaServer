# NovaServer 优化笔记

> 本文按阶段叙述这次优化**做了什么、为什么做、怎么做、效果如何**，读完即可建立完整图景。
> 逐项的细节与原始数据见 `docs/changes/`（35 份记录）；性能数据的横向对比见
> [performance.md](performance.md)；未完成项的当前状态见 [outstanding.md](outstanding.md)。

## 一、这次优化在做什么

项目起点是开源项目 [qinguoyi/TinyWebServer](https://github.com/qinguoyi/TinyWebServer)（MIT）。
它以「半同步 / 半反应堆」模型实现了一个可用的 Web 服务器，但代码中存在成体系的问题：
并发访问未保护、资源释放路径重叠、协议实现不完整、无构建与测试基础设施。

优化按 `ROADMAP` 分四个阶段推进，先梳理出 **28 项待改进问题**，分五类：

| 类别 | 项数 | 典型问题 |
|:--|--:|:--|
| 并发与生命周期 | 7 | 触发模式未生效、定时器链表无同步、释放路径重叠、忙等标志位、EMFILE 无兜底 |
| 正确性与健壮性 | 11 | 日志缓冲越界、读取返回值漏判、SQL 拼接、口令明文、固定读缓冲区 |
| 协议实现 | 3 | URL 未解码、不支持 HEAD、头部长度无校验 |
| 功能完整性 | 2 | 上传文件不可访问、上传无类型与大小约束 |
| 代码规范 | 5 | 无长度校验的字符串函数、全局 `using namespace std`、混用 `malloc`/`new` |

最终产出：**35 份变更记录**、**6397 行源码**、**7 个单元测试目标**，以及一套可复现的
性能对照数据。

## 二、阶段零 · 先量尺寸

**为什么做**：没有基线，任何优化都只能凭感觉说「变快了」。这是整个计划中性价比最高的一步——
它花掉的时间远少于后面任何一次重构，却让后面所有结论都变得可检验。

**怎么做**：用 `wrk`（`-t2 -c100 -d5s`，每组 5 次取中位数）在固定环境下测量原架构，
并把**后续对比用的四项指标**提前定死。

**结果**（`000`）：

| 指标 | 基线值 | 期望方向 |
|:--|--:|:--|
| 默认配置 QPS | 19808 | 提升 |
| P99 延迟 | 899.99 ms | 显著下降 |
| 常驻内存 | 262.8 MB | 明显下降 |
| 线程数对吞吐的影响 | 无差异（1.3% 以内） | 出现可观测的正相关 |

同时明确记录了这个测量环境的局限：4 vCPU、**客户端与服务端同机**、`wrk` 仅 2 线程。
这条自我限定在后续所有对比中都被沿用——**绝对数值不具备横向参考价值，价值在同环境的前后对比**。

## 三、阶段一 · 工程基础

**为什么做**：原项目没有构建系统、没有测试、没有 CI。在这种状态下改代码等于盲改。
本阶段的原则是「与并发架构无关的改动尽量前置」，避免在后面的架构重构中返工。

**做了什么**（11 项）：CMake 构建系统、迁移到 C++17、`clang-format` 统一格式、
编译告警治理（45 个 → 0）、不安全字符串函数替换、命名空间整理、断言与错误处理分离、
`const` 正确性、GoogleTest 单元测试、GitHub Actions CI。

**结果**：改动终于有了验证手段——`ctest` 一键跑测试，每次推送自动构建。

**留下的缺口**：「内存管理 RAII 化」标为**部分完成**。`http_conn.cpp` 中拼装 SQL 的部分
后来随参数化查询一并改掉，但 `webserver.cpp` 的站点根路径 `m_root` 仍为 `strdup`/`free`——
该指针带析构顺序约束（必须晚于线程池释放），因此以显式析构顺序而非 RAII 成员管理。

## 四、阶段二 · 正确性与协议完整性

**为什么做**：不改变核心数据结构与线程模型的前提下，先把继承来的缺陷修掉。
这一阶段的约束是「架构重构之前，能修的都先修」——否则重构时会把老缺陷一起搬过去。

**做了什么**（16 项），按性质分四类：

| 类别 | 关键项 | 问题 |
|:--|:--|:--|
| 崩溃与内存 | 日志缓冲区边界修正、读取返回值与成员初始化 | 格式化截断后仍写终止符，越过分配边界 |
| 安全 | 静态资源路径规范化、数据库访问参数化、口令加盐哈希 | 路径拼接前未做规范化与边界校验；SQL 字符串拼接；口令明文入库 |
| 协议 | URL 解码、HEAD 支持、请求头校验、状态码语义 | `%XX` 按字面处理；解析阶段直接拒绝 HEAD；超长头部无校验 |
| 功能 | 上传文件访问闭环、上传类型与大小约束 | 文件写入 `./upload/` 但静态根为 `./root/`，上传后无法通过 HTTP 查看 |

其中**路径规范化**一项的顺序不可颠倒：只加 URL 解码而不做规范化，等于新增一条绕过途径
（`%2e%2e%2f` 解码后就是 `../`），两者必须一并处理。

**一次独立核查**（`016`~`019`）：16 项落地后另做了一次独立核查，又查出 **12 项问题**，
**其中 2 处会崩溃**，分三批修复完毕。

**结果**：常驻内存 264 MB → **76 MB**（动态缓冲改造），默认 QPS 19808 → **25858**。

## 五、阶段三 · 并发模型重构

**为什么做**：这是整个计划的核心，也是唯一无法靠修补解决的部分。原架构有三个结构性问题：

1. **事件注册与连接生命周期分散在多个路径上**——同一个连接的处理在 Proactor 与 Reactor
   两条路径、主线程与工作线程之间来回切换；
2. **Reactor 路径以忙等标志位等待工作线程**，且该标志没有跨线程同步；
3. **资源释放路径重叠**——连接关闭与定时器回调都会释放同一描述符，且缺少幂等保护，
   描述符被复用后可能误操作新连接。

**怎么做**（9 项，分步推进）：

| 步骤 | 内容 |
|:--|:--|
| 抽象层 | 引入 `EventLoop` / `Channel`，把「事件源」与「事件处理」分离 |
| 定时器 | `timerfd` 替代信号驱动定时；退出信号改用 `signalfd` |
| 统一事件源 | `epoll` + `timerfd` + `eventfd` + `signalfd`——**全项目不再有信号处理函数** |
| 去忙等 | 移除忙等标志位与 `EPOLLONESHOT` |
| 生命周期 | 连接的五个关闭入口收敛到唯一出口且幂等 |
| 线程模型 | 子 Reactor 线程池落地：主线程只 `accept`，连接按轮转分配，归属线程处理其全部事件 |
| 收尾 | 删除旧架构代码、参数清理、EMFILE 兜底 |

**过程中发现并修复了两处崩溃**：连接复用时的陈旧 `munmap`（`029`）、短连接下的连接丢失（`027`），
以及 TSan 在并发场景下查出的两处数据竞争。

**结果**（同时段 A/B，见 `031`）：默认配置 QPS 25858 → **33426（+15%）**，
常驻内存 60 MB → **12.6 MB**，**线程数对吞吐从「无差异」变为显著正相关**——
说明主线程 `accept` 与子线程处理的分工真正生效了。

## 六、阶段四 · 性能优化与验证

**日志双缓冲**（`030`）：原异步实现的每行日志要取锁三次，加上写盘，代价压在调用线程上。
改造为「调用线程只把整行日志追加进线程私有缓冲，由专门的写盘线程按缓冲块（默认 64 KiB）
整块落盘」。

效果：异步写入在 `-t 2` 下 **9157 → 36209 QPS（约 4 倍）**，P99 从 22.41 ms 降到 5.79 ms；
每行日志的写系统调用降到约 **1/4.3**。同时加了**背压可见**——写盘跟不上时丢弃新行并在日志中
记下「已丢弃 N 行」，使丢失可见而非无声无息。

**性能对照**（`031`）：按阶段零的方法与重构前的基线做**同时段**对照（见第八节）。

**Sanitizer 全链路**（`032` + 阶段三的 TSan 工作）：ASan 覆盖静态资源、注册登录、上传、
退出全链路，无报告；TSan 覆盖并发场景。

**过程中查出并修复了两处问题**：登录与注册从未取过连接池连接而直接段错误
（**自初始导入即存在**，与本次改造无关）；优雅退出失效（退出码 143）——日志改为异步后暴露，
写盘线程创建早于信号屏蔽。

## 七、收口 · 全项目审核与最终复核

**为什么还要再做一次**：四个阶段都是**按事先列出的条目**推进的，条目之外的代码从未被系统检查过。
收口后做了一次覆盖**全部源码**的独立审核（`033`），查出 **8 处缺陷**，其中 7 条由本人独立复现。

最严重的一条（**A1**）是：请求行为绝对形式 URI 且无路径时**空指针解引用，一条请求即可打挂
单进程服务端**。它**继承自原项目**，四轮优化从未触及——因为没人按条目之外去逐行走一遍
请求行解析。这正是「按条目推进」的盲区。

另修：管线化请求被静默丢弃、`-p` 吞掉配置文件里的数据库端口、连接数为 0 时启动即崩溃、
连接池在锁外读链表、端口等参数缺范围校验等。

**最终复核**（`034`）：在最终 HEAD 上重跑优化前后的**同时段 A/B**，确认上述 8 处修复
**没有带来性能回退**，并顺带发现优化前的异步日志实现收到 `SIGTERM` 后完全不退出。

## 八、优化结果总览

四项指标（起点为阶段零定义）：

| 指标 | 优化前（`000`） | 优化后（`034`） | 变化 |
|:--|--:|--:|:--|
| 默认配置 QPS | 19808 | **33151** | **+67%** |
| P99 延迟 | 899.99 ms | **16.79 ms** | 降至约 1/54 |
| 常驻内存 | 262.8 MB | **12.6 MB** | **−95%** |
| 线程数对吞吐的影响 | 无差异 | `-t1` 28372 → `-t2` **48185** | 出现显著影响 |

实测最优点（`-m 0 -t 2`）为 **48185 QPS**，约为优化前基线的 **2.4 倍**。

分段演进：阶段二后 25858 QPS / 60 MB → 阶段三、四后 33426 QPS / 12.6 MB。

**代价也要说清楚**：`-m 0 -t 1` 在两次独立测量中都出现回退（−15% / −12.4%）——
新架构为每连接维护独立的定时器与事件源，单线程开销高于旧模型。这是明确的取舍，
默认的 `-t 2` 才是新架构的最优点。

## 九、这次优化沉淀下来的方法

1. **先量尺寸再动手**。阶段零的四项指标让后面所有「变快了」都可检验。
2. **同时段 A/B 是唯一可靠的对照方式**。同一份代码在不同时段测量最多差 27%，
   跨时段搬数字做对比是不成立的。`031` 与 `034` 都把优化前的代码用 `git worktree`
   重建后在同一时段背靠背测量。
3. **声明改动「没动代码」要用机械校验证明**。精简注释后，把改动前后都去掉注释并归一化
   空白再比对，差异只剩预期的那几处，才能说「一行代码都没动」。
4. **修复必须复现**。子代理或人工报出的每一条都独立复现或读代码确认过才作数；
   未经复现的线索如实转述为「未验证」，不当作结论。
5. **按条目推进有盲区**。最严重的一条缺陷是四轮优化都没碰过的——因为没人按条目之外走一遍。
   收口后补一次全项目审核是有价值的。
6. **延后承诺必须销账**。有两项曾经写「留待阶段三一并处置」，而阶段三收口时无人回收。
   阶段收口时应把「指向本阶段的延后项」列出来逐条核对，否则延后等于遗忘。
7. **区分「没做」与「决定不做」**。例如 `-o`（`opt_linger`）有意保持无效果——
   把它挪到连接描述符上会让 `l_linger = 0` 的 RST 语义生效，截断响应、破坏长连接。
   状态被**决定**才算闭环，被**遗忘**则不是。
