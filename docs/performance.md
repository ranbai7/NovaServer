## 一、测量方法与可比性

### 环境

| 项 | 值 |
|:--|:--|
| 主机 | Ubuntu 22.04 虚拟机（VMware），Intel Core i5-13500H，**4 vCPU（2 物理核 + 超线程）/ 3.8 GiB** |
| 编译 | `-O2 -DNDEBUG`（CMake `Release`） |
| 工具 | `wrk` 4.1.0，`-t2 -c100 -d5s`，每组 5 次取中位数 |
| 目标 | `http://127.0.0.1:9006/judge.html`（静态资源路径） |

### 三类对比，可比性不同

1. **同时段 A/B**（`031`、`034`）：把优化前的代码用 `git worktree` 重建，与当前代码在同一时段背靠背测量。**这是唯一可做定量结论的形式。**
2. **跨日分段对比**（`000` 与 `021` 等）：采于不同日期，含约 **±10%~27%** 的时段差异（`031` 实测同一份代码跨日可差 27%），**只能作方向性参考**。
3. **单次测量**（`024`/`027`/`029`）：用于回答「某项改动是否导致退化」，结论限定在该次测量内。

`000` 基线文档的第六节已写明本环境的四项局限：环境规模有限、**客户端与服务端同机**、`wrk` 仅 2 线程、测量期存在背景负载。

## 四、优化结果评价

### 达成的

1. **吞吐**：默认配置 +67%；实测最优点（`-m 0 -t 2`）为 48185 QPS，**约为优化前基线（19808）的 2.4 倍**。
2. **尾部延迟**：P99 从接近 1 秒降到十几毫秒量级，**这是最显著的一项**——原架构在 `-t 8` 下的 P99 长期在 800~1200 ms，说明存在严重的排队/尾延迟问题，重构后有量级上的改善。
3. **内存**：262.8 MB → 12.6 MB（−95%），且与负载无关的固定占用特征被消除。
4. **架构可扩展性**：线程数从「对吞吐无影响」变为「有明确影响」，`-t 2` 相对 `-t 1` 提升 70%——说明主线程 accept 与子线程处理的分工真正生效了。
5. **日志路径**：异步写入在 `-t 2` 下提升约 4 倍，且 P99 从 22.4 ms 降到 5.8 ms。

### 代价与倒退

1. **`-m 0 -t 1` 在两次独立测量中都出现回退**（`031` −15%，`034` −12.4%）。原因是新架构为每个连接维护独立的定时器与事件源，单线程时开销高于旧的半同步模型。**这是明确的取舍**，不是缺陷：默认的 `-t 2` 才是新架构的最优点。
2. **`-m 3 -t 8` 在 `034` 中仅 +2.0%**，落在噪声内，**不能计入收益**。
3. **`-t 8` 的 P99 反而高于旧架构**（`031` 9.670 → 14.590；`034` 9.57 → 16.79）。旧架构 `-t 8` 时 `-t` 参数实际未生效、所有连接走同一路径，其 P99 不可与新架构的同名配置直接类比。此项**需要单独解释，目前文档未给出定论**。

### 尚未解释的一处

`000` 的 **P50（0.323 ms）反而优于 `021` 的 3.690 ms**，与 P99 的改善方向相反。
一个可能的原因是 `013` 把每请求从预分配缓冲改为按需 `mmap`/`munmap`，降低了内存却增加了中位延迟（空间换时间）。
**这只是推测，尚未验证**，不应作为结论使用。

## 六、测量局限与后续建议

1. **客户端与服务端同机**是本环境最大的方法学缺陷：`wrk` 与服务端争夺同一组 CPU 核心，
   `000` 文档已指出「吞吐上限可能由客户端而非服务端决定」。**因此上表中的绝对 QPS 不具备横向参考价值**，
   其价值在于同环境的前后对比。
2. **4 vCPU（2 物理核 + 超线程）**决定了「`-t 2` 最优」这一结论有很强的环境成分，换硬件后结论会变。
3. **低成本的改进方向**：用 `taskset` 把 `wrk` 与服务端绑定到不同核心，可部分消除同机竞争；
   再进一步则需要在两台机器上分离客户端与服务端。
4. 若将来在云主机复测，应以相同脚本重跑 `021` 与当前版本，形成独立闭环的同时段 A/B，
   而不是把本文的绝对值搬过去比较。
