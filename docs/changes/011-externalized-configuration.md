# 011 · 运行配置外置

## 一、背景与动机

此前所有运行参数都写在源码里：

```cpp
// main.cpp
std::string user = "root";
std::string passwd = "123456";
std::string databasename = "yourdb";
```

```cpp
// webserver.cpp
m_connPool->init("localhost", m_user, m_passWord, m_databaseName, 3306, m_sql_num, m_close_log);
Log::get_instance()->init("./ServerLog", m_close_log, 2000, 800000, 800);
```

由此带来三个问题：

1. **换环境必须改代码并重新编译**：主机、端口、库名、口令中的任何一项变化都要动源码
2. **口令进入版本历史**：数据库口令写在源码中会随仓库一起分发，且一旦提交就难以彻底移除
3. **运行参数无法调整**：日志缓冲区大小、单文件行数、线程数上限等都固化为常量

## 二、现状分析

| 参数 | 现状 |
|:--|:--|
| 数据库主机与端口 | 硬编码为 `localhost:3306` |
| 数据库用户名、口令、库名 | 硬编码在 `main.cpp` |
| 日志目录、缓冲区大小、分行行数、队列长度 | 硬编码在 `WebServer::log_write()` |
| 站点根目录 | 由 `getcwd()` 推导后拼接 `/root` |

排查中还发现两处与日志初始化相关的问题：

- **`Log::init` 的返回值被忽略**。日志文件打开失败时 `m_fp` 保持为空，后续 `write_log` 会以空文件指针调用 `fputs`。日志是辅助设施，此时应当放弃写日志而不是影响主流程
- **日志路径的语义未落到实处**。`Log::init` 中的 `dir_name` 只截取到路径里**最后一个** `/` 之前的部分。传入 `"./ServerLog"` 时，`"./"` 是目录、`"ServerLog"` 被当作文件名，实际生成的是当前目录下的 `2026_09_27_ServerLog`——`ServerLog` 这个目录从未被使用过

此外 `Config` 中的 `LISTENTrigmode` 与 `CONNTrigmode` 两个成员被赋值但从未被读取（`WebServer` 有自己的一对成员），属于死字段。

## 三、设计方案

### 三层取值，优先级由低到高

```
内置默认值  <  配置文件  <  命令行参数
```

保留命令行的最高优先级，是为了让既有的 `./build/server -p 9007 -t 10` 用法完全不受影响；配置文件则承接那些不适合放在命令行里的取值（尤其是口令）。两者可以混用：口令放配置文件，临时换端口用 `-p` 覆盖。

实现上没有采用「先解析命令行、再让配置文件覆盖」的两遍解析（那会让文件覆盖命令行），而是让 `parse_arg` 记录**显式给出的键名**，`Config::apply` 在应用配置项时跳过这些键。

### 配置文件格式：INI 风格，不引入第三方库

```ini
[server]
port = 9006
root_dir = ./root

[database]
host = 127.0.0.1
password = "change-me"
```

支持 `[节]` 分组、`#` 与 `;` 注释、双引号包裹取值（保留首尾空白）。查找配置项时先匹配「节.键」，再匹配裸键，因此不写节名也能用。

不引入配置库的理由：只有一个配置文件、格式需求单一，引入依赖的收益不抵其成本。手写解析约 80 行，且可以完整地做单元测试。

### 未知键报错，而非静默忽略

配置文件中出现无法识别的键时**终止启动并指出键名**。

备选方案是宽松忽略（只报一条警告）。否决的理由是：`prot = 9006` 这样的拼写错误如果只是被忽略，表现就是「改了配置却没生效」——用户会反复检查取值本身，而问题在键名上。启动失败虽然更"硬"，但一次就能定位。同理，取值非整数、缺少 `=`、节缺少右括号等问题都给出**行号或键名**。

### 命令行参数拒绝非法取值

原先用 `atoi`，`-p abc` 会静默变成端口 0。改为解析失败即终止启动并打印非法取值——这类输入只可能来自误操作，没有"尽力而为"的合理语义。

### 站点根目录在启动时解析

`root_dir` 用 `realpath` 解析为规范化的绝对路径。这一步同时完成两件事：去掉 `./` 与重复的 `/`，以及**确认该目录确实存在**。若不在此处检查，配置写错时表现为「所有请求都返回 404」，定位成本高得多。

该检查发生在日志初始化之前，因此失败信息只能用 `fprintf(stderr)` 输出——这与 `003` 中 `Utils::addsig` 的处理是同一个原因：日志未初始化时不能写日志。

### `WebServer::init` 改为接收配置对象

原签名有 11 个标量参数，本次要新增 8 个（数据库主机/端口、日志目录/文件名/缓冲区/分行数/队列长度、站点根目录）。继续追加会让调用点变成一串靠位置区分的实参，容易错位。改为接收 `const Config &` 后，调用点是 `server.init(config)`，新增字段无需改动签名。

### 日志目录与初始化失败

`WebServer::log_write` 先 `mkdir` 日志目录（`Log::init` 只负责打开文件，不建目录），随后把「目录/文件名」交给 `Log::init`——此时路径中最后一个 `/` 之前的部分确实是目录，`ServerLog` 目录才真正被使用。初始化失败则把 `m_close_log` 置 1，从源头关闭日志，避免空文件指针。

`Log::write_log` 另加一道空指针检查作为兜底。

## 六、遗留问题

1. **口令仍是明文存放**：只是从源码移到了 `config.ini`，保密性依赖文件权限。支持从环境变量读取口令可以进一步缩小暴露面，未在本次实现
2. **配置不支持热加载**：修改配置需要重启进程
3. **数据库连接失败仍直接退出**：`connection_pool::init` 在任意一个连接失败时 `exit(EXIT_FAILURE)`，未做重试或降级
4. **日志目录只创建一级**：`mkdir` 不会递归建立多级路径，`log_dir` 层级较深时需预先存在
5. **配置文件不支持包含与变量引用**：多环境部署时需要各自维护完整文件
6. **`Config::parse_arg` 依赖 `getopt` 的全局状态**：同一进程内多次调用需要重置 `optind`，当前只在启动时调用一次
