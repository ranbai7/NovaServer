# 026 · 子 Reactor 线程池与连接轮转

> 本记录是**阶段三「并发模型重构」的第四批（3.4）**，承接 `024` 与 `025`。前三批把架构改成了 one loop per thread，但 loop 数仍为 1；这一批接入 `EventLoopThreadPool`，落实 `ROADMAP` 的「主线程只 accept，把新连接按轮转策略分发给若干子 Reactor 线程」。

> **状态：实现完成、功能验证通过；压测对比与 TSan 验证待补**，详见第五节。

## 一、背景与动机

`ROADMAP` 目标模型的完整表述是「主线程只负责 accept，将新连接按轮转策略分发给若干子 Reactor 线程；每个线程持有独立的 epoll 实例与事件循环」。`024` 完成了「每连接归属一个循环」，但只有一个循环——主线程既 accept 又处理所有连接。这一批补上分发。

## 二、现状分析

`024` 之后的形态：主线程在 `EventLoop::loop()` 里既接受连接又处理它们的读写。连接一多，accept 与数据处理就互相排队。

值得注意的是这一点并不只是性能问题：`ROADMAP` 里「连接的文件描述符、协议解析状态与其超时定时器全部归属所属线程」这条约定，在单循环下是**退化的**——所有连接本来就归同一个线程。只有接入线程池、连接分散到多个循环之后，这条约定才真正有约束力，`TcpConnection::close()` 那个「唯一出口 + 幂等」的设计也才真正被用到（关闭可能由定时器在子线程触发）。

## 三、设计方案

### 循环建在子线程栈上

```cpp
void EventLoopThreadPool::thread_func(int index)
{
    EventLoop loop;   // 栈上
    ...
    loop.loop();
}
```

这一点是有意的：`EventLoop` 的析构会清空待执行任务与连接注册表，而后者可能持有连接的最后一份引用。让它建在**线程自己的栈上**，析构就发生在该线程内，连接与定时器的最终释放也就在正确的线程上完成。若由主线程持有并析构，就会在那里释放别的线程的资源。

### 启动时阻塞到循环就绪

`start()` 用条件变量等到所有子线程都把自己的 `EventLoop` 填进 `m_loops` 再返回。这样调用方拿到 `next_loop()` 的指针之后不再需要同步——运行期间 `m_loops` 只读。

### 连接的建立要投递到目标线程

```cpp
    EventLoop *loop = m_thread_pool->next_loop();
    loop->run_in_loop([this, loop, connfd, peer] { ... make_shared<TcpConnection> ... });
```

`on_new_connection` 运行在主线程（acceptor 所在线程），而连接的构造必须发生在它归属的循环线程内——否则协议对象与 `Channel` 就跨越了两个线程。跨线程传递的只有描述符与对端地址这一次。

### 信号屏蔽的顺序

`block_signals` 必须在 `m_thread_pool->start()` **之前**调用。信号掩码是线程属性，子线程继承创建时的掩码；先建线程再屏蔽，那些线程就不会被屏蔽，`SIGTERM` 可能被它们按默认行为处理掉（进程直接退出，而不是走优雅退出路径）。`run()` 里这条顺序有注释标明。

## 四、实现要点

| 文件 | 改动 |
|:--|:--|
| `net/event_loop_thread_pool.{h,cpp}` | 新增：`start` / `next_loop` / `stop`，轮转用 `std::atomic<int>` |
| `webserver.{h,cpp}` | 持有线程池并在 `run()` 中启动；`on_new_connection` 改为投递到 `next_loop()`；`on_connection_closed` 去掉 `inet_ntoa`（它返回静态缓冲区，多线程下不安全） |
| `webserver.h` | 成员声明顺序调整并注明理由：析构按声明逆序，线程池应最先析构（它会 join 子线程） |
| `CMakeLists.txt` | 加入新源文件 |

`-t`（`thread_num`）从这一批起真正生效；取 0 时不建线程，全部连接归主循环（便于对照）。
