# 003 · 编译告警治理

## 一、背景与动机

阶段一引入 `-Wall -Wextra` 后暴露了 45 个告警。这些告警混杂了真实缺陷与代码清理项。在进入功能性优化之前清零，有两个作用：

1. 消除其中的真实隐患
2. 让后续新增的告警始终保持信号意义，不会被历史噪声淹没

## 二、现状分析

45 个告警（去重后 34 条，对应约 20 处代码）：

| 类型 | 数量 | 初判性质 |
|:--|--:|:--|
| `return-type` 函数缺少返回值 | 14 | 真实缺陷 |
| `unused-parameter` 未使用参数 | 8 | 清理项 |
| `stringop-truncation` 字符串截断风险 | 6 | 真实风险 |
| `unused-variable` 未使用变量 | 5 | 清理项 |
| `sign-compare` 符号比较 | 3 | 清理项 |
| `reorder` 初始化顺序 | 3 | 清理项 |
| `format-truncation` 格式化截断风险 | 3 | 真实风险 |
| `unused-result` 返回值未检查 | 1 | 真实缺陷 |
| `unused-but-set-variable` 赋值后未读取 | 1 | 真实缺陷（间接） |
| `implicit-fallthrough` 分支意外贯穿 | 1 | **真实缺陷** |

### 关键发现：两个「清理项」实为断言的副作用

`assert` 在发布构建（定义了 `NDEBUG`）下会被**完全移除**，由此产生了两个看似无害的告警：

- `webserver.cpp` 中 `ret` 被反复赋值却从未被读取 → `unused-but-set-variable`
- `lst_timer.cpp` 中 `addsig` 的 `sig` 参数失去唯一使用点 → `unused-parameter`

这暴露了以 `assert` 承担运行时校验的隐患：**校验逻辑在发布构建中会静默消失**。

## 三、设计方案

按告警性质分三类处理：

| 类别 | 处理方式 |
|:--|:--|
| 真实缺陷 | 修正逻辑 |
| 无用代码 | 删除 |
| 形式问题 | 显式标注或改写 |

### 断言与错误处理的分工

不再用 `assert` 承担运行时校验，明确划分：

- **`assert`**：仅用于「开发期才可能违反的内部不变量」，且其失效不影响正确性
- **错误分支**：用于系统调用失败等运行时错误，需在有意义的处理中体现

### 处理范围的说明

本次一并处理了几处未产生告警但属同类问题的代码（如 `websocket` 创建的断言检查、超时回调中的空指针检查），避免留下「同函数内一半改了一半没改」的不一致状态。

## 四、实现要点

### 日志模块

- `flush_log_thread` 与 `async_write_log` 补齐缺失的返回值（前者为线程入口函数，返回值无实际意义，但缺少 `return` 属于未定义行为）；未使用的参数标注 `[[maybe_unused]]`
- `log_full_name` 与 `new_log` 由 256 字节增至 512 字节，`tail` 由 16 增至 32 字节，并统一改用 `sizeof` 计算边界——原尺寸在极端输入下确实存在被截断的可能
- `dir_name` 的复制改为显式长度限制并强制写入终止符

### HTTP 模块

- 路由映射处 6 处 `strncpy(dst, src, strlen(src))` 改为 `snprintf`。原写法的**边界取决于源串长度**，编译器无法证明目标不会溢出，且不保证终止符；改写后同时移除了配套的 `malloc` / `free`
- CGI 路径拼接同样化简为一次 `snprintf`
- 发送进度判断中的有符号与无符号比较改为显式转换
- 删除 `initmysql_result` 与 `do_request` 中未使用的局部变量
- `FILE_REQUEST` 分支补充 `break`（详见下方）

### 服务器主类与线程池

- 启动路径上的 5 处 `assert` 改为错误分支，失败时记录日志并退出——原先在发布构建下这些检查会消失，绑定端口失败也不会给出任何提示
- 线程池初始化列表按成员声明顺序重新排列
- 队列长度比较改为显式转换

### 定时器模块

- 信号注册失败不再依赖 `assert`，改为输出错误信息
- 超时回调中的空指针检查移到解引用**之前**（原 `assert` 位于解引用之后，即便在开发期也无法起到保护作用）

> **为何 `Utils::addsig` 未使用 `LOG_ERROR` 宏**：该宏展开后依赖调用作用域的 `m_close_log` 成员，`Utils` 并无此成员；更关键的是当日志被关闭时 Log 单例从未初始化，其内部文件指针为空，此时写日志会崩溃。因此该处改用 `fprintf(stderr, ...)` 兜底。

## 五、验证

| 项 | 结果 |
|:--|:--|
| 编译 | 0 错误、**0 警告**（治理前为 45） |
| 产物大小 | 98 KB，与治理前一致 |
| 静态页面 | `/judge.html`、`/log.html`、`/picture.html`、`/video.html`、`/upload.html`、`/fans.html` 全部 200 |
| 路由映射 | `/0` `/1` `/5` `/6` `/7` `/8` 全部 200 |
| 数据库路径 | 登录请求正常处理 |
| 空文件响应 | 返回 200（修复前该路径异常） |

### 顺带修复的缺陷：空文件响应无法发出

`process_write` 的 `FILE_REQUEST` 分支在文件长度为 0 时，组装完响应后**缺少 `break`**，控制流直接贯穿到 `default: return false`，导致连接被关闭、响应根本发不出去。

补充 `break` 后，该路径正确落入函数末尾的公共发送逻辑。

这个缺陷正是由 `-Wimplicit-fallthrough` 暴露的——在没有开启告警的情况下它不会造成编译错误，只会表现为「访问空文件时浏览器连接被重置」，很难定位。**这是告警治理价值最直接的体现。**

## 六、遗留问题

1. **`NO_RESOURCE` 缺少响应分支**：请求不存在的文件时，`process_write` 落入 `default` 返回 false，连接被直接关闭，客户端收不到 404 响应。同时 `BAD_REQUEST` 分支当前返回的是 404 而非 400，两者归入阶段二的「状态码语义修正」一并处理。
2. **日志缓冲区写入越界**：`write_log` 中格式化截断后仍向缓冲区写入终止符，会越过分配边界。该问题依赖运行时数据，静态分析无法发现，归入阶段二的「日志缓冲区边界修正」。
3. **`-Werror` 尚未启用**：告警已清零，具备启用条件，可在搭建 CI 时一并加上。
