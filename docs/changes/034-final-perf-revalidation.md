# 034 · 在最终 HEAD 上重跑同时段 A/B 压测

> `031` 采集于 2026-09-29，而全项目审核的八处修复（`033`）是**之后**才进入代码的。
> 本文在最终 HEAD 上重跑一次优化前后的同时段对照，既复核阶段三与阶段四的累计收益，
> 也顺带回答 `031` 答不了的问题：**`033` 的八处修复有没有带来性能回退**。

## 一、背景与方法

方法与 `000` / `021` / `031` 保持一致，以便复现：

| 项 | 值 |
|:--|:--|
| 主机 / 虚拟化 | ubuntu22-virtual-machine（VMware），Intel Core i5-13500H，4 逻辑核 / 3.8 GiB |
| 编译选项 | `-O2 -DNDEBUG`（CMake `Release`） |
| 工具与参数 | `wrk` 4.1.0，`-t2 -c100 -d5s`，每组 5 次取中位数 |
| 目标 | `http://127.0.0.1:9006/judge.html` |
| 对照代码 | 旧 = `cc3bf80`（`021` 文档提交的父提交，阶段三重构之前）；新 = `7d43672`（当前 HEAD） |

「优化前」的代码用 `git worktree` 重建在本时段测量，把**时段差异**从对比中消掉——
`031` 已证明同一份代码跨时段可差 27%，直接搬旧数字比较是不成立的。

复现校验：重建出的旧二进制为 **173136 字节**，与 `021` / `031` 记录的完全一致，
确认跑的就是当年那份代码。

两处执行细节：

- **逐组合交替采集**：同一组合下「旧→新」紧邻跑完再进下一组，抵消设备的慢漂移。
- **旧代码的配置需裁剪**：旧版配置解析器对未知键会报错退出，故为其单独准备了一份
  只含它认识的键的 `config.ini`（比当前版少了 `log.batch_buf_size`、`log.flush_interval`，
  多了 `server.actor_model` 与 `log.queue_size`）。旧架构按 `031` 的做法取 `-a 0` 一列。

### B 组的数字不能读成「日志一项的收益」

`030` 的「改动前」是**新架构 + 旧日志**，它隔离出的才是日志改造单独的收益（约 4.0 倍）。

## 四、结论

1. **阶段三与阶段四的累计收益得到再次确认**：8 子 Reactor 各触发模式下吞吐 +13%~+15%，
   而**默认配置 `-t 2` 提升 +57.7%**，与 `031` 记录的 +59% 几乎一致。
2. **常驻内存降到约 1/5**：60 MB → 11.7~12.6 MB，全部组合一致。
3. **`033` 的八处修复没有带来性能回退**：本次 A 组各项与 `031`（修复前采集）逐项对齐
   （见下表），差异都在 ±10% 噪声内。
4. **日志路径的改善极大**：异步写入在最优配置下 5845 → 40061，且 P99 从 25.23 ms 降到 4.04 ms。
5. **`-m 0 -t 1` 是唯一倒退的配置**（−12.4%）。这与 `031` 记录的 −15% 一致，
   属已知取舍：新架构为每连接维护定时器与事件源，单线程时开销高于旧的半同步模型。
   **默认 `-t 2` 才是新架构的实测最优点。**

## 五、过程中的一个发现

**优化前的异步日志实现在收到 `SIGTERM` 后不退出。** B 组首轮执行时，旧代码以
`-c 0 -l 1` 启动的服务端被 `kill -TERM` 后持续存活（实测 10 秒仍未退出），
导致压测脚本 `wait` 永久阻塞。

这与 `032` 记录、并在阶段四修掉的是同一类缺陷——**写盘线程与信号处理的竞态**
（修复前的表现是退出码 143，这里是完全不退出）。本次压测对该组改用「等待 3 秒后
升级为 `SIGKILL`」的兜底，只影响关停方式，不影响被测窗口内的吞吐测量。

这一条是**顺带发现的旁证**：它说明日志改造带来的不只是吞吐，还有关停语义的正确性。
