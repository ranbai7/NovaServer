# 020 · 长连接与半关闭路径的定向验证

> 本记录不是一项既定的优化，而是进入阶段三（并发模型重构）之前补做的一轮**定向验证**。`018` 把长连接变成默认行为之后，连接复用从边缘路径变成主路径，而 `016` 第七节明确把「`ET + 长连接` 在压力下的表现」列为未覆盖项。

## 一、背景与动机

三件事叠在一起，使这条路径值得在重构前单独走一遍：

- `018` 之后，**绝大多数请求都走「复用同一连接」这条路**（此前只有显式携带 `Connection: keep-alive` 的客户端才会走到）
- `016` 的核查明确**没有覆盖** `ET + 长连接` 在压力下的表现
- 阶段三会重写连接生命周期与事件注册，届时这些验证要重做一遍——现在做，等于为重构前后各留一份对照

## 二、验证方法

工具的选择是这轮验证的关键。**curl 与 wrk 在这一类问题上都不够用**：

| 工具 | 局限 |
|:--|:--|
| curl | 遇到服务端关闭连接会自动重连，看不到「连接被关闭」；是否发送 `Expect` 随版本而异（`018` 已遇到过一次） |
| wrk | 只做「建立连接 → 请求 → 等响应」，不会半关闭，也不区分「服务端关了连接」与「响应丢了」 |

因此除压测外，一律用**原始套接字**构造请求——只有它能精确控制「同一连接上串行发 N 个请求」「发完请求即 `shutdown` 写端」这类发送方行为。

覆盖的场景与 4 种触发模式（`-m 0/1/2/3`）的组合：

| 场景 | 做法 |
|:--|:--|
| 同一连接串行多请求 | 一条连接上连续 10 轮，每轮覆盖静态页面、大文件、404、HEAD、列表页、上传、下载 |
| 并发连接 | 8 条连接，每条串行 20 个请求 |
| 压力 | `wrk -t2 -c100 -d10s`，统计 QPS、P99 与 socket 错误 |
| 空闲回收 | 建立连接、发一个请求，观察何时被回收 |
| 半关闭 | 发送请求后立即 `shutdown(SHUT_WR)`，读完整响应 |

## 三、发现的问题

四项，前两项会直接影响可用性：

### 1. `listen` 的 backlog 只有 5，突发连接建立被推迟

`listen(m_listenfd, 5)`。压测启动时 wrk 会**突发**建立 100 条连接，accept 队列随即溢出；溢出的连接需要客户端重传 SYN 才能建立，表现为请求超时。

| `-m` | QPS | P99 | timeout |
|:--|--:|--:|--:|
| 0（LT+LT） | 24188 | 10.9 ms | 0 |
| 1（LT+ET） | 26252 | 5.4 ms | 0 |
| 2（ET+LT） | 21616 | **336.4 ms** | **10** |
| 3（ET+ET） | 22441 | **373.7 ms** | **9** |

监听侧为 LT 时看不出来（每次可读事件紧接一次 accept，队列排空更细碎而持续），监听侧为 ET 时放大成超时。把 backlog 改为 512 后同条件下 timeout 归零。

### 2. `EPOLLRDHUP` 排在读写之前，半关闭时请求被丢弃

`eventLoop` 的分支顺序是 `EPOLLRDHUP | EPOLLHUP | EPOLLERR` → `EPOLLIN` → `EPOLLOUT`。而对端半关闭时，事件通常**同时**带 `EPOLLIN`（缓冲区还有请求）与 `EPOLLRDHUP`（对端关了写端）。先命中关闭分支，于是客户端「发完请求就 `shutdown` 写端」时：

- 请求被丢弃，从未被处理
- 因接收缓冲区尚有未读数据，`close` 让内核发出的是 **RST**（客户端看到 `ConnectionResetError`）

### 3. ET 读循环在 `recv` 返回 0 时丢弃本次已读到的数据

```cpp
            else if (bytes_read == 0)
            {
                return false;   // 对端已关闭
            }
```

ET 循环一直读到 `EAGAIN` 才停，而「发完请求就关写端」的客户端会让这次循环以 `recv` 返回 0 收尾——此时缓冲区里正躺着刚收到的请求，`return false` 却让调用方关闭了连接。

### 4. `EPOLLONESHOT` 未被重新激活，大文件发送卡在半途

前三项修掉之后暴露出来的。现象：半关闭下下载 5 MiB 文件，**约一半的轮次**读到 2614080 字节（恰好一半）后卡死。

根因在 ONESHOT 与事件的交互：响应发送到一半时发送缓冲填满，`EPOLLOUT` 不置位，而 `EPOLLRDHUP` 置位（对端已半关闭）——这个事件被「半关闭」分支消费掉，ONESHOT 随之失效。此后发送缓冲腾空也不会有人再激活该 fd，连接永久卡住。

### 附带：`accept` 把正常的 `EAGAIN` 记成 ERROR

ET 循环每次取完待处理连接都会以 `EAGAIN` 收尾，而那时会写一条 `accept error:errno is:11`。单次 10 秒压测产生 17 条——在同步日志模式下这是一批纯浪费的写盘。

## 四、修复

| 位置 | 改动 |
|:--|:--|
| `webserver.cpp` `eventListen` | `listen` 的 backlog 由 5 改为 512 |
| `webserver.cpp` `eventLoop` | 分支顺序调整为 `EPOLLIN` → `EPOLLOUT` → `EPOLLRDHUP/EPOLLHUP/EPOLLERR`，且最后一个分支不再无条件关闭 |
| `http/http_conn.h/.cpp` | 新增 `rearm_epoll()`：有待发完的响应则重新关注可写；请求已读完、响应尚未生成则告知调用方「还不能关」；两者皆无才返回 false |
| `http/http_conn.cpp` `read_once` | ET 分支 `recv` 返回 0 时改为 `return m_read_idx > 0`——缓冲区非空说明本次读到了数据，要先交给上层处理 |
| `webserver.cpp` `dealclientdata` | 两个分支都只在非 `EAGAIN` 时记录错误；ET 分支另外对 `EINTR` / `ECONNABORTED` 重试 |

关闭判断收敛为一处：`rearm_epoll()` 返回 false 才关闭。这样「请求已读完待处理」「响应已生成待发送」两种进行中的状态都不会被半关闭事件打断。

## 六、遗留问题

1. **半关闭只保证「响应能发出」，不保证连接优雅收尾**：响应发完后连接会由读路径关闭（`recv` 返回 0）。这一路径已覆盖，但「对端半关闭且本端还有未读数据」的极端组合未单独构造用例
2. **backlog 的取值没有做压力扫描**：512 是常见默认量级，本轮只验证了「5 太小、512 足够」，未寻找拐点
3. **`-o`（`opt_linger`）仍施加在监听描述符上**：`SO_LINGER` 语义上属于连接描述符，挪过去会让 `-o 1` 从「几乎无效果」变成「连接被 RST 掉」，属行为变化，留待阶段三一并处置
4. **本轮验证的是当前的 Proactor 与 Reactor 两种模式**：阶段三会移除这两种模式（连接的所有处理都归属其所属线程），届时本轮的全部用例都需要在新架构上重跑一遍
