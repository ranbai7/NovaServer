# 012 · 口令加盐哈希

## 一、背景与动机

此前口令以明文保存在 `user` 表中，登录时直接用 `==` 比对。库中一旦泄露（备份泄露、只读账号被滥用、日志或快照被带走），所有账号的口令立即可用；由于用户普遍复用口令，影响会扩散到其他系统。

本次把存储形式改为**加盐哈希**，并处理既有明文数据的迁移。

## 二、现状分析

```cpp
// 注册
strcat(sql_insert, password);          // 明文入库
users.insert(std::pair<std::string, std::string>(name, password));

// 登录
if (lookup_user(name, stored) && stored == password)   // 明文比对
```

三处问题：

1. **明文存储**：口令与用户名的保护级别相同，任何能读表的人都能直接获得口令
2. **无盐**：即便换成哈希，相同口令也会产生相同散列，彩虹表与「一次破解、多处复用」依然有效
3. **列宽不足**：`passwd` 为 `char(50)`，哈希串比明文长，直接改哈希会写入失败

## 三、设计方案

### 算法：PBKDF2-HMAC-SHA256

| 参数 | 取值 | 理由 |
|:--|:--|:--|
| 算法 | PBKDF2-HMAC-SHA256 | 专门为口令设计的慢哈希，OpenSSL 原生提供 |
| 迭代次数 | 100000 | 把单次校验抬到几十毫秒量级，足以让离线穷举不可行 |
| 盐 | 每条 16 字节随机数 | 相同口令在库中呈现不同散列 |
| 推导长度 | 32 字节 | SHA-256 的输出长度 |

存储格式为 `算法$迭代次数$盐$散列`，字段以 `$` 分隔（base64 字母表中不含 `$`，按它切分是安全的）。

**把迭代次数写进记录**是这里的关键设计：日后若要提高代价参数，只需改常量，既有记录仍按各自记录的次数校验，无需一次性重算全表。

备选方案是系统 `crypt_r`（`$6$` SHA-512）。它的优点是不引入源码依赖，但盐长与迭代次数由系统约定，可调性差，且不同 libc 的实现存在差异。既然构建已经依赖 MySQL 客户端库，再引入 OpenSSL 不增加部署复杂度，因此选择参数完全可控的 PBKDF2。

### 校验：定长比较

推导出的散列与实际存储的散列用 `CRYPTO_memcmp` 比较，不因首个不同字节而提前返回。这样比较耗时与匹配前缀长度无关。

存储值不是本模块的编码格式时一律返回 `false`——**明文记录不能被判为匹配**，这一点在单元测试中单独固化。

### 迁移：启动时一次性升级

被选定的方案是启动时自动升级，理由是不必人工介入，且升级完成后库中不再留存明文。

启动流程：

```
加载用户表
  ├─ 确保 passwd 列足够宽（不足则 ALTER）
  └─ 逐行检查
       ├─ 已是哈希 → 直接载入内存
       └─ 仍是明文 → 计算哈希 → UPDATE 回库 → 载入内存
```

两点值得说明：

- **列宽自动加宽**。旧表的 `char(50)` 存不下哈希串，若不处理，失败会推迟到注册或迁移写入时才暴露。因此先查 `information_schema` 确认列宽，不足则 `ALTER TABLE user MODIFY passwd VARCHAR(255)`
- **迁移失败即终止启动**。若某个账号的升级失败却继续运行，该账号会带着明文留在内存里而校验永远不通过，表现为「口令正确却登录失败」——这比启动失败更难定位。因此迁移中的任何失败都直接终止并输出原因

### 失败信息写标准错误

启动期的致命错误用 `fprintf(stderr, ...)` 而非 `LOG_ERROR`：日志开关可能被关闭（`-c 1`），此前 `Utils::addsig` 也因同样原因改用标准错误。

### 绑参样板的消除

本次新增了「按用户名更新口令」这条写语句，若继续手写 `MYSQL_BIND` 数组，三处绑定代码会各自维护一份长度变量。抽出 `StringBinder`（持有绑定数组与长度变量，避免 `MYSQL_BIND::length` 指向临时变量）与 `execute_two_params`，两处调用点各缩短为一行。

## 六、遗留问题

1. **迁移代价与记录数成正比**：每条明文记录都要做一次 PBKDF2 推导，且迁移在监听之前同步完成。实测约 52ms/行，一万条记录意味着约 9 分钟的启动延迟。记录数较多时应改为**按需迁移**（登录时发现明文则校验后升级该行），代价是明文在库中留存更久；本次按「启动后不再留存明文」的取舍选择前者
2. **迁移期间服务不可用**：进程在完成迁移前不监听端口。若需消除停机，应把迁移放到独立进程中先行执行
3. **口令复杂度与长度未做校验**：服务端不限制口令的强度或长度。需要说明的是它也不受 `passwd` 列宽的约束——入库存的是约 90 字符的编码串（算法、迭代次数、盐与散列），口令本身从不写入该列。本记录最初写作「仅受列宽 255 的约束」，`016` 的核查指出该表述不准确
4. **无口令修改与重置流程**：当前只有注册与登录两条路径
5. **登录失败无频次限制**：不存在针对同一账号或同一来源的尝试次数限制，在线暴力破解未被遏制
6. **迁移需要 DDL 权限**：`ALTER TABLE` 要求账号具备建表权限。若部署账号只有读写权限，需由运维预先执行 README 中的建表语句
7. **PBKDF2 参数未随硬件调整**：100000 次迭代是当前取值，未做基于实测耗时的自动标定
