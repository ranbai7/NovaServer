# 009 · URL 解码与静态资源路径规范化

## 一、背景与动机

路线图把「URL 未解码」（问题 19）与「静态资源路径未规范化」（问题 12）列为两个独立条目，前者属于协议完整性，后者属于健壮性。实际排查后发现后者并非单纯的处理不完善，而是**可被直接利用的任意文件读取**：

```
$ curl --path-as-is http://127.0.0.1:9083/../../../../../etc/passwd
root:x:0:0:root:/root:/bin/bash
daemon:x:1:1:daemon:/usr/sbin:/usr/sbin/nologin
...
```

因此这两项必须一并处理，且**顺序不可颠倒**：只加入 URL 解码而不做规范化，等于新增一条绕过途径——`%2e%2e%2f` 解码后就是 `../`。

## 二、现状分析

### 路径直接拼接，未做任何规范化

```cpp
strcpy(m_real_file, doc_root);
int len = strlen(doc_root);
...
snprintf(m_real_file + len, FILENAME_LEN - len, "%s", m_url);
```

`m_real_file = doc_root + m_url`，而 `m_url` 自请求行原样取出后只做了一项检查：首字符必须是 `/`。`..` 段不会被视为特殊含义，一路进入 `stat` 与 `open`，由内核完成路径解析——于是「文档根目录」这层约束在系统调用里被自然消解。

实测（修复前）：

| 请求 | 结果 |
|:--|:--|
| `/../CMakeLists.txt` | **200**，返回项目根目录下的文件 |
| `/../../../../../etc/passwd` | **200**，返回系统文件内容 |
| `/../root/judge.html` | **200**，穿越后再迂回根目录 |

`S_IROTH` 检查（要求文件对 other 可读）不能提供任何保护：`/etc/passwd` 恰好是 0644。

### URL 未解码

`%XX` 序列按字面处理，含转义字符或非 ASCII 的路径无法命中真实文件。这一方面限制了可用性，另一方面也意味着**解码一旦引入，规范化的缺失就会立刻变成新的攻击面**。

## 三、设计方案

### 处理顺序：先解码，再规范化

```
请求行原样 → decode(%XX) → 校验无 %00 → normalize(., ..) → 越界则拒绝 → 进入路由与文件拼接
```

规范化必须作用于**最终形态的路径**。若先规范化再解码，`%2e%2e` 在规范化阶段只是一个普通的名字（不含 `..`），会被放行，随后解码才还原成 `..`——判断与使用之间出现偏差。这条顺序约束在单元测试中以反例形式固定下来。

### 规范化：越界即拒绝，而非静默钳制

`normalize_path` 逐段处理：空段（重复的 `/`）与 `.` 段丢弃，`..` 段回退上一级；**若回退的层数超过已有一层级，返回空串表示越界**。

备选方案是把越界钳制在根目录，即 `/../x` 视作 `/x`。选择拒绝的理由是：这类请求不是「写法冗余」，而是试图访问根目录之外，静默改写会掩盖异常输入，也让抓取扫描行为变得不可见。规范化后路径不再含 `..` 段，`doc_root + 规范化路径` 就必然落在根目录内，无需再依赖运行时的路径比对。

### `%00` 直接拒绝

解码 `%00` 会得到一个字符串结束符。路径随后要参与 `strlen`、`strcat` 与文件拼接，含结束符的内容会在那些地方被截断，使实际处理的路径短于判断时的对象。这类「判断与使用不一致」正是绕过检查的常见来源，因此在解码后立即拒绝。

### 抽取为可单测的头文件

`decode` 与 `normalize_path` 是无状态的纯函数，移入新增的 `http/url_codec.h`（`namespace url_codec`）。这样做的直接收益是**安全边界逻辑有了单元测试**：端到端测试很难穷举「编码 × 穿越 × 迂回」的输入组合，而这些正是这类逻辑最容易出错的地方。

同时 `http_conn.cpp` 中的表单解析与路径处理共用同一份 `decode`——两处此前各自实现，`plus_as_space` 开关区分了「表单里 `+` 是空格」与「路径里 `+` 是字面量」两种约定。

## 四、实现要点

| 文件 | 改动 |
|:--|:--|
| `http/url_codec.h`（新增） | `hex_value` / `decode(in, plus_as_space)` / `normalize_path`，均为内联纯函数 |
| `http/http_conn.cpp` | 删除本地 `hex_value`/`url_decode`，改用 `url_codec`；`parse_request_line` 在路由判定前完成解码与规范化，并拒绝越界路径与 `%00`；新增 `overwrite_url` 把变换结果就地写回读缓冲区 |
| `tests/test_url_codec.cpp`（新增） | 10 组用例，覆盖解码的合法与畸形输入、规范化的可解析与越界输入，以及顺序颠倒的反例 |
| `tests/CMakeLists.txt` | 新增 `url_codec_tests` 目标 |

`m_url` 仍是指向读缓冲区的 `char *`（下游多处依赖 `strcpy(m_url, ...)` 改写它），因此变换结果直接写回原位置。解码与规范化都只会缩短路径，就地写回不会越过原占用的空间。

## 五、验证

### 单元测试

`url_codec_tests` 共 10 组用例、30 余条断言：

| 组 | 覆盖内容 |
|:--|:--|
| 解码 | 明文不变、`%XX` 与大小写十六进制、`%25` 自指、畸形转义（`%ZZ` / 结尾不完整）按字面保留、`+` 在两种约定下的差异 |
| 规范化 | 规范路径不变、空段与 `.` 段折叠、根内回退、越界拒绝、`....` 与 `..hidden` 这类合法名字不被误判 |
| 顺序约束 | 固化反例：先规范化后解码时，`/%2e%2e/%2e%2e/etc/passwd` 会以 `/../../etc/passwd` 的形式被放行 |

第 10 组用例直接断言了错误顺序下的后果，使「先解码后规范化」这一约定有回归保护。

### 端到端：越界与正常访问

| 组 | 用例 | 结果 |
|:--|:--|:--|
| 明文穿越 | `/../CMakeLists.txt`、多级穿越读 `/etc/passwd`、穿越后迂回根目录 | 全部拦截 |
| 编码穿越 | `%2e%2e`、`..%2f` 混合编码、`%00` 截断、编码后迂回 | 全部拦截 |
| 规范化后正常访问 | `/.`、`//`、`/a/../judge.html`、`/%6au%64ge.html`、`/`、静态图片 | 全部 200 |

拦截的判定不只看状态码，同时校验响应体中**不包含**目标文件的特征内容（如 `/etc/passwd` 的 `root:x:0:0`）。

## 六、遗留问题

1. **拦截后的状态码为 404**：越界路径判为 `BAD_REQUEST`，而 `process_write` 的 `BAD_REQUEST` 分支返回的是 404 与「文件未找到」文案，与实际语义不符。归入下一项「状态码语义修正」
2. **符号链接未处理**：规范化只消除了 `..`，若根目录内存在指向外部的符号链接，仍会被跟随。当前 `root/` 下没有符号链接，且上传目录不在根目录内，攻击者无法在其中创建文件，故未引入 `realpath` 比对；若后续允许向根目录写入，需要补上
3. **未处理查询串**：请求 `/judge.html?x=1` 会把 `?x=1` 当作文件名的一部分，返回 404。项目页面不产生查询串，本次未处理
4. **无静态资源扩展名限制**：根目录内任意可读文件都可下载。对静态站点属预期行为，若需收紧应在配置中给出允许的类型
5. **路径长度上限仍为固定值**：`m_real_file` 为 200 字节，超长路径会被 `snprintf` 截断，截断后可能指向另一个文件。与动态缓冲改造一并考虑
