# 033 · 全项目审核发现的缺陷与修复

> 优化路线图的四个阶段收口后，对全部源码做了一次独立审核。本文记录查出的缺陷、
> 修复方式与验证，并修正 `ROADMAP` 中因此需要下调的一项状态。

## 一、背景与方法

路线图各阶段都是**按事先列出的条目**推进的，条目之外的代码从未被系统检查过。
阶段四结束、项目对外可见之前，做了一次覆盖全部源码的审核，分三个方向并行：
HTTP 协议层、网络事件层、其余模块（日志/配置/认证/连接池/构建/测试），
外加一份「README 与 ROADMAP 声称的功能是否真的实现」的逐条核对。

审核本身也产出结论：**核心并发设计经得起逐路径推敲**——五个关闭入口确实汇聚到唯一
出口且幂等、`Channel::tie` 的弱引用保护在所有回调路径上成立、`EPOLL_CTL_DEL` 恒先于
`close(fd)`、读写方向互斥因而不存在跨连接写坏、跨线程唤醒无丢失、退出顺序与成员逆序
一致、依赖图为 DAG。声明的功能逐条都有对应实现，**没有虚报**。

下面是查出的缺陷。每条都给出了触发条件，其中 7 条由本文作者**独立复现**（不是转述）。

## 二、修复清单

| 编号 | 问题 | 触发条件 | 修法 |
|:--|:--|:--|:--|
| A1 | 绝对形式 URI 且无路径时**空指针解引用**，服务端崩溃 | `GET http://example.com HTTP/1.1` | 两处 `strchr` 的返回值就地判空（原先的判空在两次比较**之后**，形同虚设） |
| D2 | `pool_size` / `-s` 为 0 时**启动即段错误** | `-s 0` | 启动阶段校验连接数不小于 1 |
| D1 | `-p` 会**吞掉**配置文件里的 `[database] port` | 配置文件写非默认数据库端口，同时命令行给 `-p` | `m_cli_keys` 改存「节名.键名」，不再用裸键名 |
| A2 | 管线化请求被**静默丢弃** | 一个 TCP 段里先后发两个完整请求 | `reset()` 保留已完整解析后剩余的字节，写完后继续处理 |
| D4 | 端口/关闭方式等**无范围校验** | `-p 74542`（截断后绑到 9006）、`-o 5`（静默忽略） | 启动阶段逐项校验，越界即终止 |
| D3 | 连接池 `GetConnection` **锁外**读 `connList` | 多线程并发借还连接 | 读取移入锁内；取不到时把信号量还回去 |
| A3 | `write()` 部分写时 `iov_len` **重复扣减累计值** | 头部段连续两次部分写 | 改为按本次写出的字节推进（`-= temp`） |
| N1 | `next_loop()` 返回的子循环指针**无存活校验** | 子循环因 `epoll_wait` 致命错误先退出 | 判空后退回主循环继续服务 |

### A1 与 A2 值得多说一句

两者都**继承自原项目**（初始导入时就是这个写法，四轮优化从未改过它们）——这正是
「按条目推进」的盲区：ROADMAP 关注的是架构与工程基础，没人去逐行走一遍请求行解析。

**A1 的严重性最高**：无需认证、一条请求即可打挂单进程服务端。它也是最能说明「判空
写在正确的位置上」这句常识的一条——原代码有 `if (!m_url || ...)` 的判空，但它在两次
`strncasecmp` **之后**，而比较本身就会解引用。

**A2 的修法上有一个必须绕开的坑**：`reset()` 保留剩余字节后，畸形请求会让游标停在
原处，于是同一段被反复重解析，形成 400 无限循环。因此保留了「本次是否已完整解析出
一个请求」这个标志（在 `do_request()` 入口处置位）：只有解析成功的请求之后才敢保留
剩余字节，解析失败的整段丢弃——那里本来也无法重新同步。

## 三、验证

### 逐条复现（修复前 → 修复后）

| 编号 | 修复前（实测） | 修复后（实测） |
|:--|:--|:--|
| A1 | `GET http://example.com HTTP/1.1` → **段错误，退出码 139** | 返回 `400 Bad Request`，服务端存活；带路径的绝对形式仍返回 200 |
| A2 | 管线化两个请求 → **只收到 1 个响应** | 收到 **2 个响应** |
| D2 | `-s 0` → **段错误，退出码 139** | 报「数据库连接数非法: 0（须不小于 1）」，退出码 1 |
| D1 | 配置写 3333，带 `-p` → **静默改回 3306 并正常启动** | 按 3333 连接失败并退出（配置生效了） |
| D4 | `-p 74542` → 静默绑到 9006；`-o 5` → 静默忽略 | 两者均报错并终止 |
| A3 | 代码逻辑确认（窗口窄，未复现） | 按本次字节数推进 |
| N1 | 代码逻辑确认（未构造致命错误） | 判空后回退主循环 |
| D3 | 代码确认（锁外读 `std::list`） | 读取移入锁内 |

### 回归

| 项 | 结果 |
|:--|:--|
| Release / ASan 构建 | 零告警 |
| ctest（两套） | 7/7 目标全过 |
| 功能冒烟 | 18/18 通过 |
| `SIGTERM` 优雅退出 | 退出码 0 |
| 畸形请求连发 | 无循环，服务端存活，后续正常请求仍为 200 |

A2 的修复额外验证了「**修复本身不能引入新问题**」：畸形请求连发三次后服务端仍正常，
说明针对 400 循环加的那道判断有效。

## 四、状态修正

`ROADMAP` 中「参数解析健壮化」原标为**已完成**，但 D1（`-p` 吞掉数据库端口）、
D2（连接数为 0 时崩溃）、D4（多个配置项无范围校验）说明该项仍有缺口。
**本次补齐后维持「已完成」**，并在该项备注中记录这次审核的发现。

## 五、遗留

审核还转述了一批**未经复现**的线索，本次未处理，按性质分两类：

1. **边界与协议完备性**：上传列表页超过 64KB 时整个响应失败；文件长度经 `int` 传递
   （>2GB 静态文件会截断）；未处理 `Transfer-Encoding: chunked`；`boundary` 解析对
   尾随参数脆弱；上传落盘失败会残留半截文件；`mmap` 与访问之间的 TOCTOU。
2. **结构清理**：`lock/locker.h` 的 `cond` 类、`connection_pool::GetFreeConn()`、
   `LogConfig::close_log`、`Channel::m_revents`、`TcpConnection::fd()/peer()` 等死代码；
   `sem` 的隐式拷贝赋值；`http_conn.cpp` 1705 行职责混杂。

这些都不影响当前可用性，留待需要时处理。
