# 015 · 上传闭环与上传约束

## 一、背景与动机

上传功能是二次开发时新增的，但只做了一半：文件能存进来，却取不出去，且几乎不做约束。路线图把它记为两条：

| 项 | 现状 | 方向 |
|:--|:--|:--|
| 上传闭环 | 文件写入 `./upload/`，而静态资源根目录是 `./root/` | 增加上传文件的访问路由与列表展示 |
| 上传约束 | 仅有路径分隔符剥离 | 增加扩展名白名单与体积上限 |

## 二、现状分析

### 存得进去，取不出来

上传的文件落在 `./upload/`，而静态资源只从 `./root/`（站点根目录）提供，且没有任何路由指向上传目录。于是上传后唯一能看到文件的方式是登录服务器查看文件系统——**「上传成功」的页面成了一个没有出口的终点**。

### 约束只有一条

```cpp
    // 安全处理：只保留文件名，丢弃路径
    size_t slash = m_file_name.find_last_of("/\\");
    if (slash != std::string::npos)
        m_file_name = m_file_name.substr(slash + 1);
```

只剥离了路径分隔符，其余不加限制：

- **类型不限**：`.html`、`.svg`、`.js` 等可携带脚本的内容同样可以落盘
- **体积间接受限**：仅受请求体上限（8 MiB）约束，而上传并没有自己的上限

### 空文件被拒绝

```cpp
    if (m_file_content.empty())
        return BAD_REQUEST;
```

0 字节的文件是合法的上传内容，这里却被判为错误请求。

### 顺带发现：文件映射缺少返回值检查

```cpp
    int fd = open(m_real_file, O_RDONLY);
    m_file_address = (char *)mmap(0, m_file_stat.st_size, PROT_READ, MAP_PRIVATE, fd, 0);
    close(fd);
```

两处问题：`mmap` 的返回值不检查（失败时返回 `MAP_FAILED`，随后 `unmap` 会以它调用 `munmap`）；且对 0 字节文件也调用 `mmap`——长度为 0 的映射必然失败。上传闭环会让 0 字节文件变得常见（允许空文件上传后即可被下载），因此一并修正。

## 三、设计方案

### 访问路由

| 请求 | 行为 |
|:--|:--|
| `POST /upload` | 上传（既有） |
| `GET /upload` | 列出已上传文件：名称、大小、下载链接 |
| `GET /upload/<名称>` | 返回该文件 |

名称限定为**单一段落**：非空、不是 `.` 或 `..`、不含 `/`。加上解析阶段的路径规范化（`009`），两条约束共同保证访问只落在上传目录内。

### 一律按附件下载

上传内容一律附带 `Content-Disposition: attachment`，即由浏览器下载而不是就地渲染。

理由是**存储型 XSS**：上传内容来自任何能访问服务端的人，而 `.html`、`.svg` 一类内容被就地渲染时，其中的脚本会在站点同源下执行。把「可安全内联渲染」做成类型清单（图片、视频、纯文本）也说得通，但那份清单需要随浏览器行为维护，而统一按附件下载的规则更简单，也不会因为将来放开某个新类型而失效。代价是图片等本可内联查看的类型也变成下载，列表页因此承担了「查看已上传内容」的入口职责。

### 扩展名白名单与体积上限

白名单显式列出接受的类型（图片、视频、音频、纯文本、PDF、ZIP），**显式排除超文本与脚本**。体积上限取 4 MiB，小于请求体上限 8 MiB——留出边界串、头部与表单字段的开销。两者都在落盘之前校验：

| 情形 | 响应 |
|:--|:--|
| 扩展名不在白名单 | 415 `Unsupported Media Type` |
| 体积超过上限 | 413 `Request Entity Too Large` |
| 缺少文件名 | 400 |

### 列表页的两个转义

文件名来自用户，在列表页中出现两次，两处都需要转义：

- **HTML 转义**：文件名中的 `<`、`>` 等若原样输出，会被当作页面结构。转义后 `nova-<b>.txt` 显示为 `nova-&lt;b&gt;.txt`
- **URL 转义**：链接中的文件名若含 `?`、`#`、`%` 等字符，会改变链接的指向。转义后链接与文件名一一对应

## 六、遗留问题

1. **上传目录硬编码为 `./upload`**：与已外置的站点根目录、日志目录不一致，应一并纳入配置文件
2. **同名上传直接覆盖**：没有版本、时间戳或去重，两次上传同名文件会互相覆盖
3. **上传与列表均无鉴权**：任何人都可以上传、列举、下载。项目本身没有会话机制，若要做成多用户站点需先补齐身份识别
4. **无配额与清理**：不限制单用户可占用的总量，也没有过期回收
5. **两个上限的先后关系靠注释约束**：`MAX_UPLOAD_SIZE` 必须小于 `MAX_REQUEST_SIZE`，当前只是注释说明，未用 `static_assert` 固定
6. **列表页无分页**：目录中文件很多时会生成很长的页面，且单页正文受写缓冲上限（64 KiB）约束
7. **扩展名白名单基于名称而非内容**：文件名可以伪装——把脚本内容命名为 `.txt` 即可上传。由于一律按附件下载，风险被限制在「用户下载了自己上传的文件」，但若将来改为内联渲染，就需要按内容嗅探类型
