# 008 · 登录注册链路：请求体解析与数据库写入加固

## 一、背景与动机

登录与注册是服务端仅有的两条写入数据库的路径，也是唯一直接消费请求体内容的路径。原实现对请求体的解析建立在**一组固定偏移假设**之上，并为写库拼接 SQL 字符串。这套写法在「浏览器表单按预期提交」的前提下可以工作，但它把正确性寄托在输入的形状上，而不是由代码保证。

本次处理路线图中的两项：

| 项 | 现状 | 方向 |
|:--|:--|:--|
| 参数解析（问题 15） | 按固定下标提取字段，缺少边界校验 | 改为通用键值解析 |
| 数据库访问（问题 13） | 字符串拼接构造查询 | 改用预处理语句绑参 |

这两项落在同一段代码上，合并处理可以避免对同一处逻辑改动两次。

## 二、现状分析

### 请求体解析依赖固定偏移

```cpp
char name[100], password[100];
int i;
for (i = 5; m_string[i] != '&'; ++i)   // 假定请求体以 "user=" 开头
    name[i - 5] = m_string[i];
name[i - 5] = '\0';

int j = 0;
for (i = i + 10; m_string[i] != '\0'; ++i, ++j)  // 假定紧接着是 "&password="
    password[j] = m_string[i];
password[j] = '\0';
```

三处问题：

1. **下标 5 与 10 是对字段名的硬编码**。字段名、字段顺序或分隔符形态一旦变化，提取到的就是错误内容。多一个字段、少一个字段都会静默地产生错误数据，而不是报错
2. **循环没有边界**。`m_string[i] != '&'` 只以「找到 `&`」为终止条件，`m_string` 的结束符并不保证中途出现 `&`。请求体为 `user=alice` 时，循环会越过请求体末尾继续向后读，并在 `name[i - 5]` 上持续写入
3. **目标缓冲区没有长度校验**。`name` 与 `password` 是 100 字节的栈数组，`user=` 之后的内容只要超过 100 字节就越界写。请求体本身可达 2 KB，构造超长字段很容易

第 2、3 点都是内存越界，且写入的是栈上的局部数组。这类缺陷在正常运行时不表现为错误响应，只表现为难以复现的崩溃或数据损坏。

### SQL 由字符串拼接构造

```cpp
char *sql_insert = (char *)malloc(sizeof(char) * 200);
strcpy(sql_insert, "INSERT INTO user(username, passwd) VALUES(");
strcat(sql_insert, "'");
strcat(sql_insert, name);
...
```

除注入问题外，`malloc(200)` 与无长度约束的 `strcat` 组合本身就构成堆溢出风险——用户名与口令的长度之和超过缓冲区后即越界写。

## 三、设计方案

### 以通用键值解析取代固定偏移

按 `application/x-www-form-urlencoded` 的既有约定解析：

- 字段之间以 `&` 分隔
- 键与值以**第一个** `=` 分隔（值中允许出现 `=`）
- 字段名与值中的 `%XX` 转义需要解码；值中的 `+` 还原为空格

拆成三个纯函数：`hex_value`、`url_decode`、`parse_form_body`。解析结果放入 `std::map`，调用方按字段名取值，字段顺序、多余字段、缺失字段都不再影响正确性——缺失字段表现为 `find` 失败，进而判为错误请求，而不是读到越界内容。

长度问题随之消失：解析全程在 `std::string` 上完成，不经过任何固定大小的缓冲区。

`url_decode` 带一个 `plus_as_space` 开关。表单请求体与查询串的约定是把 `+` 视为空格，而**路径中的 `+` 是字面量**，不能一并还原——后续的 URL 路径解码会以 `false` 复用同一个函数。

### 以预处理语句取代 SQL 拼接

`mysql_stmt_prepare` + `mysql_stmt_bind_param` + `mysql_stmt_execute`：

```cpp
static const char kInsertSql[] = "INSERT INTO user(username, passwd) VALUES(?, ?)";
```

用户名与口令作为绑定参数传入，不参与 SQL 文本构造，注入与缓冲区溢出两个问题一并消除。

备选方案是 `mysql_real_escape_string` 转义后继续用 `mysql_query`。它的代码量更少，但转义正确性依赖字符集设置，且拼接本身仍然存在；本项目只需参数化一条语句，预处理语句的代价可以接受。

### 返回三态以区分「重名」与「失败」

原实现的 `register_user` 用一个 `bool` 同时表示「用户已存在」和「写库失败」，调用方无法区分。改为：

```cpp
enum class RegisterResult { kInserted, kDuplicate, kFailed };
```

只有 `kFailed` 才记录数据库错误信息，避免把正常的重名注册也记成故障。

## 四、实现要点

改动集中在 `http/http_conn.cpp`：

| 位置 | 改动 |
|:--|:--|
| 匿名命名空间 | 新增 `hex_value` / `url_decode` / `parse_form_body`；`register_user` 改为预处理语句绑参，返回 `RegisterResult` |
| `do_request` 的 CGI 分支 | 删除两处固定偏移循环与 `malloc` 拼接的 SQL，改为 `parse_form_body` + 按字段名取值；缺失字段或用户名为空判为 `BAD_REQUEST` |

调用方由「按位置取内容」变为「按名字取字段」，解析与字段语义的耦合被拆开。

## 五、验证

### 边界用例：畸形与超长请求体

新增用例脚本，按输入形态分四组，每组断言响应状态码或落点页面：

| 组 | 输入 | 结果 |
|:--|:--|:--|
| 字段缺失/畸形 | 无 `&`、无 `=`、只有 `user`、只有 `password`、`user` 为空、空请求体 | 全部判为错误请求（404，状态码本身的修正见 010） |
| 字段顺序与多余字段 | `password` 在前、夹杂 `extra` / `more` 字段 | 均正确登录 |
| 超长字段 | 800 字节用户名注册、800 字节口令登录 | 均按预期失败，无崩溃 |
| URL 转义 | 含空格与 `&`、`=` 的用户名/口令，以编码形式提交后注册并登录 | 注册成功、同编码登录成功、口令不符被拒 |

共 14 项断言。上述四组在 4 种触发模式 × 2 种并发模型（6 个组合）下各跑一遍，全部通过，服务端无异常输出。

### 越界写：修复前后在 AddressSanitizer 下的对照

原实现在**仅仅提交 `user=alice`（缺少 `&` 分隔符）**时即触发越界：

| 版本 | 结果 |
|:--|:--|
| 修复前 | `ERROR: AddressSanitizer: stack-buffer-overflow`，`SUMMARY` 定位到 `http_conn.cpp:547 in http_conn::do_request()` |
| 修复后 | 同样输入无任何报告 |

`http_conn.cpp:547` 即 `name[i - 5] = m_string[i];`。越界写入的是栈上的局部数组，这也解释了为何它此前未被察觉——在未开启检查的构建下，它可能长时间不表现出可观测的异常。

### 全链路：AddressSanitizer + 泄漏检查

完整功能冒烟与上述边界用例各跑一遍后以 `SIGTERM` 正常退出：

| 项 | 结果 |
|:--|:--|
| 功能冒烟 | 全部通过 |
| 边界用例 | 全部通过 |
| AddressSanitizer | 无报告 |

## 六、遗留问题

1. **解析函数未提取为可单测的单元**：`hex_value` / `url_decode` / `parse_form_body` 都是无状态的纯函数，目前定义在 `http_conn.cpp` 的匿名命名空间内，只能经由完整的请求链路验证。提取到独立头文件后即可直接写单元测试；待下一项（URL 路径解码）复用 `url_decode` 时一并考虑
2. **字段名仍固定为 `user` 与 `password`**：这是页面表单的实际字段名，属于接口约定而非脆弱假设，本次不引入通用 CGI 参数转发
3. **超长字段依赖数据库报错**：`user` / `passwd` 列为 `char(50)`，超长值由 MySQL 在严格模式下拒绝并回落到 `registerError.html`。若需更明确的提示，应在服务端先行校验长度
4. **口令仍为明文**：本次未改动存储形式，加盐哈希需要同时调整库表结构与既有数据的兼容方式，作为独立一项处理
5. **重名判定仍以内存表为准**：`register_user` 在同一临界区内查重并写库，进程内不会重复注册；但数据库中并不存在唯一约束，多实例或多进程场景下仍可能写入重名记录
