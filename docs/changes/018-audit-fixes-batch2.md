# 018 · 核查问题修复（批次二：协议与行为补齐）

> 本记录对应 `016` 第六节修复计划的**批次二**，处理 4.3（`Expect: 100-continue`）、4.4（HTTP/1.1 默认长连接）、4.5（上传目录缺失返回 500）、4.6（隐藏文件规则不一致）四项。批次一见 `017`。

## 一、背景与动机

`017` 修掉的是两处会崩溃的缺陷，它们有明确的判据——进程退出码。本批的四项没有这种判据，它们的共同点是**服务端没有违反任何硬性约束，但与客户端或与自身其它部分对不上**：

| 编号 | 现象 | 性质 |
|:--|:--|:--|
| 4.3 | 客户端发 `Expect: 100-continue` 后空等 | 协议实现不完整 |
| 4.4 | 不带 `Connection` 头的请求，每个响应后都关闭连接 | 违反 HTTP/1.1 默认语义 |
| 4.5 | 上传目录不存在时 `GET /upload` 返 500 | 把「没有内容」当成「服务端故障」 |
| 4.6 | 上传 `.hidden.txt` 成功落盘，列表页却看不到 | 两处规则不一致 |

四项都属既有问题，非阶段二引入，但都影响真实使用：4.3 让大体积上传固定多付一次超时，4.4 让绝大多数现代客户端（不长按 `keep-alive` 写头的那些）每个请求重连一次。

## 二、现状分析

### 4.3：收到期望却不回应

`parse_headers` 的头部识别是一串 `if / else if`，`Expect` 落在最后的 `else` 里，被当作未知头部记一条 `oop!unknow header: Expect`。

HTTP/1.1 中 `Expect` 唯一定义的取值是 `100-continue`：客户端在发送大体积请求体前先征求许可，服务端应以 `100 Continue` 应答。不回应**不出错**——客户端会在自身的期望超时后照常发送请求体——但那段空等是纯损耗。用原始套接字探测（只发头部、不发请求体）可以看清差异：修复前 1.5 s 内服务端不发一个字节。

### 4.4：把 HTTP/1.0 的规则用在了 HTTP/1.1 上

```cpp
        if (strcasecmp(text, "keep-alive") == 0)
        {
            m_linger = true;
        }
```

`m_linger` 的基准值是假，只在收到显式 `Connection: keep-alive` 时才置真。这是 HTTP/1.0 的语义（默认关闭，需显式请求保持）；而本服务端**只接受 HTTP/1.1**（`parse_request_line` 中非 1.1 直接返回 400），该版本的默认是保持连接。

用原始套接字在同一连接上连发两个请求即可复现：修复前第 1 个请求得到 200，第 2 个请求 `recv` 返回空——连接已在首个响应后被关闭。

### 4.5：「目录不存在」不是故障

```cpp
    DIR *dir = opendir(kUploadDir);
    if (dir == nullptr)
        return INTERNAL_ERROR;
```

上传目录是**运行期按需创建**的（`save_uploaded_file` 里 `access` 失败才 `mkdir`），因此服务刚启动、还没人上传过时它确实可能不存在——此时列表页反而报 500。

### 4.6：同一件事在两处的答案不同

上传侧只拒绝含 `/` 的名称，列表侧则跳过所有 `name[0] == '.'` 的目录项。于是 `.audit-hidden.txt` 能上传成功、真实落盘，却在列表页不可见——文件存在但用户无从发现。

## 三、设计方案

### 4.3：在读完头部、等待请求体之前回应

发送时机选在「头部全部解析完、确定要收请求体」的那一刻，而不是解析到 `Expect` 头的那一刻。理由是此时 `Content-Length` 也已校验：**超限的请求在解析该头的当下就返回 413**，根本走不到这里，因此不会出现「先许可、再拒绝」的白传。

100 响应走裸 `send` 而不进写缓冲——写缓冲承载的是最终响应，而 100 是请求处理中途的中间响应。

`Expect` 的其它取值按规范回 **417 Expectation Failed**，并关闭连接：客户端可能没等 100 就把请求体发了过来，那些字节无从处理（与 413 同样的理由）。

### 4.4：翻转基准值

`m_linger` 在 `init()` 中置真，`parse_headers` 只需处理显式关闭：

```cpp
        if (strcasecmp(text, "close") == 0)
            m_linger = false;
```

413 / 431 路径上原有的 `m_linger = false` 保持不变——那些响应之后连接上还有无从处理的字节。

### 4.5：视为空列表

列表页的职责是展示已有内容；「目录不存在」与「目录存在但没有内容」对它是同一个结果，都输出「暂无文件」。把读取循环包进 `if (DIR *dir = opendir(...))` 即可，`files` 为空时原有的空列表分支已经存在。

### 4.6：统一到「拒绝」

两处取一，选的是**上传侧拒绝点号开头的文件名**：列表页的跳过逻辑保持不动，规则更保守，改动也更小。反方向（列表侧纳入展示）需要把「跳过点号开头」改成「只排除 `.` 和 `..`」，反而放宽了展示范围。

### 协议层探针（原始套接字）

curl 在这两项上不是合适的探针：它遇到关闭的连接会自动重连，因而看不到「服务端关闭了连接」；发不发 `Expect` 也随版本而异。因此改用 python 直接构造请求：

| 用例 | 旧 | 新 |
|:--|:--|:--|
| 只发头部（`Expect: 100-continue` + `Content-Length: 100`），不发请求体 | 1.5 s 内无任何响应 | `HTTP/1.1 100 Continue` |
| 同一连接连发两个 `GET`（均不带 `Connection` 头） | 第 2 个请求 `recv` 返回空（连接已关闭） | 第 2 个请求 `200 OK` |
| 同连接连发两个 `GET`，首个带 `Connection: close` | — | 第 2 个请求连接已关闭（符合预期） |
| `Expect: foo` | 不识别 | `417` |

`016` 报告中「`curl -F` 默认 1.04 s、加 `-H 'Expect:'` 后 0.036 s」的耗时对比在本机未复现——本机 curl 不等 100 就直接发送了请求体，两个版本都是毫秒级。耗时受客户端行为影响，故记录以原始套接字的协议证据为准。

## 六、遗留问题

1. **长连接成为主路径后，连接复用路径的覆盖度需要补齐**：`m_linger` 默认置真之后，绝大多数请求都会走「复用同一连接处理下一个请求」这条路，而此前它只在客户端显式要求时才被走到。`016` 第七节列出的「`ET + 长连接` 在压力下的表现」因此从边缘场景变成常规场景，宜在阶段三重构前补一轮定向验证
2. **流水线请求仍不支持**：`init()` 会清空 `m_read_idx`，一个请求的响应尚未发出时若客户端又发了下一个请求，那些已缓冲的字节会被丢弃。HTTP/1.1 并不要求服务端支持流水线（客户端必须能容忍），故不视为缺陷，但记录在此
3. **`Expect` 的比较是大小写不敏感的整串匹配**：`100-continue; foo` 一类带扩展的取值会被判为 417。规范允许 `Expect` 携带以 `;` 分隔的扩展，实践中未见过，暂不处理
4. **`417` 后关闭连接的取舍**：规范未要求关闭，这里是为避免未读完的请求体污染连接而采取的保守做法。若客户端确实等待了 100 才发体，关闭是多余的
