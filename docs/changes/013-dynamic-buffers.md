# 013 · 动态缓冲与跨读请求的解析修正

## 一、背景与动机

路线图把这一项记为「固定 2KB，满即断连 → 改为可扩容缓冲，区分『缓冲满』与『连接关闭』」。实际动手后发现，解除尺寸限制只是其中一半——**固定尺寸的缓冲恰好掩盖了几处跨读取才暴露的解析缺陷**：一旦请求体可以跨越多次读取，这些问题就会立刻显形。

因此本项不仅解除了尺寸限制，也修正了随之暴露的三个缺陷，它们的共同点是**只在请求跨越多次读取时成立**。

## 二、现状分析

### 固定缓冲：满即断连

```cpp
static const int READ_BUFFER_SIZE = 2048;
static const int WRITE_BUFFER_SIZE = 1024;
char m_read_buf[READ_BUFFER_SIZE];
```

`read_once` 开头即检查 `if (m_read_idx >= READ_BUFFER_SIZE) return false;`，而 `read_once` 返回 false 的既有含义是「连接该结束了」。于是略大于 2KB 的请求（`Content-Length` 稍大的表单、所有 multipart 上传）不是被拒绝，而是**连接被直接关闭，客户端收不到任何响应**。

写缓冲同样固定：`add_response` 超出 1024 字节即返回 false，上层随即关闭连接。

### 内存占用与负载无关

连接对象按最大连接数预分配：

```cpp
users = new http_conn[MAX_FD];   // MAX_FD = 65536
```

每个对象自带 2KB 读缓冲与 1KB 写缓冲，即 65536 × 3KB ≈ **192 MB**，无论实际有多少连接。基线记录中「常驻内存恒为 262.7~262.8 MB、与负载无关」正是这一结构的结果。

### 缺陷一：请求体起点随读取漂移

```cpp
if (m_read_idx >= (m_content_length + m_checked_idx))
```

`m_checked_idx` 是「按行扫描」的游标，而 `parse_line` 在找不到行结束符时会把该游标一路推进到 `m_read_idx`。内容阶段每轮解析结束后循环条件仍会调用一次 `parse_line`，于是**这个游标随每次读取向后漂移**，请求体是否收完的判定基准也跟着漂移。

实测（修复前，20KB 请求体，5 次读入）：

| 读取轮次 | `m_read_idx` | `m_checked_idx` | 判定基准 |
|:--:|:--:|:--:|:--:|
| 1 | 2048 | 162 | 20195 |
| 2 | 4096 | 2048 | 22081 |
| 3 | 8192 | 4096 | 24129 |
| 4 | 16384 | 8192 | 28225 |
| 5 | 20195 | 16384 | 36417 |

第 5 轮数据已全部到齐（20195 字节），但判定基准已涨到 36417，请求永远无法完成。连接就此挂起，直到 15 秒后被定时器回收，**同样没有任何响应**。

此前这个缺陷不可见：请求体一旦超过 2KB，`read_once` 早已返回 false 把连接关掉了，根本走不到这里。

### 缺陷二：内容阶段写入结束符会破坏后续字节

`parse_content` 中的 `text[m_content_length] = '\0'` 写的位置紧随请求体之后，那里可能正是流水线中下一个请求的起始字节。

## 三、设计方案

### 读缓冲：std::vector 按需扩容

保留 `READ_BUFFER_SIZE` 作为初始容量，新增 `MAX_REQUEST_SIZE`（8 MiB）作为上限，空间不足时按几何级数翻倍。

超出上限的处理路径是本次设计的关键取舍。`read_once` 返回 false 会让调用方关闭连接，而**要在那一刻发出响应，需要同时改动 Proactor 与 Reactor 两条调用路径**。因此改为把「超限」表达为一种解析结果：

```
read_once          缓冲区不足且已达上限 → 置 m_oversized，返回 true（交给 process）
process_read       见 m_oversized → 返回 REQUEST_TOO_LARGE
process_write      回应 413，并强制 Connection: close
```

这样超限的处理完全落在 `http_conn` 内部，调用方无需区分。

### 扩容后必须重定位指向缓冲区的成员

`std::vector` 扩容会重分配，地址随之变化，而 `m_url`、`m_version`、`m_host`、`m_string` 都指向读缓冲区内部。解析是分多轮进行的：请求行可能在扩容前就已解析，指针便会在扩容后失效。

`grow_read_buffer` 因此按同一偏移量重新指向：

```cpp
const char *old_data = m_read_buf.data();
m_read_buf.resize(size);
const ptrdiff_t delta = m_read_buf.data() - old_data;
if (delta == 0) return;
if (m_url != nullptr) m_url += delta;
... // 凡是指向读缓冲区的成员都必须在此调整
```

**备选方案是「扩容后重置解析状态、从头重解析」**。未采用：解析过程会就地修改缓冲区（`parse_line` 把 `\r\n` 改写为 `\0`），缓冲区已被改动后无法重新切分出原来的行。

### 请求体起点单独记录

新增 `m_body_start`，在头部解析完成、切换到内容状态时记录一次：

```cpp
m_body_start = m_checked_idx;
m_check_state = CHECK_STATE_CONTENT;
```

内容阶段改用 `m_body_start` 作为判定基准，并且**不再调用 `parse_line`**——请求体由 `Content-Length` 定长界定，本就不该按行扫描。这同时消除了「跨读漂移」与「对请求体反复扫描」两件事。

### 写缓冲同样可扩容

`add_response` 在空间不足时扩容后重试，用 `vsnprintf` 的返回值（截断时返回「本该写入的长度」）判断是否需要重试，上限 64 KiB。重试时用 `va_copy` 重新取一份参数——被消费过的 `va_list` 不能再次使用。

### 内容阶段不再补写结束符

请求体的消费方（表单解析、multipart 解析）都带长度读取，不依赖 C 字符串语义，因此这一写入是多余的，去掉即可。

### 连接复用时归还大缓冲

`init()` 中若读缓冲容量远大于初始值（> 4 倍），则释放并重新分配，避免一次大请求之后连接对象长期占着大块内存。

## 四、实现要点

| 文件 | 改动 |
|:--|:--|
| `http/http_conn.h` | 缓冲区改为 `std::vector<char>`；新增 `MAX_REQUEST_SIZE` / `MAX_RESPONSE_SIZE`、`REQUEST_TOO_LARGE` 状态、`m_oversized` 与 `m_body_start`；声明三个扩容辅助函数 |
| `http/http_conn.cpp` | `grow_read_buffer` / `ensure_read_space` / `grow_write_buffer`；`read_once` 按需扩容并在超限时置位；`process_read` 新增内容阶段分支与超限判定；`process_write` 新增 413 分支；`parse_headers` 记录请求体起点；`parse_content` 改用 `m_body_start` 且不再写结束符；`add_response` 支持扩容重试 |
| `tests/test_password_hash.cpp` | 修正一条会偶然通过的断言（详见验证一节） |

## 五、验证

### 跨读取与超限

| 用例 | 结果 |
|:--|:--|
| 4KB 请求体，先送头部、停顿 0.4s 再送请求体（跨两次读取，触发扩容） | 正确路由到主面板 |
| 20KB 请求体单次送达 | 正常解析 |
| 9MB 请求体（超过 8 MiB 上限） | 返回 `413 Request Entity Too Large` |
| 超限之后的其他请求 | 正常返回 200 |

413 用例的构造方式值得说明：早期版本一边发送一边关闭，服务端拒绝后关闭连接时仍有未读数据，TCP 会以 RST 收尾，客户端可能连响应都读不到。改为「只发送、不关闭发送端，然后读取响应」后，六种模式下均稳定复现。

### 指针重定位的必要性（ASan 对照）

| 版本 | 4KB 跨读请求体在 AddressSanitizer 下 |
|:--|:--|
| 保留重定位 | 无任何报告 |
| 临时去掉重定位 | `ERROR: AddressSanitizer: heap-use-after-free`，定位到 `__interceptor_strrchr`（即 `do_request` 中读取已失效的 `m_url`） |

### 内存占用

| 版本 | 常驻内存（单请求后读取 RSS） |
|:--|:--|
| 改造前 | 264 MB |
| 改造后 | **76 MB** |

改造前与基线记录中的 262.8 MB 吻合。剩余部分主要是连接对象数组本身（`m_real_file`、定时器等固定成员），对应阶段三的「连接对象动态管理」。

### 回归与动态检查

| 项 | 结果 |
|:--|:--|
| 5 类用例（功能冒烟、参数边界、路径、错误响应、缓冲）× 4 触发模式 × 2 并发模型（6 组合） | 全部通过 |
| `ctest`（Release 与 ASan 两种构建，各重复 3 次） | 5/5 通过 |

### 顺带修正：一条会偶然通过的断言

`012` 新增的用例中有一条以「改写编码串末尾两个字符」来构造散列长度不符的输入：

```cpp
EXPECT_FALSE(password_hash::verify("pw", good.substr(0, good.size() - 2) + "A="));
```

base64 末组中**不参与解码的低位**被改变时，解出的字节与原值完全相同——此时该断言会失败。实测约每 6 次触发一次（六分之一恰为末组低四位为 0 的概率）。已改为确定性的构造方式（把散列字段换成 16 字节的 base64，长度必然与 32 字节的推导结果不符，并补充散列字段为空的用例）。

修正后：Release 下 20 次、ASan 下 130 次运行，全部通过。

## 六、遗留问题

1. **请求体上限为硬编码常量**：8 MiB 写在头文件中，未纳入配置文件；若需按部署调整，应移入 `config.ini`
2. **超限后客户端可能读不到 413**：服务端拒绝后关闭连接，若客户端仍在发送，TCP 会以 RST 收尾并可能丢弃已到达的响应。这是 HTTP 的固有情形（RFC 7230 亦建议 413 后关闭连接），但提示了客户端应尽快停止发送
3. **写缓冲上限仅约束响应头与内联正文**：文件响应经 `mmap` 由 `writev` 直接发送，不受 64 KiB 限制
4. **连接对象仍按最大连接数预分配**：缓冲区改为按需分配后常驻内存降至 76 MB，但对象数组本身仍固定，属阶段三的处理范围
5. **上传仍需请求体全部驻留内存**：multipart 解析在内存中构造完整请求体，上传体积上限将在后续的上传约束中单独设定
6. **请求体较长时单次读取的分配策略**：容量按几何级数增长，最大可能一次性占用 8 MiB；若并发大量大请求，内存峰值仍较高
7. **对端关闭写端时请求被丢弃（已定位，本次未修复）**：客户端发送请求后立即关闭写端（`shutdown(SHUT_WR)`，部分命令行工具与脚本即为此种写法）时，请求数据与对端 FIN 落在同一批事件里，而事件循环把 `EPOLLRDHUP` 判在 `EPOLLIN` 之前，连接会在数据被读取前关闭。以「发送请求后立即关闭写端」请求静态页面，**10 次请求 0 次收到响应**。

   曾尝试把判定顺序调整为「可读可写先于对端关闭」（改动仅在 `webserver.cpp` 的事件分支顺序）。该改动修复了上述现象，但在 Reactor 模式下引入了新的失败：

   | 版本 | 「新连接 + Connection: close」120 次请求无响应数 |
   |:--|:--|
   | 改动前（判定顺序维持原样） | 0 |
   | 仅调整判定顺序 | 8（其中部分请求返回 400） |
   | Reactor 对照：判定顺序调整前 | 0 |

   失败形态为「服务端回 400」或「无响应」。开启日志后可见关键线索：请求体已完整读入（`recv=56`），但解析却是从 `Host: t` 这一行开始的——请求行未被解析，即解析状态在连接对象被复用时出现了错用。这与路线图问题清单第 3 项（**连接关闭与定时器回调均会释放同一描述符，缺少幂等保护，描述符被复用后可能误操作新连接**）和第 5 项（**Reactor 路径以忙等标志位等待工作线程，且该标志无跨线程同步**）一致：调整判定顺序会让关闭路径改由工作线程任务队列处理，从而放大这两个既有缺陷的暴露面。

   由于阶段二的约束是「不改变核心数据结构与线程模型」，而该问题涉及连接生命周期与事件循环的重建（阶段三的「连接生命周期与释放路径收敛」「移除忙等与 EPOLLONESHOT」），因此**本次撤回该调整**，连同上述证据一并留待阶段三与事件循环重写一并处理。
