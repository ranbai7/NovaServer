# 032 · AddressSanitizer 服务端全链路运行

> 阶段四的最后一项。此前 ASan 只覆盖了单元测试与功能链路，本次把**服务端本身**放进
> ASan 跑一遍完整的请求链路与并发连接，并在退出时执行泄漏检查。
> 过程中查出一个由日志改造引入的优雅退出回归，一并记录。

## 一、背景与目的

阶段三的 TSan 复核了并发正确性，但内存正确性只在单元测试层面过了 ASan。请求处理链路
（状态机解析、路径映射、文件映射与发送、上传落盘、数据库取连接）里有大量手工的
`mmap` / `munmap` / 裸指针，这些路径短连接并发下才会被反复走到，单元测试碰不到。

顺带一个现实理由：ASan 的报告要求进程**正常退出**才会执行泄漏检查，这条约束本身就能
把「优雅退出是否真的生效」验出来——事实证明确实如此，见第四节。

## 二、方法

按 CMake 选项启用 ASan（生成目录 `build-asan`，`RelWithDebInfo` + `-DENABLE_ASAN=ON`）：

```bash
cmake -B build-asan -DCMAKE_BUILD_TYPE=RelWithDebInfo -DENABLE_ASAN=ON
cmake --build build-asan -j4
```

服务端**开启日志**（`-c 0`，默认的异步写入方式）运行，使日志路径同样处在 ASan 之下：

```bash
ASAN_OPTIONS=detect_leaks=1 ./build-asan/server -p 9104 -m 0 -t 2 -c 0 -f <配置> \
  > /tmp/asan.out 2>&1 &

./test_pressure/smoke.sh 9104                    # 全链路功能冒烟
wrk -t2 -c50 -d3s                       http://127.0.0.1:9104/judge.html   # 长连接并发
wrk -t2 -c50 -d3s -H "Connection: close" http://127.0.0.1:9104/judge.html  # 短连接风暴

kill -TERM <pid>; wait <pid>                     # 优雅退出，退出码须为 0
```

覆盖面：静态资源、站点根、404、URL 转义、HEAD 与 `Content-Length`、路径穿越、
上传白名单与取回闭环、**注册与登录（含写库）**、空闲连接回收；外加长连接与
短连接（连接建立/关闭风暴）两组并发各 3 秒。

## 三、结果

| 项 | 结果 |
|:--|:--|
| 功能冒烟 | **18/18 通过** |
| 并发长连接 | 32964 req/s |
| 并发短连接（连接风暴） | 22394 req/s |
| 服务端在整个过程中的内存错误 | **无** |
| `SIGTERM` 退出码 | **0** |
| ASan / LSan 输出 | **0 字节**（无任何报告） |

### 为什么「0 字节」是可采信的

ASan 在无问题时**不产生任何输出**，而退出码为 0 说明泄漏检查确实在退出路径上执行了。
为排除「检查根本没跑」这种可能，用一个**故意泄漏**的最小程序在同样环境下做了对照：

```c
#include <stdlib.h>
int main(void) { void *p = malloc(1234); (void)p; return 0; }
```

```bash
gcc -fsanitize=address -g -o leakcheck leakcheck.c && ./leakcheck
# ==30458==ERROR: LeakSanitizer: detected memory leaks
# Direct leak of 1234 byte(s) in 1 object(s) allocated from:
#     #0 ... in __interceptor_malloc ...
# 退出码 = 1
```

对照组被如实报告且退出码为 1，说明本环境确实会报告泄漏。因此服务端那份空输出是
「检查过、且干净」，而不是「检查没执行」。

（阶段三的记录里提到退出时 `libmysqlclient` 有 248 字节的 `possibly lost`。本次未出现，
推测与那次是用 valgrind 测量、且当时的连接池使用方式不同有关；这里只如实记录本次结果。）

## 四、过程中查出的回归：优雅退出失效

第一次运行时 `SIGTERM` 的**退出码是 143（被信号杀死）**，而不是 0。这个现象本身不会
产生任何 ASan 报告，只是让泄漏检查静默地不执行——如果只盯着「有没有 ASan 报告」，
就会把「检查没跑」误当成「检查通过」。

**定位**：用 `write_mode` 做了一次对照——

| 写入方式 | 是否有写盘线程 | `SIGTERM` 退出码 |
|:--|:--|--:|
| 0（同步） | 无 | **0** |
| 1（异步，默认） | 有 | **143** |

**根因**：信号掩码是线程属性，子线程继承的是创建它那一刻的掩码，因此 `SIGTERM` 必须在
创建**任何**线程之前屏蔽。代码里这句约束本来就有注释，但日志改造把默认写入方式改成了
异步，**写盘线程在 `WebServer::log_write()` 里就建好了，早于 `run()` 中的屏蔽**——
于是它带着未屏蔽的掩码，`SIGTERM` 被投递给它时按默认动作终止进程。

这是本次日志改造引入的回归：旧的异步方式虽然也会建线程，但那时默认为同步，
默认配置下并不会走到这条路径，因此问题一直没暴露。

**修法**：把 `SignalWatcher::block_signals({SIGTERM, SIGINT})` 从 `WebServer::run()`
移到 `main()` 开头（配置解析之前），`run()` 只保留把信号接到事件循环上这一步。
修完 `write_mode` 两种取值下退出码均为 0。

> 教训：验证项要挑那些**失败时不会吵闹**的。退出码 143 不产生任何报错输出，
> 若这次只跑冒烟、不看退出码与泄漏报告，这个回归会一直留着。

## 五、遗留

1. 本次覆盖的是静态资源、上传与登录注册路径；**文件上传的大体积分支**（接近体积上限）
   未单独构造。
2. ASan 是**逐次运行**的检查，不具备覆盖率度量；未被执行到的分支不会报错。判断覆盖面
   依据的是功能冒烟与压测实际走到的路径，而非插桩统计。
3. 阶段四至此收口，无其它遗留。
