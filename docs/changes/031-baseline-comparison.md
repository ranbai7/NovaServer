# 031 · 按阶段零方法重跑压测，与 `021` 基线对照

> 阶段四的收尾项之一。目的是回答「阶段三与阶段四的改动累计带来了什么」。
> 与既有基线不同，本次不只复跑一遍，还把 `021` 的代码在同一时段重建后一并测量，
> 把时段差异从对比中消掉。

## 一、背景与方法

`021` 是阶段三（并发模型重构）**之前**的基线。本次重跑量化的是**阶段三与阶段四的累计效果**，
而不是日志改造一项——阶段四的日志改动只在开启日志时生效，而本组压测按阶段零的方法以
`-c 1` 关闭日志，它根本不参与。

方法与 `000` / `021` 一致，以便复现：

| 项 | 值 |
|:--|:--|
| 主机 / 虚拟化 | ubuntu22-virtual-machine（VMware），Intel Core i5-13500H，4 逻辑核 / 3.8 GiB |
| 编译选项 | `-O2 -DNDEBUG`（CMake `Release`） |
| 工具与参数 | `wrk` 4.1.0，`-t2 -c100 -d5s`，每组 5 次取中位数 |
| 目标 | `http://127.0.0.1:9006/judge.html` |
| 服务端 | `-c 1` 关闭日志 |

```bash
cmake -B build -DCMAKE_BUILD_TYPE=Release && cmake --build build
cp build/server ./server
./test_pressure/bench.sh 100 5s 5
```

### 为什么要做同时段 A/B

`021` 采集于 2026-09-27，与本次相隔两天，且当时的代码与现在**不是同一套架构**
（旧的是半同步/半反应堆线程池，`-a` 参数尚在）。跨时段、跨架构地直接搬那批数字来比较，
结论会被「时段差异」污染。

因此本次把 `021` 对应的代码用 `git worktree` 重建、在本时段重测了一遍：

```
$ git worktree add --detach /tmp/nvs-base <021 文档提交的父提交>
$ cmake --build build && ls -l build/server
  173136 字节
```

**重建出的二进制是 173136 字节，与 `021` 文档记录的完全一致**，确认跑的就是当年那份代码。
两份数据在同一时段、同一环境下相继采集，构成干净的 A/B。

## 三、结论

### 一、常驻内存下降约八成，这是最稳健的一项

所有组合下 RSS 从 **60.0 MB 降到 11.7~12.6 MB**。这一项是结构性的：连接对象由「按最大
连接数预分配」改为动态管理（阶段三 3.4），与线程数、触发模式都无关，因而不受测量噪声影响。

### 二、默认配置下吞吐提升，但幅度因组合而异

`-m 0 -t 8`（默认）从 29084 升到 33426，**+15%**；四种触发模式在 `-t 8` 下分别 +15% /
+4% / +24% / +6%。提升真实存在，但同一配置在两次测量间本就可能有 10% 以上的波动，
因此**单看默认组合的增益并不足以支撑强结论**。

### 三、架构的最优点发生了位移：从 `-t 1` 移到 `-t 2`

旧架构的最优行是 `-t 1`（32246），新架构的是 `-t 2`（**47177**，5 次实测 46554~49187，
P99 稳定在 5 ms 以内）。在各自的最优点上比较，**提升约 46%**。

位移与 `-t 1` 的倒退是实测结果，其原因**本次未做验证**，下面只是与数据相符的一种解释：

- 旧模型里 `-t 1` 是一个共享的工作线程池，主线程既做 epoll 也做 accept，工作线程只负责
  已就绪连接的读写与处理；新模型里主线程只 accept，`-t 1` 意味着全部 100 条连接都归一个
  子 Reactor 处理。两者线程数相同，但连接事件的来源不同
- 到了 `-t 2` 及以上，主线程与子线程的分工才带来并行度；继续加线程（`-t 4`、`-t 8`）则因
  主线程、子线程与压测客户端共 7~11 个线程争抢 4 个逻辑核而收益回落

要确认哪一种解释成立，需要分别测量各档位下的 CPU 占用与上下文切换次数，本次未做。

可以确定的是：**4 核环境下新架构的线程数甜点是 2 而不是默认的 8**。它意味着「子 Reactor
线程数」这个参数的默认值宜随部署机器的核数来定，而不是取一个固定的大数。

### 四、延迟

在各自的最优点上，P99 从 6.310 ms 降到 **3.750 ms**，P50 从 3.290 ms 降到 2.060 ms。
但在默认的 `-t 8` 下，新架构的 P99（14.6~20.8 ms）反而略逊于旧架构（5.1~16.4 ms）——
这也与第三节的过订阅解释一致：线程数超过核数时，请求在队列上的等待被放大。

## 四、局限

1. **客户端与服务端同机**：两者争夺同一组 CPU 核心，绝对吞吐的上限可能由客户端而非服务端决定。
   线程数甜点落在 2 而非更高，也有这一层原因。
2. **只覆盖静态资源路径**：登录、注册等涉及数据库查询的路径未单独测量。
3. **架构差异不可分离**：本次对照的是「阶段三 + 阶段四」的累计结果，无法把两者拆开。
   阶段四的日志改动在 `-c 1` 下不参与，因此这组数字实际反映的是阶段三。
4. 旧架构的 `-a` 参数（Proactor / Reactor）已在阶段三移除，表中取 `-a 0` 一列进行对照。
