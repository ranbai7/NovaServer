# 006 · 持续集成接入

## 一、背景与动机

阶段一完成了构建系统迁移、代码格式统一与单元测试接入，但这些检查都依赖人工执行——没有人会记得每次改完都跑一遍 `ctest`，也不会有人每次都验证代码在干净环境中能否构建。

持续集成解决两个问题：

1. **干净环境验证**：本地机器可能残留着未被察觉的隐式依赖（例如某个头文件恰好被间接包含）。只有在全新的机器上从零构建，才能暴露这类问题。
2. **自动回归保护**：单元测试接入后，需要保证它每次都被执行，而不是"写了但没人跑"。

## 二、现状分析

| 已有的 | 缺失的 |
|:--|:--|
| CMake 构建系统，支持 Debug/Release 与 Sanitizer 开关 | 构建过程只能在本地手动触发 |
| 13 个单元测试用例，可经 `ctest` 运行 | 测试不会随代码变更自动执行 |
| 格式统一且编译告警为零 | 这些成果没有自动化的守护机制 |

## 三、设计方案

选用 **GitHub Actions**，它是仓库所在地 GitHub 的原生 CI 服务，无需引入第三方平台，免费额度对公开仓库没有限制。

### 触发条件

| 事件 | 目的 |
|:--|:--|
| 推送到 `main` | 保证主干始终处于可构建、可测试状态 |
| 向 `main` 提交 PR | 在合并之前就发现问题 |

### 矩阵构建

同一套步骤分别以 **Release** 与 **Debug** 两种构建类型各执行一遍。

这样做的价值在于：两种配置的编译选项不同（Release 带 `-DNDEBUG`），某些依赖断言的代码路径只在其中一种下才会暴露问题。前面在告警治理中发现的「断言在 Release 下被移除」正是这类差异。

### 步骤设计

| 步骤 | 命令 | 作用 |
|:--|:--|:--|
| 检出代码 | `actions/checkout@v4` | 将仓库内容取到运行环境 |
| 安装依赖 | `apt-get install libmysqlclient-dev libgtest-dev` | 供服务器编译与单元测试使用 |
| 配置 | `cmake -B build -DCMAKE_BUILD_TYPE=<类型>` | 生成构建系统 |
| 编译 | `cmake --build build -j$(nproc)` | 并行编译 |
| 测试 | `ctest --test-dir build --output-on-failure` | 执行单元测试，失败时输出详情 |

## 四、实现要点

新增 `.github/workflows/ci.yml`。文件结构与关键字段：

```yaml
name: CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  build-and-test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        build_type: [Release, Debug]
    steps:
      ...
```

- `on` 定义触发事件
- `jobs` 下的每个条目运行在一台独立虚拟机上
- `strategy.matrix` 使同一套步骤按多个取值分别执行，`${{ matrix.build_type }}` 在步骤中引用当前取值
- `--output-on-failure` 是关键细节：不加它，测试失败时只能看到一行失败提示，拿不到具体断言信息

README 中增加了构建状态徽章，链接到该 workflow 的运行记录。

## 五、验证

### 配置校验

以 YAML 解析器校验文件结构，确认触发事件、运行环境、矩阵配置与 5 个步骤均被正确解析。

### 本地模拟执行

按 CI 中的命令序列在本地依次执行：

| 步骤 | 结果 |
|:--|:--|
| `cmake -B build -DCMAKE_BUILD_TYPE=Release` | 配置成功 |
| `cmake --build build -j$(nproc)` | 编译成功，0 错误 |
| `ctest --test-dir build --output-on-failure` | 100% tests passed |

### 远端验证方式

代码推送后，可在仓库的 **Actions** 页面看到本次运行：

- 黄色圆点表示运行中，绿色对勾表示全部通过
- 点击进入可查看每个步骤的完整日志
- 矩阵的两个配置会作为两个独立的执行记录并列显示

## 六、遗留问题

1. **`-Werror` 尚未启用**：当前告警已清零，理论上可以开启以阻止新告警进入。但 GitHub runner 的 GCC 版本高于本地开发机，新版编译器可能报告额外的告警而导致 CI 在无关改动上失败。建议在 CI 跑通若干次、确认无新增告警后再启用
2. **格式检查未纳入**：`clang-format` 在不同版本间对个别规则的处理存在差异，本地使用 23.1.1 而 runner 上的版本不同，直接比对可能产生误报。若要纳入，需在 CI 中固定 `clang-format` 的版本
3. **Sanitizer 未纳入 CI**：CMake 已提供 `ENABLE_ASAN` / `ENABLE_TSAN` 开关，但动态检查会显著增加运行时间，适合作为独立的 workflow 定期执行，而非每次推送都跑
