# 002 · 代码格式统一

## 一、背景与动机

阶段一引入 `-Wall -Wextra` 后暴露了 45 个编译告警，后续需要逐项治理。在开始治理之前先统一代码格式，有两个作用：

1. 让后续的告警修复 diff 只包含语义改动，不被格式噪声淹没
2. 为代码风格建立明确约定，避免后续新增代码风格不一

这项工作只有放到最前面才有意义——越往后，格式化产生的 diff 与真实改动就越难区分。

## 二、现状分析

格式化前的代码风格：

| 方面 | 状况 |
|:--|:--|
| 缩进 | 大部分为 4 空格，但 `CGImysql/` 下使用制表符 |
| 大括号 | 函数与控制语句均采用换行风格（Allman），整体一致 |
| 指针与引用 | 符号紧贴变量名，如 `char *ptr` |
| 行宽 | 无统一限制，部分行超过 120 列 |
| 空白 | 存在行尾空格与多余连续空行 |

整体风格基本统一，但缺少工具约束，只能靠人工维持。

## 三、设计方案

选用 clang-format，配置以 LLVM 风格为基础，再按项目现状覆盖关键项。

**设计原则是「贴近现有风格」**：如果选一套与现有代码差异很大的风格（例如把大括号改为行尾），格式化会产生数千行的纯重排 diff，既掩盖真实改动，也让这次提交变得难以审阅。

| 配置项 | 取值 | 理由 |
|:--|:--|:--|
| `BreakBeforeBraces` | `Allman` | 与现有代码一致，避免大规模重排 |
| `IndentWidth` | 4 | 与现有代码一致 |
| `PointerAlignment` / `ReferenceAlignment` | `Right` | 保持 `char *ptr`、`const string &name` 的写法 |
| `ColumnLimit` | 120 | 兼顾可读性与现有行的长度分布 |
| `AllowShortFunctionsOnASingleLine` | `Inline` | 保留类内访问器的单行写法 |
| `SortIncludes` | `CaseSensitive` | 规范化头文件顺序 |
| `IncludeBlocks` | `Preserve` | 保持现有分组，不强行合并 |

被否决的方案：

| 方案 | 否决理由 |
|:--|:--|
| 直接沿用 LLVM 默认风格 | 2 空格缩进与行尾大括号会与现有代码全面冲突，产生大量无意义重排 |
| 仅靠人工约定 | 无法在提交前自动检查，约束力不足 |
| 同时引入 clang-tidy | 静态检查规则较多，会与本次格式统一的目的一起放大 diff，留待后续单独评估 |

格式化范围仅限项目自身源码。`test_pressure/` 下为第三方压测工具，不纳入格式化范围。

## 四、实现要点

新增 `.clang-format` 配置文件，置于项目根目录，clang-format 会自动向上查找应用于所有子目录。

执行方式：

```bash
git ls-files '*.cpp' '*.h' | xargs clang-format -i
```

检查是否合规（不修改文件）：

```bash
git ls-files '*.cpp' '*.h' | xargs clang-format --dry-run -Werror
```

使用的工具版本为 clang-format 23.1.1。

## 五、验证

| 项 | 结果 |
|:--|:--|
| 需要格式化的文件 | 16 个（全部源码文件） |
| 变更规模 | 320 行插入 / 350 行删除 |
| 编译 | 成功 |
| 编译告警数 | **仍为 45**，与格式化前一致，未引入新问题 |
| 运行时 | 服务端正常启动，`/judge.html`、`/log.html`、`/picture.html`、`/video.html`、`/upload.html` 均返回 200 |

变更主要集中在两处：`CGImysql/` 下的制表符转为空格，以及全项目的行尾空白清理。**语义无任何改动**。

## 六、遗留问题

1. **45 个编译告警仍未治理**，为阶段一的下一项工作
2. **格式化提交会使 `git blame` 指向本次改动**：由于这是一次纯格式提交，可为后续的 blame 操作建立忽略清单（`.git-blame-ignore-revs`），避免真实改动的归属被格式噪声掩盖
3. **未在提交前自动校验格式**：可考虑在 CI 中加入格式检查，保证后续提交始终合规
