# 027 · 3.4 验证：轮转分发成立，但短连接风暴下有稳定崩溃

> 本记录承接 `026` 第五节列出的待补项。它同时包含两部分：**已经通过的验证**（轮转分发与压测对比）和**一项未通过的验证**（连接建立/关闭风暴），后者是一个尚未定位到根因的真实缺陷，因此单独留痕供后续修复。

> **状态**：3.4-a（分发验证与压测对比）通过；3.4-b 的短连接场景**确认为缺陷**，已缩小到 `do_request` 内的一小段，但未定位到根因。3.4-b 的其余场景、3.4-c 未开始。

## 一、3.4-a：轮转分发成立

### 分发确实生效

`-t 4` 下以长连接持续施压（`wrk -c100 -d10s`），采样各线程瞬时 CPU（两次读 `/proc/<pid>/task/*/stat` 取差）：

| 线程 | CPU 占用 |
|:--|--:|
| 子线程 ×4 | 49.7% / 49.7% / 49.7% / 49.0% |
| 主线程（只 accept） | 0.0% |

对照 `-t 0`（全部连接归主循环）：主线程 **99.0%**，单核饱和。

四个子线程的负载几乎相同，主线程不再承担数据处理，`026` 第三节「连接的建立要投递到目标线程」的设计得到验证。

### 线程数矩阵

参数与 `021` 基线一致（`-c100 -d5s`，每组 5 次取中位数）：

| -t | QPS | P50 (ms) | P99 (ms) |
|--:|--:|--:|--:|
| 0 | 25315 | 3.59 | 46.73 |
| 1 | 27141 | 3.53 | 7.18 |
| **2** | **45918** | **2.10** | **3.41** |
| 4 | 32739 | 2.89 | 9.02 |

与 `021` 基线（默认配置 QPS 25858）对照：`-t 0/1` 持平（重构未退化），`-t 2` **+78%**。

### `-t 2` 反超 `-t 4` 是环境容量所致，不是代码问题

本机 4 个 vCPU 实为 **2 物理核 + 超线程**：`/sys/devices/system/cpu/cpu*/topology` 显示 `core_id` 0/1 在两个 `physical_package_id` 下各出现一次。wrk 与压测目标同机，客户端本身占用约 2 核，服务端实际可用约 2 核。

把 wrk 绑到单核（`taskset -c 0`）后重测，`-t 2` 仍然最优（46920），`-t 3`（43626）与 `-t 4`（33090）随之下降。因此 `021`「线程数无差异」的结论应改写为：**分发带来了正相关，但本机容量在 2 个子线程处封顶**。真实的多核收益需要更多物理核才能观测。

## 二、3.4-b 的连接风暴场景：确认崩溃

`026` 把「连接建立/关闭风暴」列为 TSan 的重点场景。用 `wrk -c100 -H "Connection: close"`（短连接，4 秒内建立/关闭约 8 万条连接）施压，服务端稳定段错误。5 轮结果：

| -t | 崩溃轮数 |
|--:|--:|
| 0 | 0/5 |
| 1 | **4/5** |
| 2 | **5/5** |
| 4 | 2/5 |

`-t 1`（主线程 accept + 1 个子线程）就有 4/5 的崩溃率，说明问题位于**主线程与子线程的那条路径**上，而不需要多个子线程之间的竞争。

加大压力后 `-t 0` 也会崩（`-c100 -d10s` 下 1/8），因此**这不是多线程竞态，而是确定性的逻辑缺陷**——只是单线程下触发概率低。

### 崩溃现场

三次捕获到的崩溃点各不相同，是典型的**堆破坏**（破坏点与崩溃点分离）：

| 捕获点 | 栈 |
|:--|:--|
| `unlink_chunk` ← `_int_malloc` | unsorted bin 中一个 chunk 的 fd/bk 链表指针被覆盖 |
| `_int_malloc` ← `malloc(2048)` | 由 `http_conn::reset()` 的 `m_read_buf.resize` 触发 |
| `epoll_ctl` | 由 `http_conn::write()` → `EventLoop::update_channel` 触发 |
| `0x0` 跳转（TSan 下） | 栈与返回链全为 0，vtable / `std::function` 被毁 |

崩溃轮次的 QPS 会先退化（同一配置 6500 → 3672），说明破坏在**累积**，malloc 逐渐变慢。

## 三、定位过程：二分法把范围收缩到 `do_request`

用「逐段移除响应生成的组成部分」的方式二分，每次记录 QPS 以确认负载可比：

| 变体 | QPS | 崩溃 |
|:--|--:|--:|
| 固定短响应（完全跳过 `process_read`） | 16181 | 0/5 |
| 只保留 `parse_request_line` | 16206 | 0/4 |
| 保留 `set_real_file`，跳过 `stat` 与 mmap | 16251 | 0/4 |
| 完整解析，仅禁用 mmap | 13040 | 3/5 |
| 完整处理 | ~21000 | 5/5 |

前四行的 QPS 处于同一量级，对比成立。落在 `do_request` 中 `set_real_file` 之后、且与 `FILE_REQUEST` 分支相关的一小段。

## 四、已经排除的原因

| 手段 | 结果 | 排除了 |
|:--|:--|:--|
| ASan（`-O0`/`-O2`，含 `quarantine_size_mb=0`） | 14+ 轮零报告 | 堆/栈越界写、use-after-free |
| `_GLIBCXX_DEBUG` | 3/3 崩溃，无容器误用报告 | `vector` 越界与迭代器失效 |
| TSan | 崩溃最快（约 94 个请求）但**无数据竞争报告** | 数据竞争 |
| `MALLOC_ARENA_MAX=1/2` | 崩溃率不变 | 多 arena 相关 |
| 运行时索引不变量检查 | 零命中 | `m_read_idx`/`m_checked_idx`/`m_body_start` 越界 |
| 运行时指针不变量检查 | 零命中 | `m_url`/`m_version`/`m_host`/`m_string` 指向缓冲之外 |
| 缓冲尾部金丝雀（`size` 与 `capacity` 之间） | 零命中 | 读/写缓冲被越界写 |
| `Channel` 析构时的 `in_epoll` 检查 | 零命中 | `epoll_event.data.ptr` 指向已析构的 Channel |
| 禁用空闲定时器 | 崩溃率不变 | 超时路径 |
| 禁用 mmap | 仍崩（3/5） | 文件映射与 `munmap` |

**特别值得记录的一点**：ASan 在所有配置下都不触发，而 Release 下 2.6 万个请求就崩——不是概率不足（ASan 下同等时间跑了约 6.5 万个请求），而是**这一类破坏不在 ASan 能覆盖的范围内**。此后不应再以「ASan 干净」作为此类问题的证据。

## 五、结论与后续

1. **缺陷是真实的**，且在压测场景下必现（`-t 1/2` 几乎必崩），不能当作噪声忽略
2. **但它不阻塞 3.5 与 3.6**：这两项是参数清理与文档，与请求处理路径无关
3. **它阻塞 3.4-b 的结论**：在一个随时会崩的进程上得到的「TSan 无数据竞争报告」不能作为验收证据
4. 下一步定位建议用 **valgrind**（能直接指出越界写/UAF 的指令位置）或 `LD_PRELOAD` 的电栅栏实现（`free` 后 `mprotect` 为 `PROT_NONE`）；本机当前未安装 valgrind，且两者都需要额外的环境权限或开发成本
5. 复现命令：

```bash
cmake -B build -DCMAKE_BUILD_TYPE=Release && cmake --build build -j4
cp build/server ./server
./server -p 9006 -m 0 -t 1 -c 1 &
taskset -c 0 wrk -t1 -c100 -d4s -H "Connection: close" http://127.0.0.1:9006/judge.html
```
