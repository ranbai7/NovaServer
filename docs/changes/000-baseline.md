# 000 · 性能基线

> 本记录不是一项优化，而是**所有优化的对比基准**。后续每项改动完成后，都需按本文的方法复测并与本表数据对比，才能量化收益。
>
> **后续进展**：项目完成阶段一、阶段二与核查修复之后，连接复用成为默认行为（`018`），内存布局也随动态缓冲（`013`）改变，本文的数字**不再适合作为阶段三重构前后的对比基准**。已在 `021-baseline-after-fixes.md` 另采一份并列归档，本文保留为「最初架构」的历史记录，两者不可直接对比，原因见那份记录第二节。

## 一、背景与动机

优化如果缺少起点数据，"提升了多少"就无从谈起。因此在改动任何代码之前，先完整测量一次当前实现的吞吐、延迟与资源占用，并把测量方法固化为可复现的脚本。

## 二、测量方法

### 测试环境

| 项 | 值 |
|:--|:--|
| 主机 | ubuntu22-virtual-machine |
| 虚拟化 | VMware |
| CPU | Intel Core i5-13500H，**4 个逻辑核** |
| 内存 | **3.8 GiB** |
| 内核 | 6.8.0-138-generic |
| CPU 窃取 | `st = 0`（宿主无争抢，虚拟化噪声可控） |
| 编译选项 | `-O2`（`make DEBUG=0`） |
| 服务端二进制 | 100352 字节 |

### 压测工具与参数

| 项 | 值 |
|:--|:--|
| 工具 | `wrk` 4.1.0（epoll） |
| 目标 | `http://127.0.0.1:9006/judge.html`（静态页面，约 2.3 KB） |
| 并发连接 | `-c100` |
| 单次时长 | `-d5s` |
| 重复次数 | 每组配置 **5 次，取中位数** |
| 日志 | 服务端以 `-c 1` 关闭日志，避免 I/O 干扰 |
| 变量控制 | 每次测量重启服务端进程；同一二进制、同一参数、同一时段连续完成 |

选择 `-c100` 的依据：预先在 50 / 100 / 200 / 500 四档并发下试跑，吞吐均稳定在 18k 附近不再上升，说明服务端已饱和，增大并发不会带来额外信息，只会放大客户端开销。

### 复现方式

```bash
make DEBUG=0 server
./test_pressure/bench.sh 100 5s 5
```

脚本位于 `test_pressure/bench.sh`，负责遍历配置组合、重启服务端、重复测量并输出中位数。原始输出归档在 `test_pressure/results/`。

## 三、测量结果

单位：QPS 越高越好，P50/P99 为毫秒，RSS 为服务端常驻内存。**加粗行**为默认配置（`-m 0 -a 0`）。

| -m | -a | -t | QPS | P50 (ms) | P99 (ms) | RSS (MB) |
|:--:|:--:|--:|--:|--:|--:|--:|
| **0** | **0** | **8** | **19808** | **0.323** | **899.99** | **262.8** |
| 1 | 0 | 8 | 17982 | 0.347 | 906.03 | 262.8 |
| 2 | 0 | 8 | 22373 | 0.234 | 1070.00 | 262.8 |
| 3 | 0 | 8 | 20641 | 0.241 | 842.26 | 262.8 |
| 0 | 1 | 8 | 18585 | 0.228 | 774.83 | 262.7 |
| 1 | 1 | 8 | 20332 | 0.234 | 822.54 | 262.7 |
| 2 | 1 | 8 | 16102 | 0.267 | 803.80 | 262.8 |
| 3 | 1 | 8 | 17685 | 0.285 | 202.60 | 262.8 |
| 0 | 0 | 1 | 19577 | 0.326 | 1130.00 | 262.7 |
| 0 | 0 | 2 | 19745 | 0.325 | 1190.00 | 262.7 |
| 0 | 0 | 4 | 19566 | 0.331 | 895.50 | 262.7 |

> `-m`：触发模式（0=LT+LT，1=LT+ET，2=ET+LT，3=ET+ET）；`-a`：0=Proactor，1=Reactor；`-t`：线程数。

### 测量噪声

同一配置重复 5 次的 QPS 波动范围约 **±10%**。例如 `-m 0 -a 0 -t 8` 的 5 次结果为 18037 / 19808 / 19590 / 20423 / 20074。

**这意味着：改进幅度小于 10% 的优化，在本环境下无法被可靠观测。** 后续对比需注意此阈值；如需更高精度，应增加重复次数或改用更隔离的测试环境。

## 四、结果分析

### 结论一：吞吐对工作线程数几乎不敏感

| 线程数 | QPS |
|:--:|--:|
| 1 | 19577 |
| 2 | 19745 |
| 4 | 19566 |
| 8 | 19808 |

四档之间差异不超过 1.3%，**远低于噪声水平**。单线程与八线程吞吐相同，说明工作线程数不是当前的吞吐瓶颈。可能的瓶颈位置有二：主线程的事件分发与 `accept` 路径，或压测客户端本身（`wrk` 仅用 2 个线程，与 4 核服务端存在资源竞争）。区分二者需要更隔离的环境，列为待确认项。

### 结论二：延迟长尾极为严重

平均的 P50 在 **0.23~0.35 ms**，而 P99 落在 **0.20~1.19 s**，两者相差约三个数量级。最差单次结果达到 1.3 s。

这说明绝大多数请求处理很快，但存在少量请求被严重延迟——在真实场景中，用户感受到的正是这些长尾请求。

### 结论三：连接侧触发模式实际未生效

`-m 0` 与 `-m 1` 的差异仅在 `connfd` 的触发模式（LT 与 ET），但实测 QPS 分别为 19808 与 17982，差异 9%，落在噪声区间内；`-m 2` 与 `-m 3` 同理。

这印证了 ROADMAP 中记录的初始化时序问题：注册文件描述符时读取的成员变量尚未赋值，导致连接侧实际始终按 LT 注册。因此 `-m 1` / `-m 3` 的参数组合从未真正改变连接行为。

**影响**：该缺陷修复后，ET 路径将首次真正执行，届时 `-m` 四种组合的表现需要重新测量。

### 结论四：内存占用与负载无关

所有配置下服务端常驻内存恒为 **262.7~262.8 MB**，与线程数、触发模式、并发模型均无关。这是按最大连接数预分配连接对象的直接结果——无论实际连接多少，这部分内存都已占用。

## 五、后续对比基准

阶段四复测时，优先关注以下四项：

| 指标 | 基线值 | 期望方向 |
|:--|:--|:--|
| 默认配置 QPS | 19808 | 提升 |
| P99 延迟 | 899.99 ms | 显著下降 |
| 常驻内存 | 262.8 MB | 明显下降 |
| 线程数对吞吐的影响 | 无差异（1.3% 以内） | 出现可观测的正相关 |

## 六、测量局限

1. **环境规模有限**：4 核 3.8 GiB 虚拟机，远小于生产环境，绝对数值不具备横向参考价值；本记录的价值在于同环境的前后对比。
2. **客户端与服务端同机**：两者争夺同一组 CPU 核心，吞吐上限可能由客户端而非服务端决定。
3. **压测客户端线程数偏低**：`wrk` 仅用 2 线程，可能未完全压满服务端。
4. **测量期间存在背景负载**：编辑器等常驻进程会引入噪声，这与观测到的 ±10% 波动相符。
5. **未测量纯静态与数据库密集路径的区分**：本次仅覆盖静态资源请求，登录注册等涉及数据库查询的路径未单独测量。

上述局限在优化完成后于云主机复测时可部分消除——届时需在云主机上以相同脚本重跑 `baseline-v1` 与优化后的版本，形成独立闭环的对比数据。
